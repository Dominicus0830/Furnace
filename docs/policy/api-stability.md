# API 안정성 정책

이 문서는 Furnace 플러그인 API(`furnace-api`)를 어떻게 바꾸고, 없애고, 버전으로 나타내는지 정한다. 플러그인 개발자가 Furnace 로 옮길지 판단하는 기준이므로, 여기 적힌 약속을 깨는 변경은 이 문서를 먼저 고친 뒤에만 할 수 있다.

근거: `docs/feature-parity/` 의 결정 D5(2026-11-06 수용), 불만 표 89·62번.

## 1. 버전 두 개

| 이름 | 어디에 적나 | 누가 보나 |
|---|---|---|
| API 버전 `apiVersion` | 플러그인 `plugin.yml` 등 매니페스트 | 플러그인 개발자, 서버 로더 |
| 마인크래프트 버전 | 서버 빌드 이름, 지원 클라이언트 | 플레이어, 운영자 |

- API 버전은 마인크래프트 버전과 **따로** 매긴다. 1.21.1 이후 마인크래프트 버전을 지원하더라도 API 버전 규칙은 같다.
- 새 마인크래프트 버전을 지원하는 일은 API 의 **마이너** 올림으로 처리한다. 그 자체로 메이저 올림이 되지 않는다.
- 매니페스트에 `apiVersion` 이 없으면 서버는 현재 메이저 버전으로 본다. 코드 쪽 구현은 B1 묶음에서 한다. 이 문서는 규칙만 정한다.

## 2. 버전 규칙 (semver)

`MAJOR.MINOR.PATCH` 를 쓴다.

- **PATCH**: 동작 버그 수정. 공개 타입·메서드 시그니처는 바뀌지 않는다. 이전 버전으로 만든 플러그인은 그대로 돌아가야 한다.
- **MINOR**: 호환되는 추가만 한다. 새 인터페이스, 새 메서드(기본 구현 포함), 새 이벤트, 새 열거형 값(이 경우 `switch` 를 쓰는 플러그인이 깨질 수 있다는 점을 릴리스 노트에 적는다). 기존 이름·시그니처·의미는 바꾸지 않는다.
- **MAJOR**: 호환이 깨지는 변경. 제거, 시그니처 변경, 의미 변경. 아래 3장의 폐기 절차를 거친 뒤에만 한다.

## 3. 폐기 절차

1. **대체 먼저.** 없앨 API 를 대신할 API 를 같은 버전(또는 그 이전 마이너)에 먼저 낸다. 대체가 없는 채로 폐기 경고만 내지 않는다.
2. **폐기 표시.** 대체 API 가 나온 마이너 버전에서 해당 API 에 폐기 표시를 붙이고, 문서에 대체 방법을 적는다. 콘솔 경고는 같은 항목에 대해 한 번만 낸다.
3. **최소 두 마이너 유지.** 폐기 표시 뒤에도 최소 두 마이너 버전 동안 동작을 유지한다.
4. **제거.** 제거는 MAJOR 올림에서만 한다. 제거 사실과 옮기는 방법을 릴리스 노트 맨 위에 적는다.

예외는 없다. 보안 문제로 긴급히 막아야 할 때도 대체 API 와 폐기 표시를 먼저 낸 뒤 제거 시점을 당긴다. 이 경우 릴리스 노트에 이유를 적는다.

## 4. 영구 지원 항목

다음은 폐기 대상이 아니다. 기존 플러그인이 많이 쓰고, 현재 대체 방식도 같이 있어야 하기 때문이다.

- **문자열 메시지와 Adventure `Component`(Text)**: 둘 다 영구 지원한다. 문자열 편의 메서드(예: 레거시 색 코드 `&` 를 쓰는 변환)는 폐기하지 않는다. 같은 일을 하는 두 방식이 공존하며, Adventure 쪽이 권장 방식이라는 점만 문서에 적는다. (불만 표 62번, 커뮤니티에서 문자열 폐기에 반대한 #9489 와 같은 입장이다.)
- **단순 명령(`BasicCommand`)과 Brigadier 명령**: 같은 트리에 등록할 수 있고, 둘 다 영구 지원한다.

## 5. 대상이 아닌 것

- `internal` 또는 `impl` 패키지, 리플렉션으로 접근하는 필드·메서드는 이 약속의 대상이 아니다. 필요한 것은 API 로 승격해서 정식 공개한다.
- 바닐라 결과를 바꾸는 운영 옵션(기본 꺼짐)은 옵션 이름과 기본값을 MINOR 에서만 추가한다. 기본값을 바꾸는 일은 MAJOR 에서만 한다.
- 실험용으로 표시한 API 는 위 규칙을 따르지 않는다. 대신 표시가 붙은 버전과 제거 계획을 함께 적는다.

## 6. 적용 시점

- 이 정책은 다음 릴리스부터 적용한다. 그 이전 API 는 가능한 범위에서 같은 규칙을 소급해 따른다.
- 정책을 바꾸면 이 문서를 먼저 고치고, 변경 이유를 같은 PR 설명에 적는다.
