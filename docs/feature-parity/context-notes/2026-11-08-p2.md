## 2026-11-08 Bukkit 비동기 작업 스레드 풀·종료 대기 (P2, paper-vs-spigot B2·B3·B4)

기준: Paper 1.21.1 패치 `Improved-Async-Task-Scheduler`, `Name-craft-scheduler-threads-according-to-the-plugin`, `Wait-for-Async-Tasks-during-shutdown`, `Add-getMainThreadExecutor-to-BukkitScheduler`(원문 읽기, 코드는 옮기지 않음). 위의 두 서버(Paper·Spigot) 중 Spigot 은 풀이 `newCachedThreadPool` 에 이름 `Craft Scheduler Thread - N` 이고 끌 때 기다리지 않는다. Paper 를 따랐다.

**구조**
- `LegacyScheduler` 가 비동기 풀을 직접 가진다(`newPlatformPool`: 코어 4·최대 `Integer.MAX_VALUE`·30초·`SynchronousQueue`·코어 스레드도 놀면 정리·미리 4개 띄움). 스레드는 데몬(Paper 는 아님 — 멈춘 작업이 JVM 종료를 붙잡지 않게 Furnace 만 다르게 했다).
- 옵션 `plugins.compat.scheduler.async-threads=platform|virtual`(기본 platform, 틀린 값은 기동 거부). 서버(`PluginSettings`)가 읽고 호환 모듈은 새 API `Furnace#compatOption(key)`(`plugins.compat.*` 키만, 글자 그대로)로 받는다. 기본값과 같게 적은 값은 안 적은 것과 같아 `compatOption` 이 null 이다(그래서 `PluginSettings.DEFAULT` 와 같은 설정).
- 일하는 동안 스레드 이름에 ` - 플러그인이름`을 붙이고 끝나면 되돌린다(가상 스레드 모드에서도 같은 규칙).
- 취소된 비동기 작업도 몸통이 끝나기 전까지는 `activeWorkers()`·`isCurrentlyRunning()` 에 남는다(CraftAsyncTask.cancel0 은 일꾼이 있으면 runners 에서 빼지 않는다). 전에는 취소 즉시 목록에서 사라졌다.
- 종료: 새 `PluginFormat#afterPluginsDisabled(Furnace)` 훅. `PluginManagerImpl.disableAll()` 이 모든 onDisable 뒤에 `PluginBootstrapper.afterAllDisabled` 로 이미 만든 어댑터에게만 부른다(Bukkit 플러그인이 없으면 호환 클래스는 올라오지 않는다 — `CompatIsolationTest`). `CompatFormat` 이 `Compat.awaitAsyncTasksAtShutdown` 으로 `awaitAsyncWorkers(5000)`: 100ms 마다 확인, 남으면 `Nag author(s): '[저자]' of '이름 vX' about the following: This plugin is not properly shutting down…` SEVERE. 그 뒤 풀을 `shutdown()`(인터럽트 없음).
- `getMainThreadExecutor(Plugin)`: `runTask` 로 다음 틱 전역(주) 스레드에서 돈다. 꺼진 플러그인이면 `IllegalPluginAccessException`, null 은 Paper 문구의 `IllegalArgumentException`.

**남은 차이**
- Paper 는 비동기 작업 대기열을 주 스레드가 아니라 관리 스레드 하나("Craft Async Scheduler Management Thread")가 돈다. Furnace 는 박동이 전역 스레드에서 돌고 도착한 비동기 작업만 풀로 넘긴다. 비동기 반복 작업이 아주 많은 서버에서 전역 스레드 부담이 되면 관리 스레드를 따로 두는 후속 작업을 하라(지금은 측정한 문제 없음).
- Paper API 의 `getAsyncScheduler()`(Folia 모양, `PaperSchedulers.Async`)는 아직 서버의 가상 스레드 실행기를 쓴다 — 같은 pinning 위험이 있다. 후속 후보.
- 플랫폼 풀은 Paper 처럼 스레드 수에 상한이 없다. 작업이 계속 블로킹하면 스레드가 늘어난다(Paper 와 같은 위험, 스레드 이름으로 어느 플러그인인지 보인다).
- 종료 대기는 `/stop`·Ctrl+C 경로의 `disableAll()` 에서만 돈다. `/plugins reload <이름>`(개발 모드 핫 리로드)은 기다리지 않는다(Paper 의 reload 는 기다린다 — 필요하면 후속).
- `PaperSchedulersTest.entityTasksFollowEntityAndRetiredFiresOnDisconnect` 는 이 변경 전 기준 브랜치에서도 이 컨테이너에서 실패한다(엔티티 스케줄러, 이 변경과 무관).
