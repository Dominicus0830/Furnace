## 2026-11-07 CraftBukkit 어댑터 — 근거·함정 (H6)

- **`Class.forName` 은 이름이 다른 클래스를 받지 않는다(이 컨테이너 JDK 21 로 직접 확인).** 클래스로더의 `findClass("p.v1.Target")` 가 `p.Target` 을 돌려주면 `loader.loadClass(...)` 는 그것을 받지만, `Class.forName(name, init, loader)`(그리고 상수 풀 해석)는 이름 불일치로 `ClassNotFoundException: p/v1/Target` 을 던진다. 그래서 "로더가 접미사 이름을 접미사 없는 클래스로 돌려준다"만으로는 리플렉션이 안 풀린다 — 바이트코드의 클래스 참조는 ASM 으로 바꾸고, 문자열 리플렉션은 호출 자리를 다리(`CraftNames`)로 돌린다.
- **엔티티 정체성.** Furnace 엔티티 핸들(`EntityHandle`)은 만든 순간 필드를 복사한 스냅샷이라 이벤트·검색마다 새 객체다. `Compat.entity` 가 예전처럼 매번 새 `CraftEntity` 를 만들면 `getHandle()` 의 정체성(`==`·Map 키)을 지킬 수 없다. UUID → 약한 참조 캐시로 같은 `CraftEntity` 를 돌려주고 새 스냅샷을 그 안에 갈아 끼운다. 플레이어는 접속 동안 핸들이 같으므로 예전 규칙(핸들이 바뀌면 새 `CraftPlayer` = 재접속) 그대로다.
- **Craft 계층을 "옮긴" 이유.** CraftBukkit 은 `CraftEntity ← CraftLivingEntity ← CraftHumanEntity ← CraftPlayer` 다. 설계(H5)의 `CraftPlayer extends CompatPlayer` 로는 `(CraftEntity) player` 가 성립하지 않는다(자바 단일 상속 — `CraftLivingEntity` 와 `CraftEntity` 를 Compat 줄 사이에 끼울 수 없다). 실제 플러그인이 가장 많이 쓰는 꼴이 `((CraftEntity) e).getHandle()` 이므로 Compat* 를 Craft* 로 옮겼다(`git mv`, 메서드 본문은 그대로). 옮기면서 `org.domi.furnace.compat.paper` 의 몇 클래스·메서드를 public 으로 열었다(`Compat.furnace/commandMap/services`, `CompatBlock`·`CompatChunk`·`CompatConsole`·`EntityPdc`·`CompatPlayerInventory`·`CompatInventory`).
- **바닐라 대조(`javap`, `main` 브랜치 `tools/vanilla-data/server-1.21.1`, 커밋 안 함).** `cuq`=ItemStack: `e()` isEmpty = `this == EMPTY || item == AIR || count <= 0`, `H()` getCount = 비었으면 0, `g()` getItem = 비었으면 `cut.a`(Items.AIR), `a(cuq,cuq)` matches = 같은 객체이거나 개수 같고 `c(...)`, `c(cuq,cuq)` isSameItemSameComponents = 종류 같고(둘 다 비었으면 참) 컴포넌트 `Objects.equals`, `b(cuq,cuq)` isSameItem, `toString` = `count + " " + item`(indy 레시피 `\u0001 \u0001`). `cul`=Item `toString` = `BuiltInRegistries.ITEM.wrapAsHolder(this).getRegisteredName()`(`jm.g()` = 키 문자열, 없으면 `[unregistered]`). `bsr`=Entity `equals` = 네트워크 id(`o`) 비교, `hashCode` = id.
- **ASM 프레임.** 리플렉션 호출을 다리로 바꿀 때 분기·지역 변수를 건드리지 않으므로 `COMPUTE_MAXS` 만 쓰고 스택 맵 프레임은 그대로 옮긴다(`Class.forName(String)` 앞에 `ldc 자기클래스` 하나를 더 넣어도 그 값은 바로 소비돼 프레임 지점의 스택은 같다). `COMPUTE_FRAMES` 의 `getCommonSuperClass` 가 병렬 로더에서 클래스를 잘못 로딩하는 문제(H5 검토 지적)를 피한다. `ClassWriter(reader, …)` 의 상수 풀 복사 최적화는 쓰지 않는다(옛 접미사 이름이 상수 풀에 남지 않게).
- **시험의 Spigot 모양 jar 만들기.** `JarCompiler.jar(…, stubs)` 로 `org.bukkit.craftbukkit.v1_21_R1.*` 스텁을 함께 컴파일하되 jar 에서 뺀다 — 실제 Spigot 플러그인 jar 와 같이 접미사 이름을 참조하지만 그 클래스는 서버에 없는 모양. 변환기를 빼면 시험이 `NoClassDefFoundError`·`ClassNotFoundException` 으로 실패하는 것을 확인했다(시험이 변환을 실제로 본다).
- **대조표가 늘어난 이유.** `compatReport` 를 다시 돌리면 `net.minecraft` 클래스가 "있음"이 되면서 그 클래스의 Spigot 난독화 멤버(`MinecraftServer#aA` 등)가 "클래스는 있는데 없는 멤버"로 올라온다(167 → 271). 퇴보가 아니라 측정 범위가 넓어진 것이다. 반면 `MinecraftServer#server`(9 jar)는 CraftBukkit 이 더한 필드라 shim 에 넣었다.
