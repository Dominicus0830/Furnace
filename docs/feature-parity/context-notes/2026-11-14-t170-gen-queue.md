# T-170 생성 대기열 재설계 (2026-11-14)

`furnace-gen-wait`(FIFO `newFixedThreadPool`)를 `world/GenQueue` 로 바꿨다. 근거: 공유 폴더 `furnace/reviews/w60-explore/W60-explore.md` 2·2-1장, 독립 검토 `W60-review.md` 2장, 반론 X(`opt-review-r2/X-rebuttal.md`) 3.2절. 결정 W-4 ①(굶김 없음).

## 동작

| 무엇 | 어떻게 |
|---|---|
| 순서 | 생성 요청은 그 차원 플레이어들과의 지금 체비셰프 거리 순(50ms 마다 다시 잼), 같으면 넣은 순. 플레이어 없는 차원은 넣은 순. 위치 없는 작업(재생성 등)은 늘 먼저. 미리 생성(`background`, T-175)은 맨 뒤 |
| 차례 | 생성 칸을 쓰는 사람(지금 걸어 둔 생성이 있거나 1초 안에 디스크에 없는 청크를 원한 사람)을 줄 세운다. 앞의 K 명(`turnOwners`, 기본 max(2, 예산÷16))만 큰 칸(`turnQuota`, 기본 16)을 받고 그 사람들 요청을 먼저 뽑는다. 한 사람이 16개를 시작하면(또는 2초가 지나거나 150ms 동안 걸 것이 없으면) 줄 뒤로 가고, 아직 시작 안 한 그 사람 요청은 취소한다(다음 차례엔 지나친 땅). 줄 선 사람은 칸 1 |
| 취소 | 플레이어 미리 불러오기(`Region.loadChunk(cp, true)`)로 걸린 생성은 **시작 전에** 어느 플레이어의 추적 범위(`trackingDistance + 1` 체비셰프 — `ChunkTrackingView.contains` 의 바깥 한 겹까지)에도 없으면 취소. 취소된 로드는 `CancellationException` 으로 끝나 플레이어 자리(`chunkPrefetches`·`genPrefetches`)가 돌아간다. 이미 시작한 생성(원형·장식 중간 상태)은 건드리지 않는다 |
| 시간 티켓 | 순간 이동 뒤·포털 티켓(`World.addTicket`, 5틱)의 로드는 티켓이 살아 있는 동안만 시야 밖이어도 남기고, 끝나면 시야 밖일 때 취소(`loadChunkForTicket` keepAlive). 고정으로 두면 60명이 한꺼번에 순간 이동할 때 사람당 9개씩 540개가 거리와 상관없이 3초 뒤 맨 앞으로 왔다 |
| 고정 | 그 밖의 요청자(영구 티켓·플러그인·스폰 청크·`chunkAt`)는 진행 중 요청을 `Ticket.pin()` 으로 고정 — 취소와 같은 원자 값 하나에 CAS 라 둘 중 하나만 이긴다. 이미 취소된 뒤에 붙으면 그 실패가 끝난 다음 새로 건다(취소가 새지 않는다). 고정 요청은 3초 넘게 기다리면 거리·차례와 상관없이 먼저 |
| 생성 칸 | 플레이어당 "디스크에 없는 청크" 미리 불러오기 수. 차례가 꺼져 있으면(`turnOwners=0`) `clamp(예산 ÷ 탐험 인원, 1, 16)` — 새로 원하기 시작한 사람은 바로 인원에 더한다(한꺼번에 순간 이동해도 저마다 16개씩 걸지 않게). 디스크 청크는 칸을 안 쓰고 예전 상한(16)만 — 이미 만든 땅은 느려지지 않는다. "디스크에 있나"는 열린 region 파일 위치표를 IO 없이 본다(`RegionFileStore.peekChunk`, 모르면 생성으로 셈) |
| 되돌리기 | `-Dfurnace.gen.order=fifo` = 예전과 같음(넣은 순, 취소·칸·차례 없음) |

손잡이(시스템 속성, 측정·운영용): `furnace.gen.turnOwners`(0 = 차례 끔 → 가까운 순 몰아주기), `furnace.gen.turnQuota`, `furnace.gen.turnMaxMs`(2000), `furnace.gen.budget`(전역 예산 = 생성 스레드 × 4), `furnace.gen.playerCap`(고정 칸, 0=자동 — 주면 차례도 끔), `furnace.gen.cancelDelayMs`(0), `furnace.gen.cancelMargin`(0), `furnace.gen.pinnedMaxWaitMs`(3000), `furnace.gen.strictBudget`(전역 토큰 — 측정용).

## 왜 차례인가 (60명 lines, 클라우드 4코어, 판마다 90초 걷기)

생성은 이웃 원형 7×7 을 함께 쓴다. 한 사람 둘레를 몰아 만들면 완성 하나에 원형 3.5개, 사람마다 하나씩 흩어 만들면 7~10개. 그래서 "몰아주기"는 빠르지만 몰아 받지 못한 사람은 영영 굶는다(요청이 뒤처져 거리가 커지면 앞서가는 사람의 새 요청에 계속 밀린다). 차례는 몰아주되 돌아가며 몰아 준다.

|---|---|---|---|---|---|---|---|---|
| F 예전 FIFO (e8 r0·r1) | 25.9·20.4 | 33.2·31.8 | 5.1 | 0.026 | 0 | 37·38 | 31~33초 | 11~20(최대 119) |
| 가까운 순 몰아주기 `turnOwners=0` (e8·e9 5판) | 32.9~41.1 | 33.9~42.9 | 3.5~4.1 | 0.15~0.20 | 0.004~0.007 | 23~26 | 2.2~3.0초 | 0 |

- 차례는 예전(F)과 받은 청크 수가 거의 같고(23~25 대 20~26), 발밑 평균은 3배, 굶는 사람은 37명 → 0~2명, 대기 30초 → 3초.
- 몰아주기는 총량이 가장 크지만 W-4(굶김 없음)에 어긋난다 — 손잡이로만 둔다.
- K=1·4, 차례 칸 8 은 모두 나빴다(K=4 는 동시에 흩어 만들어 16.9/초·굶는 사람 28, 칸 8 은 17.1/초·21).
- 클라우드 판끼리 흔들림이 크다(같은 설정 33 ↔ 43/초). 1판 비교로 결론 내지 말 것.

## 바닐라 동일성

- 무엇을 만드는지는 그대로고 **생성 순서**만 바뀐다. 겹치는 장식 결과가 순서에 따라 다를 수 있는 것은 바닐라도 같다(1차·B2 에서 받아들인 기준).
- 취소는 시작 전 요청만 — `ChunkPipeline` 의 원형·장식 상태는 시작한 요청만 만진다. 취소된 청크는 시야 안이면 다음 틱에 다시 걸린다(늦춰질 뿐).
- 바닐라 1.21.1 은 시야 안 청크에 티켓을 걸고 티켓 레벨(거리) 순으로 만들며, 시야를 벗어나면 티켓이 빠져 대기 작업이 내려간다 — 거리 순 + 시야 밖 취소와 같은 꼴.

## 함정

- `gen.queue` 는 시작한 요청만 잰다(생존자 편향). 굶김은 `batch.gqstale`(시작 못 한 채 아무 추적 범위에도 없는 생성 요청 수 — 취소되지 않고 남은 것)와 사람별 링 0~2(`r02zero`) 로 본다. `batch.gqowners`·`gqmaxper`·`gqnoown` 은 대기열 안 요청의 주인 수·한 사람 최대·주인 없는 수.
- lines 장면은 시작할 때 콘솔 tp 로 시간 티켓이 사람당 9개(60명 540개) 생기고 걷기 첫 20초 동안 이것부터 만든다 — 걷기 첫 구간 수치는 이 짐을 포함한다.
- FIFO 판은 봇이 청크를 거의 못 받아 땅 높이 모드가 y200 에 머문다(`ground` miss 가 큼) — 몹 부하가 작게 잡힌다. 판끼리 엔티티 수 비교는 같은 모드끼리.
- "뒤처진 요청 칸만 돌려받고 요청은 대기열에 남기기"는 공정하지만 생성이 절반(18.6/초)이 된다 — 흩어 만들기 때문. 폐기.
