# 채팅 처리 스레드: 연결별 순서 사슬 + 채팅 실행기 (T-035, 2026-11-14)

출처: 2차 CSP B6 1.6(채팅 처리기 200ms·8명 → 전역 틱 27초 멈춤), 반론 Y 2.3(`AsyncPlayerChatEvent` 처리기의 `callSyncMethod(...).get()` 교착),
1차 반론 C 3.3 + O12 D3 2라운드 답(사슬 조건 넷), 반론 2차 2장 D(`tap.inbound` 순서). 결정 D2 = Paper 처럼(11-14 추천대로).

## 고치기 전
- `ConnectionHandler.tryHandleChat` 이 채팅 본문을 `global().execute` 에 넣어 `AsyncChatEvent`(→ Bukkit `AsyncPlayerChatEvent`)가 **전역 스레드**에서 돌았다.
  `isAsynchronous()=true` 인데 `Bukkit.isPrimaryThread()=true`.
- 그래서 처리기 안의 흔한 패턴 `Bukkit.getScheduler().callSyncMethod(plugin, …).get()` 은 자기 자신(전역)이 돌려야 할 작업을 기다려 교착했다
  (시간 제한 없는 `get()` 이면 영구, 워치독 크래시). 막히는 처리기(DB·웹훅)는 시간·날씨·명령·RCON·`#tick` 을 함께 멈췄다.

## Paper 1.21.1 (PR #363 검토가 원문 대조 — `33ff3dff` 의 Adventure·Add-proper-async-player-disconnections·Configurable-chat-thread-limit 패치)
- `chatMessageChain = new FutureChain(server.chatExecutor)` — 이벤트·방송은 채팅 실행기("Async Chat Thread - #%d").
- 채팅 서명 풀기(`getSignedMessage`)는 `tryHandleChat(..., sync=false)` 로 **넷티 스레드에서** 한다. 명령은 `server.execute`(주 스레드)로 바로 가고
  **채팅 뒤로 줄 서지 않는다**(사슬로 가는 것은 채팅 방송과 서명 명령의 메시지 출력뿐). 그래서 Paper 는 디코더를 넷티·주 스레드가 순서 없이 쓴다.
- 명령 람다 첫 줄 `if (player.hasDisconnected()) return;`(CraftBukkit SPIGOT-7346).
- 스팸·`too_many_pending_chats`·`chat_validation_failed` 킥은 `disconnectAsync`: 주 스레드가 아니면 읽기를 멈추고 주 스레드에서 끊는다(PlayerKickEvent 는 주 스레드, 취소되면 다시 읽음).
- 채팅 실행기 크기 설정 `chat-executor-core-size`/`max-size`(기본 무제한). 대화 입력은 `processQueue` 로 주 스레드.

## Furnace 수정
- `server/chat/ChatChain`: 연결(`PlayerChatState.chain()`)마다 하나. chat·chat_command·chat_command_signed·chat_session_update 4패킷을
  **도착 순서대로 하나씩** 처리한다.
  - 채팅 단계(`append`/`appendThen`): 채팅 실행기 스레드에서 서명 풀기 → 입력 가로채기 확인 → `AsyncChatEvent` → 방송 → 스팸 셈.
    입력 가로채기(Conversation)는 전역에 넘기고 그 처리가 끝난 뒤 다음 단계로.
  - 전역 단계(`appendGlobal`): 명령 두 종류와 세션 바꾸기(+`initialize_chat` 방송). "끝남" = 전역 람다가 돌아온 때(region 꼬리 `CommandFuture` 는 안 기다림 — 전역 큐의 지금 보장과 같다).
  - 기다리는 동안 실행기 스레드를 붙잡지 않는다(`whenComplete` 로 이어 걸기). 단계 사이 happens-before 는 사슬 잠금·실행기 넘김·future 완료가 준다 →
    동기화 없는 `SignedMessageChain.Decoder` 를 채팅 단계와 명령 단계가 번갈아 써도 된다.
  - 상한 256(처리 안 된 단계). 넘치면 `disconnect.spam` 으로 끊는다(바닐라 스팸 감지는 메시지 10개 남짓에서 이미 끊으니 op 가 막힌 처리기 위로 수백 개를 몰아 보낼 때만). 한 번만.
  - 명령 단계는 플레이어가 이미 나갔으면 건너뛴다(SPIGOT-7346).
- 킥: 채팅 스레드에서 감지한 스팸·`too_many_pending_chats` 와 사슬 넘침은 `ServerCore.kickOnGlobal` — Paper `disconnectAsync` 처럼 읽기를 멈추고
  전역에서 `Player.kick`(PlayerKickEvent 는 전역), 취소되면 다시 읽는다. `Player.kick` 은 취소되면 false 를 돌려준다.
  - 실행기는 플랫폼 스레드 캐시 풀(가상 스레드 아님 — 결정 D1, synchronized 안에서 막히는 처리기가 운반 스레드를 붙잡지 않게).
- 루프에 그대로 남는 것: 패킷 읽기, `tap.inbound`(ProtocolLib 받는 리스너가 도착 순으로 보게), last-seen 갱신(`unpackAndApplyLastSeen`), 금지 문자 킥, 채팅 숨김 알림, `resetLastActionTime`.
- 받는 사람 쪽 서명 추적은 이미 `PlayerChatState.packAndTrack`(synchronized, 압축·보내기·추적이 한 묶음)이라 여러 채팅 스레드가 같은 사람에게 보내도 받는 순서와 추적 순서가 같다.

## 관측 차이
- 한 연결 안의 채팅·명령 순서는 그대로(바닐라처럼 한 줄). **Paper 와 다른 점**: Paper 는 서명 없는 명령을 채팅 뒤로 줄 세우지 않으므로,
  채팅 처리기가 막히면 Paper 는 그 플레이어의 명령이 바로 돌고 Furnace 는 처리기가 끝날 때까지 늦는다. 서명 풀기를 사슬 안에서 해
  디코더 경주가 없는 대신 치르는 값이다(바닐라 순서 쪽을 택함).
- 서로 다른 연결의 채팅은 이제 동시에 처리될 수 있다(Paper 와 같다).
- 채팅과 같은 연결의 다른 패킷(이동·플러그인 메시지 등)의 상대 순서는 Paper 처럼 보장하지 않는다(채팅이 비동기).
- `AsyncChatEvent`·렌더러는 채팅 실행기 스레드에서 불린다(문서 고침). `PlayerCommandPreprocessEvent` 는 전에도 지금도 전역 스레드(문서가 "연결 스레드"라고 잘못 적혀 있었다).
- 채팅 처리기 안의 **블록 읽기**(`getLocation().getBlock().getType()` 등)는 이제 `ThreadOwnershipException`(전에는 전역 + region 빌림으로 읽혔다).
  Paper 는 비동기 스레드에서도 값을 준다(경주 있음). 결정 D2(Paper 처럼 비동기)의 결과 — 후속 후보: 비동기 문맥(채팅·runTaskAsynchronously)의 블록 읽기를
  로드된 청크 스냅숏으로 주는 호환 계층 공통 길. 위치·체력·월드·손 아이템은 채팅 스레드에서도 값을 준다(검토 재현으로 확인).

## 시험
- `ChatThreadDeadlockTest`(호환): 처리기의 `callSyncMethod(...).get(5초)` 가 42 를 받는다 / 막힌 처리기 동안 전역 작업·틱·콘솔 명령이 돈다. **고치기 전 코드에서 둘 다 실패**(TimeoutException).
  스팸 킥 이벤트가 전역 스레드에서 / 막힌 채팅 뒤 명령은 나간 뒤 돌지 않는다(검토 R1·R2).
- `ChatChainOrderTest`: 채팅·`/say`·서명 채팅·서명 `/msg` 20개 + 가운데 세션 갱신 → Bob 이 받은 순서 = 보낸 순서, 세션 뒤 서명 유지. "사슬 없이 실행기에 바로" 변이에서 실패 확인.
- `ChatChainTest`: 순서·겹침 없음, 전역 기다리는 동안 스레드 하나짜리 실행기에서도 다른 사슬이 돈다, 상한, 실패 격리, 닫힌 전역.
- 시험 서버 `TestPlayer.sync()` 장벽이 그 연결의 사슬을 기다린다.
