# 채팅 처리 스레드: 연결별 순서 사슬 + 채팅 실행기 (T-035, 2026-11-14)

출처: 2차 CSP B6 1.6(채팅 처리기 200ms·8명 → 전역 틱 27초 멈춤), 반론 Y 2.3(`AsyncPlayerChatEvent` 처리기의 `callSyncMethod(...).get()` 교착),
1차 반론 C 3.3 + O12 D3 2라운드 답(사슬 조건 넷), 반론 2차 2장 D(`tap.inbound` 순서). 결정 D2 = Paper 처럼(11-14 추천대로).

## 고치기 전
- `ConnectionHandler.tryHandleChat` 이 채팅 본문을 `global().execute` 에 넣어 `AsyncChatEvent`(→ Bukkit `AsyncPlayerChatEvent`)가 **전역 스레드**에서 돌았다.
  `isAsynchronous()=true` 인데 `Bukkit.isPrimaryThread()=true`.
- 그래서 처리기 안의 흔한 패턴 `Bukkit.getScheduler().callSyncMethod(plugin, …).get()` 은 자기 자신(전역)이 돌려야 할 작업을 기다려 교착했다
  (시간 제한 없는 `get()` 이면 영구, 워치독 크래시). 막히는 처리기(DB·웹훅)는 시간·날씨·명령·RCON·`#tick` 을 함께 멈췄다.

## Paper 1.21.1 (기억, 대조 필요 — hub.spigotmc.org·papermc 원문은 이 컨테이너에서 못 읽음)
- `ServerGamePacketListenerImpl.chatMessageChain = new FutureChain(server.chatExecutor)`, `chatExecutor` 는 데몬 캐시 풀 "Async Chat Thread - #%d".
- 채팅: `tryHandleChat(..., sync=false)` → 서명 풀기는 netty 스레드, 이벤트·방송은 사슬(채팅 스레드). 명령: `server.execute`(주 스레드).
- 대화(Conversation) 입력은 `processQueue` 로 주 스레드에 넘긴다.

## Furnace 수정
- `server/chat/ChatChain`: 연결(`PlayerChatState.chain()`)마다 하나. chat·chat_command·chat_command_signed·chat_session_update 4패킷을
  **도착 순서대로 하나씩** 처리한다.
  - 채팅 단계(`append`/`appendThen`): 채팅 실행기 스레드에서 서명 풀기 → 입력 가로채기 확인 → `AsyncChatEvent` → 방송 → 스팸 셈.
    입력 가로채기(Conversation)는 전역에 넘기고 그 처리가 끝난 뒤 다음 단계로.
  - 전역 단계(`appendGlobal`): 명령 두 종류와 세션 바꾸기(+`initialize_chat` 방송). "끝남" = 전역 람다가 돌아온 때(region 꼬리 `CommandFuture` 는 안 기다림 — 전역 큐의 지금 보장과 같다).
  - 기다리는 동안 실행기 스레드를 붙잡지 않는다(`whenComplete` 로 이어 걸기). 단계 사이 happens-before 는 사슬 잠금·실행기 넘김·future 완료가 준다 →
    동기화 없는 `SignedMessageChain.Decoder` 를 채팅 단계와 명령 단계가 번갈아 써도 된다.
  - 상한 256(처리 안 된 단계). 넘치면 `disconnect.spam` 으로 끊는다(바닐라 스팸 감지는 메시지 10개 남짓에서 이미 끊으니 op 가 막힌 처리기 위로 수백 개를 몰아 보낼 때만).
  - 실행기는 플랫폼 스레드 캐시 풀(가상 스레드 아님 — 결정 D1, synchronized 안에서 막히는 처리기가 운반 스레드를 붙잡지 않게).
- 루프에 그대로 남는 것: 패킷 읽기, `tap.inbound`(ProtocolLib 받는 리스너가 도착 순으로 보게), last-seen 갱신(`unpackAndApplyLastSeen`), 금지 문자 킥, 채팅 숨김 알림, `resetLastActionTime`.
- 받는 사람 쪽 서명 추적은 이미 `PlayerChatState.packAndTrack`(synchronized, 압축·보내기·추적이 한 묶음)이라 여러 채팅 스레드가 같은 사람에게 보내도 받는 순서와 추적 순서가 같다.

## 관측 차이
- 한 연결 안의 채팅·명령 순서는 그대로. 서로 다른 연결의 채팅끼리는 이제 동시에 처리될 수 있다(Paper 와 같다).
- 채팅과 같은 연결의 다른 패킷(이동·플러그인 메시지 등)의 상대 순서는 Paper 처럼 보장하지 않는다(채팅이 비동기).
- `AsyncChatEvent`·렌더러는 채팅 실행기 스레드에서 불린다(문서 고침). `PlayerCommandPreprocessEvent` 는 전에도 지금도 전역 스레드(문서가 "연결 스레드"라고 잘못 적혀 있었다).
