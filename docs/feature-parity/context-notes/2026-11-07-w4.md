## 2026-11-07 구조물 템플릿 API·청크 티켓 API (W4, 불만 표 43·46번)

문서: `docs/api/structures.md`, `docs/api/chunk-tickets.md`. 코드: `api/structure/*`, `api/world/ChunkTicket(s)`, `server/plugin/StructuresImpl`·`ChunkTicketsImpl`, `World.addPluginTicket/removePluginTicket`.

- **46번 "먼저 확인"의 결과**: 플러그인 소유 티켓은 없었다. 있던 것은 시간 제한 티켓(`World.addTicket` — 포털·드래곤)과 `/forceload`(`ForcedChunks`, 저장됨)뿐이었다. 그래서 `pluginHolds`(퇴출 막기)·`pluginTicking`(엔티티·블록 엔티티 틱) 개수 표 두 개를 `World` 에 새로 두고, `World.ticketed`(퇴출 판단)와 `Region.blockEntityTicking`(틱 판단)이 보게 했다. 틱 단계는 `/forceload` 와 같다(무작위 틱·자연 스폰은 바닐라처럼 플레이어 가까이만).
- Paper 의 plugin chunk ticket 이 정확히 어느 티켓 레벨인지는 Paper 소스를 볼 수 없어 확인 못 했다(가정: 청크를 로드된 채로 두고 엔티티 틱까지 준다). 그래서 `ticking` 을 고를 수 있게 했고, 한 줄짜리 `add(owner, world, cx, cz)` 는 `ticking=true`.
- 티켓 장부는 플러그인 객체(`FurnacePlugin`) 단위이고 `PluginManagerImpl.disable` 이 `releaseAll` 을 부른다. 꺼진 뒤 늦게 오는 `add` 는 거절한다(가짜 광원 API 와 같은 `cleared` 약한 집합 방식 — 켜지지 않은 시험용 인스턴스는 거절하지 않는다).
- **43번 해석**: "배치·저장·찾기"를 ① `place`(구조물 블록 불러오기·`/place template` 과 같은 `TemplatePlacer.placeInWorld`), ② `save`(구조물 블록 저장의 `StructureBlockEntity.fillFromWorld`), ③ `locate`(`/locate structure` 의 `StructureLocator.findNearest`) + 저장소 조작(목록·정보·가져오기·내보내기·지우기)로 풀었다. 바닐라와 같은 코드 경로를 그대로 부르므로 새 바닐라 대조는 없다.
- **함정(region 경계)**: 배치기·저장기는 `RegionLevel` 한 개가 가진 청크 안에서만 읽고 쓴다(`LiveGrid`). 영역이 여러 청크에 걸치면 먼저 임시 티켓(`addPluginTicket(..., false)`)으로 전부 올린 뒤 시작 청크의 region 에서 하고, 그 region 이 아직 이웃 청크를 안 가졌으면(합치기는 region 이 쉬는 동안만 일어난다) 100ms 간격으로 최대 20번 다시 한다. 그래도 안 모이면 아무것도 바꾸지 않고 `NOT_LOADED`. 임시 티켓은 끝나면 놓는다(`withRegion`).
- **함정(가장자리 한 칸)**: 배치기의 가장자리 모양 갱신(`ShapeUpdater.updateShapeAtEdge`)이 영역 바로 바깥 한 칸을 읽는다. 그 칸의 청크가 `LiveGrid` 에 없으면 `missingAccess` 로 `checkComplete` 가 실패한다(처음 시험에서 청크 가장자리까지 꽉 찬 판이 `FAILED` 였다). 그래서 올리는 청크 범위를 영역 ±1 칸으로 넓혔다. `/place template` 은 이 여분을 안 올려서 같은 경우 "not loaded" 로 거절한다(바닐라는 필요한 청크를 그 자리에서 불러오는 차이).
- 영역이 `LiveGrid.MAX_GRID_RADIUS`(9, 19x19 청크)를 넘으면 `TOO_LARGE`. 청크를 올리기 전에 미리 계산해 거절한다(`/place` 의 "anything larger than 19x19 chunks" 와 같은 한계). `MAX_GRID_RADIUS` 를 public 으로 열었다.
- **기본값 차이**: `PlaceOptions.includeEntities` 기본 참(`/place template` 은 엔티티를 만든다), 구조물 블록은 기본 거짓(ignoreEntities=true). `SaveOptions.includeEntities` 기본 거짓(구조물 블록과 같다). 코드에서 명시하면 둘 다 고를 수 있다.
- 팔레트 선택: 바닐라는 `settings.getRandom(pos).nextInt(size)` 로 고른다. API 의 `palette >= 0` 은 그 번호 하나만 남긴 템플릿 보기(`StructureTemplate.onlyPalette`)를 놓아 고른다. -1 이면 바닐라 그대로.
- `seed=0` 은 지금 시각(바닐라 `createRandom(0)` 과 같음) — 상자 전리품 시드와 `integrity<1` 의 BlockRot 이 시드를 쓴다. 같은 시드면 같은 결과(시험으로 확인).
- 템플릿 이름 검사는 `TemplateManager.pathOf`(바닐라 `createAndValidatePathToGeneratedStructure` — `//`·밖으로 나가는 경로 거절)와 `ResourceId`(소문자·숫자·`_-.`/ 만). 가져오기(`define`)는 `size`·`blocks`·`palette(s)` 가 없으면 거절하고 데이터 픽서(Q8)를 거친다.
- `locate` 는 `/locate` 의 단일 스레드 작업기와 별개의 전용 단일 스레드(`furnace-structure-locate`)를 쓴다. `StructureLocator` 가 스레드 안전한지는 `/locate` 가 한 스레드로 돌리는 것에 맞춰 같은 방식으로 직렬화했다. 반경 상한 100 청크(`/locate` 와 같음).
- 남은 한계: ① 한 템플릿 놓기가 여러 region 에 걸친 먼 청크 사이를 잇지 못함(위 `NOT_LOADED`), ② 데이터 팩이 정의한 새 구조물 종류 찾기 불가(`/locate` 와 같은 한계), ③ 틱 사이 영역의 블록이 다른 스레드(플레이어)에 의해 바뀌는 경쟁은 region 스레드에서 한 번에 놓으므로 없다. 플레이어에게 새 블록을 보내는 건 `commit` 의 `setBlock` 방송 경로.
