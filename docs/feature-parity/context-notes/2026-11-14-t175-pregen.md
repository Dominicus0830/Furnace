# T-175 미리 생성 명령 (2026-11-14)

`/furnace pregen` — 운영 설명은 `docs/ops/many-players-pregen.md`, 코드 머리말은 `world/Pregen.java`·`command/builtin/PregenCommands.java`. 결정 W-3 ①(만든다), P-O04-15(D9)와 같은 것.

## 설계

| 무엇 | 어떻게 |
|---|---|
| 순서 | 가운데 청크에서 바깥으로 고리마다(고리 k = 둘레 8k 칸, 위 +x → 오른 +z → 아래 −x → 왼 −z). 영역 밖 칸은 건너뛰고 번호는 영역 안 칸만 센다 — 진행 파일은 번호 하나(`next`)로 이어 한다. 고리 안에서는 이웃으로 이어 가서 이웃 원형(7×7)을 함께 쓴다 |
| 대기열 | `Region.loadChunkBackground` → `GenQueue.Ticket.forBackground()`. T-170 대기열의 `(2 << 32)` 맨 뒤 키, 시야 밖 취소·차례·고정 대기(3초) 모두 무관. 플레이어 요청이 하나라도 있으면 그 뒤라 차례·전역 예산 규칙을 안 건드린다 |
| 붙은 요청 | 다른 요청자(플레이어 미리 불러오기 포함)가 진행 중인 미리 생성 로드에 붙으면 `Ticket.promote()` — 고정하고 맨 뒤 표시를 뗀다(다음 거리 재기에서 보통 요청처럼). 붙지 않으면 플레이어가 미리 생성 차례를 기다려 굶는다 |
| 멈춤 | 상태(volatile) 쓰기 → 진행 중 키의 표를 `cancelBackground()`(시작 전·안 붙은 것만). region 쪽은 요청을 건 뒤 상태를 다시 보고 멈췄으면 스스로 취소 — 둘 중 하나는 반드시 상대를 본다(드커 꼴) |
| 건너뜀 | 올라와 있으면 끝. 아니면 그 청크 IO 레인에서 `RegionFileStore.hasChunk`(위치표만) — 앞서 넣은 저장 뒤에 보므로 방금 저장한 청크도 있다고 본다 |
| 창 | 동시에 걸어 두는 청크 = 생성 스레드 × 2(`furnace.pregen.window`). 창 1 은 같은 땅에서 약 3배 느렸다(169 청크 20초 대 6초) |
| 역압 | `World.ioBackedUp()` 이거나, 이번 실행에서 만든 청크 중 아직 올라와 있는 것이 1024 개(`furnace.pregen.maxResident`) 이상이면 200ms 뒤 다시. 30초 넘게 올라와 있는 청크는 누가 붙잡은 것으로 보고 더 세지 않는다(스폰 근처 미리 생성이 영영 멈추지 않게) |
| 내려가기 | 만든 청크는 티켓 없이 올라와 구독자가 없으면 `evictIdleChunks` 유예 뒤 저장·내려간다 — 플레이어가 지나간 청크와 같은 길. 엔티티 틱(시뮬레이션 거리)·무작위 틱(128 블록)은 플레이어 근처만이라 미리 생성 청크는 틱을 받지 않는다(바닐라 Chunky 티켓 레벨 33 과 같은 관측) |
| 진행 파일 | 차원 `data/furnace_pregen.properties`(원자적 교체), 시작·보고(10초)·멈춤 때. 끝나면·`cancel` 이면 지운다. 재기동 뒤 자동으로 이어 하지 않는다(Chunky `continue-on-restart` 기본 false 와 같다) |
| 중복 | 한 차원에 하나. 멈춰 둔 진행 파일이 있으면 `start` 를 거절(`resume`/`cancel` 먼저) |

## 함정

- **멈췄다 바로 이어 하면 취소된 옛 요청에 붙는다.** 취소된 미리 생성 요청은 대기열에서 뽑혀 `tryStart` 거짓 → `CancellationException` 으로 끝나기까지 잠깐 `loading` 에 남는다. 새 미리 생성이 그 진행 중 로드에 붙으면(미리 생성끼리는 고정·promote 안 함) 취소 실패를 받는다. 처음엔 이것을 "대기열이 닫힘"으로 보고 멈춰 버렸다 — 대기열이 안 닫혔으면 같은 청크를 다시 건다(3번까지).
- **취소한 요청은 대기열에서 바로 빼야 한다(검토 R1).** `cancelBackground` 는 상태만 바꿔서 맨 뒤 키 그대로 대기열에 남았고, 그 청크에 붙은 요청자(고정 요청·플레이어 미리 불러오기)가 대기열이 빌 때까지 기다렸다. `pickLocked` 가 취소된 요청을 가장 먼저(키 `Long.MIN_VALUE`) 뽑아 만들지 않고 끝낸다. 시험 `PregenStopJoinTest`.
- 다시 걸기 3번을 다 써도 대기열이 안 닫혔으면 그 청크만 실패로 세고 계속한다(R3). 진행 파일의 수는 이어 할 번호 뒤에서 먼저 끝난 청크를 뺀다 — 이어 하면 다시 보므로(R4). 보고 때 파일 쓰기는 잠금 밖에서, 순번으로 옛 내용이 새 내용을 덮지 않게, 끝·취소 뒤엔 다시 만들지 않게(R5).
- 시험 `PregenTest` 는 생성 스레드 1 개짜리 `GenQueue` 를 위치 없는 작업으로 막아 두고 순서를 본다. 창 2 안에서는 디스크 확인(IO 풀 2 스레드)이 끝난 순으로 대기열에 서므로 "가운데가 맨 처음"이 아니라 "처음 두 개 안"이다.

## 결과 동일성 확인 (클라우드 4코어, 시드 12345)

- 미리 생성은 플레이어가 걸어가 만드는 것과 같은 `Region.loadChunk` → `AnvilWorldSource.loadChunkAsync` → 생성기 → `finishLoad`(빛·생성 때 동물·블록 엔티티) → 저장 길을 탄다. 다른 것은 대기열 순서뿐이다.
- 같은 영역(3000,3000 둘레 13×13)을 창 1(순서 고정)로 두 번 만들면 **블록·바이옴·하이트맵·구조물이 169/169 청크 모두 같다.** 창 기본(순서가 스레드 타이밍에 따라 바뀜)과 견주면 39/169 청크에서 광석 덩어리·얼음 기둥 등 경계를 넘는 장식 1818 블록이 다르다.
- 스폰 둘레 21×21 을 미리 생성(기본 창) 두 번 / 미리 생성 대 `/forceload` 로 만든 것도 겹치는 장식(이끼·점토·스컬크·동굴 덩굴)이 다르다 — 생성 순서 의존이고 미리 생성 탓이 아니다(T-170 노트 "바닐라 동일성"과 같은 기준: 바닐라도 겹치는 장식은 청크가 만들어진 순서를 따른다). 비교 스크립트는 공유 폴더 `furnace/reviews/t175-pregen/`.
