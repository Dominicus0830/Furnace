## 2026-11-12 복잡한 12종 와이어 대조 (easy-nms E5)

- **확인 방법**: E4b 와 같은 하네스 — Furnace 로 쓴 프레임을 바닐라 1.21.1 서버 jar 의 `GameProtocols` 코덱으로 읽고 다시 써 바이트를 비교한다(실행법은 `2026-11-12-easy-nms-e4b.md`, 재현 자료 `/mnt/project-files/furnace/reviews/e5-repro/`). 동적 레지스트리는 damage_type(`-Ddmg`)·chat_type(`-Dchat`) 을 넣는다. 하네스·바닐라 코드는 커밋하지 않는다.
- **결과**: 132 프레임 모두 같은 바이트(ok=132 bad=0). 입자 전 종류, 명령 인자 parser 전 종류, recipe_serializer 23종 전부, 빛·청크·발전 과제·태그·상인 거래·서명 채팅 세 가지 거름 방식·번들 구분자를 포함한다. 값이 달라진 6건은 모두 바닐라 쪽 정규화다: 블록 상태 입자 4종과 폭발의 블록 입자는 바닐라가 빠진 속성을 기본값으로 채워 읽고(`oak_stairs[facing=east,half=top]` → `…,shape=straight,waterlogged=false]`, 같은 상태 번호), 먼지 크기 9.0 은 바닐라 생성자가 4.0 으로 죈다(Furnace 도 쓸 때 죈다).
- **level_particles**: bool override_limiter, f64 셋, f32 넷(x_dist·y_dist·z_dist·max_speed), i32 count, 입자 = particle_type 번호 + 종류별 내용. vibration 의 목적지는 position_source_type 번호(block 0 = BlockPos, entity 1 = varint id + f32 y_offset) + varint arrival_in_ticks.
- **explode**: f64 셋, f32 power, 부서진 칸 목록은 `Mth.floor(x/y/z)` 에서의 i8 차이 셋 — 바닐라는 `(byte)` 로 잘라 쓰므로 ±128 밖이면 엉뚱한 칸이 간다. Furnace 는 쓸 때 거부. 그 뒤 f32 밀림 셋, BlockInteraction 서수, 작은·큰 입자, 소리(holder — E4b 직접 정의 소리 규칙과 같다).
- **light_update / 청크 빛**: BitSet 넷(`toLongArray` — 끝의 0 long 은 빠진다) + `byteArray(2048)` 목록 둘. 바닐라 클라이언트 `DataLayer` 는 정확히 2048 바이트가 아니면 예외, 마스크 비트마다 배열을 하나씩 `next()` 하므로 모자라면 NoSuchElementException — 둘 다 쓸 때 거부.
- **level_chunk_with_light**: i32 x·z, heightmaps NBT, 구역 버퍼(varint 길이, 2 MiB 상한), 블록 엔티티 목록(u8 packed_xz, i16 y, block_entity_type 번호, NBT 또는 없음 태그). 구역 버퍼 내용은 해석하지 않고 그대로 둔다.
- **commands**: 노드마다 플래그 바이트(종류 0~2, 4 실행, 8 리다이렉트, 16 제안), 자식 번호 목록, 리다이렉트, 이름, 인자 종류(command_argument_type 번호 + 내용), 제안 이름. 수 범위 인자는 플래그 바이트(1 최솟값, 2 최댓값) 뒤 있는 것만. 받는 쪽 `validateEntries` 는 자식·리다이렉트 둘 다 해결된 노드를 반복해 빼며 남으면 "impossible command tree" — Furnace 는 같은 알고리즘으로 쓸 때 거부. 자식 하나 + 리다이렉트 하나가 서로 가리키는 것은 바닐라 기준 순환이 아니다(생성기의 첫 "순환" 표본은 실제로 통과).
- **player_chat**: uuid, varint index, 선택 서명 256바이트, 본문(256자, i64 시각, i64 salt, 마지막 확인 목록 20개), 선택 unsigned 텍스트, FilterMask(서수, PARTIALLY_FILTERED 만 BitSet), ChatType.Bound.
- **update_recipes**: 레시피 = RL id + recipe_serializer 번호 + 내용. shaped 는 width·height varint 뒤 재료가 개수 없이 width×height 개, 바닐라 클라이언트 `RecipeManager` 는 같은 id 가 두 번이면 중복 키로 실패 — 쓸 때 거부. 재료 하나는 아이템 목록(빈 스택 불가 — `ItemStack.STREAM_CODEC`).
- **recipe(책)**: 상태 서수, 책 설정 bool 8개(제작·화로·용광로·훈연기 순으로 열림·거름), 이름 목록, INIT 일 때만 강조 목록.
- **update_advancements**: DisplayInfo 의 i32 플래그(1 배경, 2 토스트, 4 숨김), 배경 RL 은 플래그 1 일 때만. 진행도는 맵(id → criterion 이름 → 선택 i64 시각).
- **update_tags**: 맵(레지스트리 RL → 맵(태그 RL → varint 목록)).
- **merchant_offers**: ItemCost = item holder 번호, varint 개수(1 이상), DataComponentPredicate(타입 있는 컴포넌트 목록). 제거된 컴포넌트는 나타낼 수 없다. 바닐라 클라이언트는 out_of_stock 이면 uses 를 max_uses 로 맞춘다.
- **bundle_delimiter**: 본문 없음. 짝이 깨지면 클라이언트 번들 상태가 엉키므로 플러그인이 혼자 보내지 못하게 막았다(`sendBundle` 을 쓴다).
- **맵인 목록**: 태그·진행도는 바닐라 맵이라 같은 키가 두 번이면 마지막 값만 남는다. Furnace 는 읽을 때 같게, 쓸 때는 거부(키는 RL 처럼 비교 — `"item"` = `"minecraft:item"`).
- **서버 청크 패킷의 빛 마스크(고침)**: `ChunkSerializer` 가 빈 마스크를 `long[]{0}`(길이 1 + 0) 으로 써 바닐라(`BitSet.toLongArray` → 길이 0)와 바이트가 달랐다. 클라이언트는 똑같이 읽어 보이는 차이는 없었지만, furnace-test `GenericPacketRoundTripTest` 가 E5 로 청크 패킷을 읽게 되며 찾았다. `LightUpdate` 처럼 빈 집합은 길이 0 으로 쓴다.
- **독립 검토(PR #275)로 더 찾은 것**: 검토 재실행은 131 같은 바이트 + update_tags 1개가 레지스트리 순서만 다름(바닐라 `ResourceKey` 는 hashCode 를 덮어쓰지 않아 HashMap 순서가 실행마다 다르다 — 구현 때 ok=132 는 그 실행의 순서 덕).
  - 명령 인자 `minecraft:resource`·`resource_or_tag` 는 클라이언트 `ResourceArgument`·`ResourceOrTagArgument` 생성자가 `lookupOrThrow` 로 레지스트리를 찾아, 없으면 IllegalStateException 으로 끊긴다(`resource_key`·`resource_or_tag_key` 는 찾지 않는다). `TagCollector.applyTags` 도 `registryOrThrow`. 둘 다 쓸 때 클라이언트 레지스트리(정적 78 + 동기화 11, `registries/client-registries-1.21.1.txt` — 정적은 바닐라 jar 의 BuiltInRegistries.REGISTRY 를 돌려 뽑음)로 검사한다.
  - 원격 연결의 `TagCollector.updateTags` 는 동기화 대상이 아닌 레지스트리의 태그를 모두 `resetTags` 한 뒤 적용한다 — update_tags 는 전체 교체(문서 경고).
  - 클라이언트 `MessageSignatureCache` 는 128칸이고 `unpack(id)` 가 배열을 바로 읽는다 — 서명 번호 128 이상은 AIOOBE 로 끊긴다. MESSAGE_SIGNATURE_PACKED 쓰기에 127 상한(delete_chat 도 같은 노드).
  - 번들 구분자: 서버 번들은 `Player.sendBundle` 이 구분자 프레임을 직접 넣어 리스너를 거치지 않는다(검토가 걱정한 리스너 취소 경로는 지금 없다). 그래도 PacketEvent 에서 구분자 취소·바꾸기는 막았다.
  - 다른 노드의 자식으로 ROOT 를 두는 것은 `NodeResolver.resolve` 가 `instanceof RootCommandNode` 로 건너뛰어 거부하지 않는다.
  - 기록만: 읽기가 바닐라 디코드보다 엄격한 곳 — ItemCost 개수 0 이하, 같은 조건 컴포넌트 두 번(바닐라는 목록이라 받는다), 명령 노드 종류 3(바닐라는 stub null 로 ROOT 처럼 다룬다). 서버가 보낸 패킷만 읽으므로 영향 없음.
