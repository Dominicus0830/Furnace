# 호환 계층 실제 플러그인 시험 (H4) — 2026-11-07

H1~H3 이 `furnace-compat-paper` 에 Bukkit 호환 API 를 새로 써 넣었지만(컨테이너에서 Bukkit·Paper 원문을 못 받아 기억 기준의 clean-room), 그것이 **실제 플러그인이 쓰는 API 와 얼마나 겹치는지**는 재 본 적이 없었다. H4 는 그것을 잰다: 실제 Bukkit·Paper API 로 컴파일된 jar 를 가져와 (1) 바이트코드가 요구하는 API 를 호환 계층과 견주고 (2) 플러그인 jar 는 헤드리스 서버에 올려 본다. 결과는 표와 우선순위로 남기고, 이후 후퇴를 막는 기준표(시험)를 둔다.

- 상세 대조표(생성 파일): [`compat-h4-coverage-2026-11-07.md`](compat-h4-coverage-2026-11-07.md)
- 기준표(후퇴 방지): `furnace-compat-paper/src/test/resources/realworld-baseline.properties`
- 사용자 결정·확인: `docs/user-todo/entries/2026-11-07-h4.md`, 함정: `docs/feature-parity/context-notes/2026-11-07-h4.md`

## 범위 해석 (가장 그럴듯한 읽기)

작업 묶음 문서의 H4 는 "실제 Bukkit·Paper 플러그인 몇 개로 기동·동작 시험(호환 표 작성). NMS·CraftBukkit 을 직접 쓰는 플러그인도 표에 넣는다"이다. 이를 **측정 묶음**으로 읽었다 — 호환 API 를 더 넣는 묶음이 아니다. 측정에서 나온 빈틈은 순위로 정리해 다음 묶음의 입력으로 넘기고, 이 PR 에서는 API 를 새로 만들지 않았다(만들면 "측정 전후"가 섞인다). 예외로 H1 이 H4 에 넘긴 `DamageCause.CAMPFIRE` 존재 확인은 아래 "확인한 것"에 있다.

## 어떻게 쟀나

1. **jar 확보**: 컨테이너는 Maven Central(구글 미러 포함)에만 닿는다. Modrinth·Hangar·SpigotMC·GitHub 릴리스·papermc 저장소·JitPack·CodeMC 는 모두 막혀 있어 Vault·PlaceholderAPI·EssentialsX·LuckPerms·WorldEdit 같은 인기 플러그인 jar 는 받지 못했다. Central 에 있는 실제 jar 만 썼다(버전 고정, `furnace-compat-paper/build.gradle.kts` 의 `realWorld` 설정).
   - **실제 플러그인(plugin.yml 있음)**: `helper 5.6.14`(대형 플러그인 라이브러리, 1197 클래스), `CommandAPI 10.1.2`(Brigadier·NMS 를 리플렉션으로 깊이 쓰는 인기 플러그인).
   - **실제 플러그인들이 흔히 가져다 쓰는 라이브러리(실제 Bukkit 으로 컴파일됨)**: bStats, XSeries, cloud(bukkit·paper), CommandAPI core, commodore, InventoryFramework, adventure-platform-bukkit, FastBoard, BoostedYAML.
2. **정적 대조**(`Coverage`): 클래스 파일 상수 풀에서 `org.bukkit.*`·Paper·Spigot·BungeeChat·CraftBukkit·NMS·Adventure·서버 제공 라이브러리 심볼(클래스·필드·메서드, **반환형까지 정확한 서명**)을 읽고, 호환 계층 클래스(반사)와 JVM 심볼 해석 규칙(JVMS 5.4.3: 자기→상위 클래스→상위 인터페이스, 인터페이스 참조도 `Object` 메서드 허용)으로 견준다. 결과는 "요구 상한"이다 — 그 코드 경로가 실제로 실행되는지는 모른다.
3. **동적 기동**(`LivePluginProbe`): plugin.yml 이 있는 jar 를 `FurnaceTestServer` 에 올려 5틱 돌리고, 서버 로그(logback 어펜더)에서 가장 안쪽 예외를 모은다.

## CraftBukkit·NMS 를 직접 쓰는 쪽 (H5~H7 의 수요)

정적으로 보이는 `org.bukkit.craftbukkit.*`·`net.minecraft.*` 클래스 참조는 600개가 넘지만(생성 문서 2·5장) 대부분은 **리플렉션 문자열이 아니라 상수 풀에 이름이 직접 적힌 경우**만 잡힌 값이다. 실제로는 훨씬 많은 NMS 접근이 문자열로 가려져 있어 정적 수치는 하한에 가깝다. 관찰:

- **버전 붙은 CraftBukkit 패키지**: 실제 jar 안에 `org.bukkit.craftbukkit.v1_20_R1`·`v1_20_R2` 처럼 **서버 버전별 리로케이션 패키지**를 이름으로 가진 클래스가 있다(예 `…v1_20_R1.inventory.CraftItemStack`). 1.21.1 서버가 Paper 라면 리로케이션 없는 `org.bukkit.craftbukkit` 이라고 기억하지만(원문 대조 못 함), 옛 플러그인 다수가 `Bukkit.getServer().getClass().getPackage().getName()` 의 마지막 조각으로 버전 문자열을 얻어 클래스를 이름으로 찾는다. H7 의 리매핑 클래스로더가 이 경로(버전 문자열 → 클래스 이름)를 다뤄야 한다.
- **Mojang 계열 라이브러리**: `com.mojang.authlib.GameProfile`·`Property`(3 jar), `com.mojang.serialization.Codec`·`JsonOps`(2 jar)처럼 NMS 가 아니라 서버가 싣고 있는 Mojang 라이브러리를 직접 쓰는 경우가 많다. Furnace 서버에 이 라이브러리가 있는지(없으면 B 에 포함)가 선행 확인 항목이다.
- **CommandAPI** 는 Brigadier(B) → 그 뒤 NMS 순으로 막힌다. NMS 대응 전에는 로드조차 못 하므로 H5~H7 의 실제 시험 대상으로 가장 적합하다.

## 확인한 것: `DamageCause.CAMPFIRE`

H1 이 기억 기준으로 넣은 `DamageCause.CAMPFIRE`(와 `KILL`·`WORLD_BORDER`)가 실제 API 에 있는지를 확인했다. GitHub 코드 검색 API(`api.github.com/search/code`, `text_matches` 조각)로 PaperMC/Paper 의 `paper-api/.../EntityDamageEvent.java` 를 봤다: `HOT_FLOOR`, **`CAMPFIRE`**(`@Deprecated(since = "26.2")`, 설명 "Damage caused when an entity steps on Material#CAMPFIRE or Material#SOUL_CAMPFIRE. Damage: 1 or 2 (for soul fire)"), `CRAMMING` 순으로 선언돼 있다. `KILL`·`WORLD_BORDER`·`SONIC_BOOM`·`FREEZE`·`DRYOUT`·`FLY_INTO_WALL` 도 같은 파일에 있다. "deprecated since 26.2" 로 보아 그 전부터 있었던 것으로 **추정**한다(1.21.1 존재 자체는 원문을 못 받아 직접 확인하지 못했다). 선언 순서(`HOT_FLOOR`→`CAMPFIRE`→`CRAMMING`)도 지금 열거형과 같다. **확인 못 한 것**: 1.21.1 시점에 캠프파이어 피해가 `CAMPFIRE` 원인으로 매핑됐는지(현재 master 는 `HOT_FLOOR`·`CAMPFIRE` 둘 다 `CONTACT` 로 보낸다, deprecated 때문). 1.21.1 의 매핑은 원문(CraftEventFactory)을 못 받아 확인하지 못했다 — 현재 구현(`campfire`→`CAMPFIRE`)은 deprecated 이전 동작에 대한 기억 기준이다.

## 시험과 다시 돌리는 법

- `RealWorldCompatTest`(`furnace-compat-paper`): 스캐너(상수 풀 읽기·JVM 해석·종류 분류) 단위 시험, **기준표 대비 후퇴 없음**(jar 별 없는 심볼 수가 기준보다 늘면 실패), 실제 플러그인 기동 상태가 기준보다 나빠지지 않음·실패 원인이 로그에 남음, 실패한 실제 플러그인 옆의 다른 플러그인은 켜짐. 좋아지면 시험이 알려 주기만 하고(통과) 기준표를 새로 쓰도록 안내한다.
- 대조표·기준표 다시 만들기: `./gradlew -PskipOracle=true :furnace-compat-paper:compatReport`(문서와 기준표를 쓴다). 새 호환 API 를 넣는 묶음은 이걸 한 번 돌려 두 파일을 같이 커밋한다 — 다만 생성 문서 한 곳을 모든 PR 이 건드리면 병합 충돌이 나므로, **충돌하면 문서를 버리고 병합 뒤 다시 생성**한다(생성 파일이다).
- 플러그인 하나만 기동해 보기: `./gradlew -PskipOracle=true :furnace-compat-paper:liveProbe -Pjar=helper`.
- **저장소에 없는 jar 로 재 보기**(라이선스·크기 때문에 커밋하지 않는 실제 플러그인): `-PextraJars=<폴더 또는 jar>` 를 `compatReport`·`liveProbe` 에 붙인다. 이 경우 저장소 문서·기준표는 건드리지 않고 `furnace-compat-paper/build/compat-h4-extra-report.md` 에 쓴다.

## 한계

- (검토 지적, 후속 후보) 플러그인 자기 클래스를 owner 로 쓴 호출(`MyPlugin.getConfig()` 처럼 javac 가 수신 타입을 owner 로 적는 상속 호출)은 판정에서 빠진다. 지금 13개 jar 에서는 jar 당 0~14개라 순위는 안 바뀌지만, `JavaPlugin` 을 상속한 큰 플러그인은 과소평가된다. 상속 사슬을 따라 API 로 귀속하는 개선이 필요하다.
- 기준표는 jar 별 "없는 심볼 개수"만 기록한다. 한 심볼을 구현하고 다른 심볼을 지우는 경우는 못 잡는다(개수 기준 슬랙).
- 6장(서버 제공 라이브러리)은 Guava·Gson·SnakeYAML·Adventure·Brigadier·log4j·slf4j·fastutil 로 **내가 확인한 목록만** 본다(netty·JOML 등 Paper 가 싣는 다른 라이브러리는 분류하지 않았다).
- 실제 플러그인이 켜지기 시작하면 `LivePluginProbe` 는 네트워크(bStats 전송 등)에 닿을 수 있다. 시험에는 시간 상한(3분)만 있고 네트워크 차단은 없다 — 켜지는 플러그인이 생기면 임시 폴더의 bStats 설정을 끄는 일이 필요하다.

- 인기 플러그인(Vault·PlaceholderAPI·EssentialsX·LuckPerms·WorldEdit 등)을 직접 못 받아 **측정 대상이 Central 에 있는 플러그인과 라이브러리로 한정**됐다. 다음 표본은 사용자가 jar 를 올려 주면 같은 도구로 즉시 잰다.
- 정적 대조는 요구 상한이다(안 타는 코드 경로까지 센다). 반대로 리플렉션·`Class.forName`·`MethodHandle` 로 가려진 접근은 못 본다(특히 NMS).
- 이 호환 계층은 Bukkit 원문 없이 쓴 clean-room 이라 여기서 "있음"은 이름·서명이 맞다는 뜻이지 동작이 같다는 뜻이 아니다. 동작 동등성은 해당 묶음(A~H)이 각자 시험으로 확인한다.
