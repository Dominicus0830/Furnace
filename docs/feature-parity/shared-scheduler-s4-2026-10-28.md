## 동작
- 켜면 `FurnaceMain` 이 `SharedScheduler.startShared(region-threads, "furnace-region-")` 하나를 만들고 세 차원 월드가 공유한다. `region-threads` = 서버 전체 워커 수(이름·기본값 유지).
- 종료 훅 순서: 월드들 `regionizer::close`(자기 큐 분리) → 공유 풀 `close` → fallback → global.
- 끄면 지금과 같은 int 생성자 경로. 차원 하나뿐인 풀에서는 선택기가 순수 EDF 분기를 타고 `maxRunning = MAX` 라 S3 와 같은 동작이다.
- 선택기: 키 `(capped 2 / starved 0 / 그 외 1, headDue)` 사전식 최소, 같은 클래스에서 마감 차 ≤ 1µs 면 rr 로 시작 위치를 돌린다. `maxRunning` = 다른 차원에 때가 된 머리가 있으면 `perDimCap = T−1`, 없으면 MAX(N3). 상한은 `tryTake` 가 잠금 안에서 다시 확인한다.
- 스레드 이름은 공유 모드에서 `furnace-region-N`. 소유권(`Region.isOwnerThread`, `Owned`)·sprint/freeze 코드는 바꾸지 않았다.

## 설계서와 다른 점
- 기본값 false(설계서는 true) — 사용자 결정.
- 굶음 판정을 풀 상수(2·초기 tick) 대신 차원별 `starveTicks × rz.tickNanos()` 로 했다(`/tick rate` 를 따라간다). `furnace.sched.starveTicks`(기본 2), `furnace.sched.dimCap`(기본 T−1) 은 프로퍼티로 남겼다.
- `tryTake(now)` 단일 인자(상한 없음) 오버로드를 남겼다.
- 설계서의 개별 시험 `DimensionTravelSharedPoolTest`·`SplitDuringOtherDimTest` 대신, 기존 시험을 시험 전용 스위치로 공유 풀에서 다시 돌린다(아래).
- 과부하 벤치(`runOv`) 의 "shared" 는 아직 예전의 "한 월드 근사" 그대로다. 실제 공유 풀로 바꾼 것은 `dimensionsTickJitter` 뿐.
- 계측 추가(설계서 §7.1 보다 많음): `timeouts`(PARK 만료 복귀), `missedWakeups`(만료로 깼는데 until 보다 1ms 넘게 이른, 이미 지난 머리가 있었다 = 깨우기 유실 의심), `takeMisses`(tryTake null).
- `ConfigLoader` 의 `> 2·C` 경고, 릴리스 노트는 만들지 않았다(기본 꺼짐이라 의미 변경이 아직 운영에 닿지 않는다).

## 조사 1 — 최대값 튐(51.96ms / 57.46ms)
- 의심: PARK_MAX(50ms) 만료로 깬 깨우기 유실.
- 코드 경로 점검: `schedule`→`publishHead`→앞당겨졌으면 `wake`; `tryTake` 끝 `wake(새 머리)`; 상한으로 `tryTake` 가 null 이면 `publishHead`(값 불변) 뒤 워커가 **자지 않고** 곧바로 다시 고른다. capped 판정은 "다른 차원에 때가 된 머리가 있을 때"만이라, 한가한 워커가 할 일이 있는데 자는 경로는 없다(그 차원이 capped 면 다른 때가 된 차원을 고르고, 없으면 capped 가 풀린다). 자기 직전 ②는 모든 차원의 머리 최솟값을 다시 본다.
- 계측: 4 회 측정(아래 표 포함 40 회 이상 공유 실행)에서 공유 풀 `missed` **항상 0**. 차원별 풀(현행)은 부하 5ms 에서 `missed` 가 0~26 나온다(워커 24 개가 4 코어를 다툴 때 OS 깨움 지연으로 보인다 — 원인 미확인).
- 튐은 **두 모드 모두** 비슷한 빈도로 한 회차씩 난다(현행 max 47.6·41.0·38.7·33.5ms, 공유 59.5·55.6·41.4ms). 공유 쪽 튐 회차에도 `missed=0` 이라 만료 경로의 깨우기 유실은 아니다. 공유 머신(동시에 gradle 10여 개)·GC 로 추정하지만 **확인하지 못했다**(GC 로그·JFR 미수집). 깨운 뒤 unpark 가 늦게 도착하는 경우는 이 계측이 잡지 못한다.
- 결정적 재현 시험: 유실 상황을 찾지 못해 새로 만들지 않았다. 기존 N1·N2 훅 시험(`SharedSchedulerTest`)은 그대로 통과.

## 조사 2 — 부하 5ms 에서 CPU +11%/+25%
- 틱 수(`regionTicks`)는 두 모드가 같다(3차원 1212, 6차원 2424).
- 원인: 벤치 부하가 **벽시계 바쁜 대기**였다. 이상적인 부하 CPU = region 수 × 200 × 5ms = 6000ms(3차원) / 12000ms(6차원). 현행은 5420 / 9440ms 로 **이상값보다 적다** — 스레드 12·24 개가 4 코어를 다투다 바쁜 대기 중에 선점되어 일을 덜 하고 그만큼 늦는다(현행 p95 ≈ 5ms 와 맞물림). 공유는 6000 / 11880ms 로 거의 이상값.
- 확인: 부하를 스레드 CPU 시간으로 재게 바꾸면(`cpuLoad=true`, 같은 일량) 공유 CPU 가 **같거나 낮다**(3차원 6290→6180, 6차원 12450→12230). 스케줄러 자체 비용(유휴 CPU)도 공유가 낮다(앞 측정: 6차원 유휴 270→150ms).
- 개선: `select()` 가 매번 `dims.toArray()` 로 할당하던 것을 등록·해제 때만 바뀌는 배열로 바꿨다. 효과는 측정 오차 안.

### 해석
- 중앙값 기준 p95·p99·max·깨어남은 공유가 모든 시나리오에서 같거나 낫다. 같은 일량 CPU 는 공유가 같거나 낮다.
- 남는 것은 **한 회차씩 나는 30~60ms 튐**으로, 두 모드 모두에 있고 공유 쪽 깨우기 유실 계측은 0 이다. 원인(GC·머신 경합 추정)을 확인하지 못했다.
- 기본값 전환 여부는 사용자 판단으로 남긴다(이 문서는 결과만 기록).

## 남은 위험
- 튐 원인 미확인(GC 로그·JFR 로 확인 필요). unpark 지연은 `missed` 계측이 못 잡는다.
- `perDimCap` 은 다른 차원이 때가 됐을 때만 걸리고 워커를 예약하지 않는다 — 무거운 차원이 마지막 워커로 긴 틱을 시작하면 가벼운 차원은 최대 Tmax 늦을 수 있다(설계 §4.3 범위).
- 공유 모드의 sprint held 틱 10kHz 재예약(§4.4)·과부하 시나리오(§9.2-B/C/D)는 실제 공유 풀로 측정하지 않았다(`runOv` 는 근사).
- 시험 전용 스위치로 돈 기존 시험이 실제 공유 풀을 탔는지 직접 세지 않았다.
