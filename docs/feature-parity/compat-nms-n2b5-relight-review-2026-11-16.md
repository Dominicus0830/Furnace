## 2. 관점별 검토

### (1) 4.3 붙잡기 정확성 — 논증은 맞다, 경계 조건 4개가 빠져 있다

확인한 것:
- Furnace `blockChanged` 는 `sky.updateSource`(원천 높이 배열만 고침, 빛 값은 안 씀) + 두 엔진 `checkBlock`. `SkyLightEngine.checkNode` 는 바닐라처럼
  `updateSourcesInColumn` 으로 "원천 아래 15 지우기/원천 위 15 채우기"를 **검사 때** 한다. 그래서 "원천은 B1, 빛은 B0, B0→B1 칸마다 검사 대기" 는
  바닐라 `LevelChunk.setBlockState`(ChunkSkyLightSources 즉시) 직후·`runLightUpdates` 전 상태와 같은 꼴이다. ✔
- 바닐라도 `ThreadedLevelLightEngine` 이 작업을 묶음(최대 1000)으로 나눠 돌리므로 "블록은 이미 B1, 검사 일부만 처리" 상태는 바닐라에서도 늘 생긴다 —
  3×3 밖(거리 2) 검사를 계산 중에 먼저 처리하는 것은 그 범위 안이다. ✔
- 거리 2 이상에서 온 증가·감소는 C 에 닿지 못한다(수평 17칸 ≥, 하늘 원천의 무손실 하강은 원천 열 안에서만). C 의 살아 있는 빛을 바꾸는 붙잡히지 않은 길은
  새 이웃 켜기(⑦이 처리)와 T-064 묶음 게시(⑥ awaitLightIdle 뒤라 덮임)뿐이다. ✔
- 얼리기 전에 쌓여 있던(이번 틱 아직 안 돈) 검사도 붙잡히는데, 이미 맞는 빛 위에서 `checkNode` 를 다시 돌리는 것은 감소→재증가로 같은 값에 돌아온다(무해, 일만 더). ✔
- 가짜 광원은 일꾼이 얼리지 않은 값을 섞어 읽을 수 있지만, 그 칸의 `emissionChanged` 검사가 붙잡혀 있다가 감소→재증가로 고친다. ✔
- ⑧ `computeSources` 는 "처음 올릴 때" 규칙(hasOnlyAir 특이점)이고 일꾼 계산도 같은 규칙이라 C 안에서 빛·원천이 서로 맞는다. 이후 바뀜은 `updateSource` 규칙 — 새로 올린 청크와 같다. ✔

빠진 것 → **R2·R3·R4**(아래). 교착은 찾지 못했다: 준비·설치는 일꾼을 기다리지 않고, 일꾼은 잠금이 없고, 설치의 `awaitLightIdle` 은 지금도 있는 자기 묶음 기다리기다.
남는 교착 위험은 플러그인 콜백을 region 스레드에서 부르는 것뿐이다(R5).

### (2) 4.4 합치기·나누기 — 방향은 맞다, 지금 코드의 `hasWork()` 가드에 걸린다

- 붙잡기 수를 `World` 에 두고 통을 검사처럼 옮기는 것은 맞다. 기다리지 않는 것도 맞다.
- 그런데 지금 `ChunkLevel.absorb`(843행)·`splitTo`(901행)는 `if (lightEngine.hasWork()) moveChecksTo(...)` 로 감싸져 있고, `lightTickEnd` 도 `hasWork()` 로 넘기기를 정한다 → **R2**.
- 녹이기를 다른 스레드가 하는 것은 원자 수로 풀린다. 단 `ownSection` 의 "0 이면 그 자리 쓰기" 판정은 **acquire 읽기**여야 한다(일꾼의 읽기 → 설치 감소(release) → 주인의 0 읽기로
  happens-before 가 이어져야 그 자리 쓰기가 일꾼 읽기와 겹치지 않는다). 문서에 "감소는 getAndAdd, 판정은 getAcquire" 를 적을 것(R2 에 포함).

### (5) 성능 — 모델은 타당, 빠진 비용 셋(S5)

- 일꾼 풀 `clamp(코어/4,1,4)`: `availableProcessors` 는 SMT 포함(데스크탑 16 → 4, 4코어 컨테이너 → 1). 1024청크 × 1.27 × 4 ms ≈ 5.2 s CPU → 1스레드 5 s, 4스레드 1.3 s. 생성 풀(코어−1)과 겹쳐 코어를 넘기지만 M3 로 볼 일. 수용.
- **빠진 것 ①** 설치 패킷: 하늘 많은 청크의 전 섹션 LightUpdate 는 꽉 찬 층이 많아 청크당 수십 KB(15 로 찬 층도 2 KB 배열로 나감). 1024청크면 시청자당 수십 MB이고 FAWE 가 곧이어 청크를 통째로 다시 보낸다.
  Paper 도 같으니 관측상 필요하지만, M2(타일당 ≤ 2 ms)에 패킷 만들기를 넣으면 넘을 가능성이 크다 → M2 를 "끼우기·원천"과 "패킷 만들기·보내기"로 나눠 재고, M3 에 보낸 바이트를 넣을 것.
- **빠진 것 ②** 붙잡기 판정 비용: 검사마다 `ConcurrentHashMap<Long,…>` 조회(박싱)는 relight 중 레드스톤 램프 같은 검사 많은 장면(M4 `lamps400Bench`)에서 눈에 띌 수 있다. 붙잡기 집합이 바뀔 때만 올리는 세대 수 + region 쪽 원시 long 집합 사본을 권한다.
- **빠진 것 ③** 메모리: 타일마다 새 ChunkLight 10×10(압축 전 최대 ~10 MB), 동시 타일 일꾼×2 → 수십 MB 일시. 기록만.
- 얼리기 시간이 T-064(한 틱)보다 훨씬 길다(수백 ms). `sections()` 원소에 그 자리에서 쓰는 길(지금 본 것은 바이옴 읽기뿐이라 문제 없음)과 `-ea` 단언을 relight 얼림 상태로도 돌릴 것(시험 항목, S9).

## 3. 필수 수정 (R)

**R1. 저장·종료의 stale 표시 범위.** 지금 안은 "그 청크에 붙잡힌 검사가 있으면 표시"다. 붙잡힌 검사는 **이웃 청크**의 빛도 바꾼다(15칸).
반례: 계산 중 N 의 경계 옆 횃불을 부숨(검사 붙잡힘) → 이웃 K(N 옆, 붙잡기 밖일 수 있음)는 아직 횃불 빛을 들고 있음 → K 저장(표시 없음) → 종료(작업 버림) →
다음 기동 때 N 은 표시로 다시 계산되지만 K 는 저장 빛을 믿어(T-012) **유령 빛이 영구로 남는다**. (K 가 계산 중 내려가면 풀린 감소가 `decreaseBlocked` 로 K 를 표시하므로 그 경우는 이미 덮인다 — 문제는 K 가 로드된 채 저장·종료되는 경우.)
고칠 것: (a) `settleLightForSave` 는 붙잡힌 검사가 **그 청크 체비셰프 1 안**에 있으면 표시(지금 T-064 의 `LIGHT_BATCH_REACH` 판정과 같은 꼴). 지금 메서드의 앞쪽 조기 반환(`lightBatch==null && !hasWork`, `!asyncLight()`) 보다 먼저 볼 것.
(b) 종료·월드 내리기는 "작업 버림" 대신 **붙잡기를 모두 풀고 붙잡힌 검사를 끝까지 계산한 뒤 저장**, 끼우지 못한 relight 대상 C 는 `lightStale` 표시(들여온 블록 + 옛 빛이 남으므로). 이러면 종료 경로는 정확하고 표시가 최소가 된다.

**R2. 붙잡힌 일과 `hasWork()`·풀림 알림.** (a) `LevelLight.hasWork()` 를 둘로 나눌 것: 옮기기·종료용 "통 포함 전부"와 틱 넘기기용 "지금 돌릴 수 있는 일". 지금 가드 그대로면
합치기·나누기에서 통만 있는 쪽의 붙잡힌 검사가 **사라지거나**(absorb 843행, splitTo 901행), 반대로 통만 있는데 매 틱 빈 runUpdates/묶음을 넘긴다.
(b) 붙잡기 수는 다른 region 의 설치가 0 으로 내린다 — 통을 든 region 이 이를 알 수 있게 세계 단위 "풀림 세대" volatile 수를 두고, 세대가 바뀐 틱에만 통을 다시 훑는다(0 비용 경로 유지).
(c) 통은 순서 유지 + 중복 제거 집합(`LongLinkedSet`)으로. (d) 4.4 의 원자 수: 감소 getAndAdd(volatile), `ownSection` 판정 getAcquire.

**R3. ⑦ 멤버십은 키가 아니라 이번 로드 정체성으로.** 계산 중 둘레 X 가 내려갔다가 **다시 올라오면** 키는 U 에 그대로라 ⑦ 이 못 잡는다. 그런데 새 X 의 빛 켜기(`lightChunk`/`attachPrecomputed`)가
C 로 민 빛은 검사가 아니라 전파라 끼우기에 덮이고, U 의 X(옛 블록)로 계산한 C 값이 남는다. 준비 때 3×3 각 칸의 컬럼 정체성(또는 `World` 의 로드 표시 객체, 328행)을 기억하고 ⑦ 에서 비교할 것. 재생성 명령으로 컬럼이 바뀌는 경우도 같은 규칙으로 덮인다.

**R4. 붙잡기 시간의 상한(기아).** 같은 3×3 을 덮는 relight 가 앞 것이 설치되기 전에 계속 준비되면(플러그인이 매 틱 같은 청크를 relight, 또는 겹치는 타일이 꼬리를 물면) 수가 0 으로 내려가지 않아
그 근처 빛 갱신(플레이어 횃불)이 **끝없이** 밀린다. Paper 는 무한 반경 작업이 FIFO 라 사이사이 밀린 빛 작업이 돈다. 고칠 것 — 둘 중 하나를 문서에 정할 것:
(a) 검사가 "자기가 들어올 때 이미 걸려 있던 붙잡기"에만 붙잡히게(붙잡기마다 세대 번호; 얼리기 **전**에 들어온 검사는 그 relight 결과를 깨지 않는다 — B0 에 이미 들어 있다), 또는
(b) 겹치는 3×3 의 준비는 앞 것의 설치 뒤로 미루고, 설치로 0 이 된 청크의 통은 다음 준비 전에 그 region 이 계산한다. 시험: 매 틱 같은 청크 relight + 옆에 횃불 → 정해진 틱 안에 빛 반영.

**R5. 콜백 스레드·순서.** Paper 는 청크 콜백을 빛 일꾼 **한 스레드에서 순서대로** 부르고 그 뒤 onComplete 를 부른다. 설계는 여러 region 스레드에서 동시에 부른다.
FAWE 는 괜찮지만(빈 람다, 작업 걸기만), 일반 Paper 플러그인은 (i) 콜백 안에서 주 스레드 미래를 `join` 하거나(region 스레드면 교착·틱 정지), (ii) 스레드 안전하지 않은 모음에 담는다(동시 호출 경쟁).
"웬만한 Paper 플러그인 지원" 원칙에 따라 콜백은 요청마다 **한 줄(직렬) 실행기**(relight 풀 위)에서 설치 순서대로 부르고, done 은 그 줄의 마지막에 둘 것. region 스레드는 설치만 하고 콜백을 넘긴다.

**R6. 검증 보강(7장).**
(a) **멱등 + 동시 바뀜 퍼즈 시험**: 이미 맞는 빛의 5×5 에서 가운데를 relight 하고, 시험 이음매로 일꾼을 잡은 동안 C·N·거리 2 에 무작위로 블록·광원을 바꾼다(시드 고정, 여러 판) →
끝난 뒤 **5×5 전체** = 같은 블록으로 새로 켠 값. relight 대상이 원래 맞았으므로 Paper 의 "둘레 그대로" 효과와 섞이지 않고 붙잡기 논리만 정확히 잰다.
(b) **변이 확인**: 붙잡기를 끄면(또는 판정을 C 만으로 좁히면) (a) 가 실패해야 한다(4.3 예).
(c) RelightOracleTest 의 참값은 3×3 이 아니라 **5×5 이상**을 새로 켠 값과 비교 — 4.2 의 "둘레 1칸이면 충분"을 가정이 아니라 시험으로 확인.
(d) R1 시험: 계산 중 이웃 K 저장 → 종료 → 다시 올려 K 값 확인. R3 시험: 계산 중 둘레 내렸다 올리기. R4 시험(위).
(e) M5 실측의 `anvil-diff` 범위에 편집 41청크와 함께 **둘레 한 줄(편집 안 한 청크)**도 넣어, Paper 와 같은 "둘레 그대로" 꼴인지 본다.

## 4. 권장 (S, 구현 때 반영하면 좋음)

- **S2** P1 순서: 핀 먼저 → 로드·빛 확인(Paper 와 같이). 빛이 아직 안 켜진 청크는 **받을 때 빼서** 반환 수에 넣지 않는 쪽이 Paper 반환값과 같다(지금 안은 받고 "끝난 것"으로 셈 — 4.8). 차이를 둘 거면 5장에 적을 것.
- **S3** 9장에 H·I 안 추가(위 2장 (4)).
- **S4** U 정의를 "타일 안 요청 청크 각각의 3×3 합집합 ∩ (이 region 소유·빛 있음)"으로 명확히(8×8 칸 전체가 아님). +27%/+100% 계산과 맞추기.
- **S5** M2 를 끼우기·원천 / 패킷으로 나누고 M3 에 보낸 바이트·패킷 만들기 시간 추가. 패킷 만들기를 region 밖으로 뺄 수 있는지 구현 때 판단.
- **S6** 붙잡기 판정을 세대 수 + 원시 long 집합 사본으로(박싱 없는 조회).
- **S7** Furnace 만의 차이 하나: Paper 는 relight 중 새 청크 빛 켜기도 멈추지만 Furnace 는 계속한다. 그래서 계산 중 3×3 안에서 켜진 새 이웃 X 는 **옛 C 의 빛**을 받아 든다(⑦ 이 C 는 다시 하지만 X 의 유령 빛은 남음).
  드물고 Paper 의 "둘레 그대로"와 같은 종류라 5장에 적고 넘어가도 된다. 고친다면 설치 뒤 C–X 경계 칸 검사 걸기(Starlight `checkChunkEdges` 꼴)를 T-205 후보로.
- **S8** 둘레 유령 빛·모자람(Paper 동작)을 고치는 경계 검사는 Paper 와 달라지므로 기본 끔 옵션 후보로만 남길 것.
- **S9** 시험 `AsyncLightTest` 류 단언(-ea)을 relight 얼림이 걸린 상태로도 한 번 돌릴 것.
