# 여럿일 때 청크 전송 측정 (M12, 2026-11-07)

대상: "플레이어 2명부터 청크 전송이 1명일 때보다 느리다"(work-packages M12). 10-27 의 동시 직렬화 중복(perf-c2)은 이미 고쳐져 있었다.

## 방법
- 4코어 컨테이너, `-Xmx3G`, 시드 12345 노이즈 월드, 시야 10(441청크), 클라이언트 응답 64청크/틱.
- 클라이언트: `tools/bot-test/chunkrate/multi.js` (minecraft-protocol 직접). map_chunk 는 x,z 만 읽는다 — 본문을 해석하면 4명이 한 node 프로세스에서 CPU 를 다 써 클라이언트가 먼저 막혔다(처음 측정의 함정).
- 미리 만든 땅을 스냅샷해 두고 매 실행마다 되돌린 뒤 서버를 새로 켠다(디스크에서 읽기). 모두 스폰에 접속 → 콘솔 `/tp` 로 동시에 보내고, 각자 새 시야 정사각형을 다 받을 때까지 ms.
  - 떨어진 곳: 2000칸 간격(서로 다른 region). 가까운 곳: 352칸(22청크) 간격 — 시야가 맞닿는다. 같은 곳: 모두 한 자리.
- CPU 분포는 JFR(`settings=profile`) 실행 표본.

## 원인과 수정
### ① 종료 때 생성 청크 유실 (가장 큰 체감)
"가까운 곳" 을 처음 재었을 때 2명 10.8~12.4초, 4명 17.8~21초(1명 1.47초)였다. 미리 만들어 둔 줄 알았던 땅이 디스크에 없어서 다시 생성하고 있었다.
- 4명이 새 땅 1,764청크를 만든 뒤 `/stop` → 디스크에 남은 청크 **1,019개(58%)**. 로그는 "저장 실패 0건".
- `Region.saveDirtyChunks` 는 IO 레인이 밀리면(`ioBackedUp`, 레인당 256) 남은 청크를 자동 저장 큐(다음 틱)로 넘긴다. 종료 단계 `flushAll` 은 한 번뿐이고 그 뒤 틱이 없어 그대로 사라졌다. 여럿이 새 땅을 돌수록 dirty 가 많아 잘 일어난다 — 재시작 뒤 "이미 가 본 땅" 이 처음처럼 느린 원인.
- 수정: `World.flushAllDrained` — 미룬 청크가 0 이 될 때까지 `flushAll` → `ioBarrier` 를 되풀이(역압은 그대로라 스냅샷이 한꺼번에 쌓이지 않는다). 종료(60초 마감, 넘기면 남은 수를 오류로 남김)와 `save-all` 이 쓴다. 미룬 수만 보므로 틱이 도는 동안의 save-all 이 새로 dirty 가 되는 청크 때문에 끝없이 돌지 않는다.
- 후: 같은 실행 뒤 **1,764/1,764** 저장. 시험 `GeneratedChunkSaveTest.flushAllDrained_savesEverythingDespiteBacklog`(레인 막힘 → flushAll 한 번은 대부분 미룸 → drained 는 모두 디스크에).

### ② 디스크 청크의 빛 계산 (CPU)
떨어진 4명일 때 CPU 가 꽉 찼다(vmstat 사용 93~97%). JFR: 빛 계산이 표본의 약 40%(생성 풀 `precomputeLight`), 그중 절반이 블록빛 원천 찾기 — 청크마다 98,304칸을 하나씩 읽어 발광 여부를 봤다. 하늘빛 원천 높이 찾기(맨 위에서 지형까지 칸마다)와 15 채우기가 그다음.
- 바닐라는 저장된 빛을 쓴다. Furnace 는 시야 밖 이웃이 내려간 동안 바뀌면 저장된 빛이 낡을 수 있어(바닐라는 이웃 고리를 늘 올려 둔다) 다시 계산을 유지하고, 계산만 빠르게 했다:
  - 블록빛: 팔레트에 발광 상태가 없는 구역은 건너뜀(바닐라 `findBlockLightSources` 의 `maybeHas` 와 같은 판단).
  - 하늘빛 원천: 한 상태로만 찬 구역은 맨 위·안쪽이 막지 않으면 통째로 지남.
  - 하늘빛 15 채우기: 모든 열의 원천보다 위인 구역은 `Arrays.fill`. 대기열에 넣는 칸과 순서는 그대로.
- 결과 동일성: 실제 월드 청크 5,776개를 예전·새 코드로 계산해 빛 배열·원천 높이 SHA-1 이 모두 같다. 시험 `LightFastPathTest`(무작위 지형 300개 + 이웃 있는 3×3 차례 켜기 20회, 힌트 유무 비교).
- 청크당 1.09ms → 0.35ms. 떨어진 4명 2.2~2.7 → 1.6~2.3초.

## 남은 것
- 4명 동시 새 시야가 1명보다 1.3배 안팎 느린 것은 CPU 몫(4코어, 봇 클라이언트도 같은 머신). 다음 후보: 섹션 직렬화(`PaletteStorage.unpack` + `Palette.write` 다시 팔레트화, N-07 와이어 바이트 조건), 디스크 디코드(`loadIndexed`), POI 복원.
- 새 땅은 월드젠 CPU 가 병목(furnace-chunk-send-rate). 여럿이 따로 새 땅을 돌면 생성량이 사람 수만큼 늘어 느린 것은 바닐라도 같다(공평하게 나뉘는 것은 확인 — 4명 각 28.1초로 같음).
- 1명 속도(1.49초)를 정하는 미리 불러오기 상한 16은 이번에 건드리지 않았다(생성 중 가까운 청크 우선을 지키려는 상한).
