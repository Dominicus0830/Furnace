# C-5 성능 측정 (2026-10-28): 청크 본문 스냅샷 복사, 스폰 거리 판정 할당, 엔티티·POI 저장 잠금

앞선 기록: `perf-c2-2026-10-27.md` 5.2, `perf-c4-2026-10-28.md` "미채택(제안)", `perf-c1-2026-10-27.md` F-01 "별도 과제".
원칙: 공유 머신이라 벽시계 대신 **스레드 CPU ns, 할당 바이트, 횟수**(ThreadMXBean 차분, 잠금 차단 횟수와 시간)를 근거로 삼는다. 3회 반복 범위로 적는다.
기준선은 수정 전 커밋(`77542d14`)을 스크래치 디렉터리에 풀어 같은 벤치로 쟀다(`PlayerWalkTickBench`, 방법은 C-4 와 같다).

## 1. 청크 본문 스냅샷 복사

### 기준선 JFR (N=32, region 스레드 샘플 무게 합 4089MB)
| # | 비율 | 할당 | 위치 |
|---|---|---|---|
| 1 | 54.3% | `int[]` | `PaletteStorage.unpack` ← `ChunkSection.blocks` ← `ChunkSnapshot.of` |
| 2·3 | 11.3%·11.0% | `byte[]` | `ChunkSnapshot.copyLight:115/116` (하늘빛·블록빛) |
| 6·7 | 2.3%·2.0% | `byte[]` | `Object.clone` ← `copyLight` |

스냅샷 복사가 region 스레드 할당의 약 81% 다(C-4 의 52% 보다 크다. C-4 이후 자연 스폰 목록 할당이 빠져 비율이 올랐다).

### 설계 비교
| 안 | region 스레드 복사 | 와이어 바이트 | 편집 경쟁(N-05) | 위험 |
|---|---|---|---|---|
| A. 지금(즉시 풀기 + 빛 복제) | 섹션마다 int[4096] 16KB, 빛 52층 × 2KB | 기준 | 스냅샷이 독립 사본 | 없음(기준) |
| **B. 팔레트 원본 사본 + 균일 빛 층 공유** | 팔레트(int[] 수십 개) + BitStorage long[](4비트면 2KB, 단일값이면 0). 빛 층이 모두 0 또는 모두 15 면 복사 없이 공유 상수 | `Palette.write` 가 받는 int[] 는 같은 값(풀기만 풀 스레드로 미룸). 빛 층 내용 같음 | 사본은 원본과 배열을 나누지 않아 스냅샷 뒤 편집이 새지 않음 | 공유 빛 상수를 누가 고치면 오염(쓰는 곳 없음, 읽기 전용 계약을 주석으로) |

B 를 채택했다. 출력 동일성 시험을 만들 수 있고(같은 int[] 가 같은 직렬화기로 들어간다), 쓰기 경로를 하나도 건드리지 않는다.
C·D 는 모든 쓰기 경로에 무효화를 걸어야 해서, 하나라도 놓치면 N-05 가 깨진다. E 는 region CPU 가 는다.

### 구현 (B)
- `PaletteStorage.readCopy()`: 팔레트와 BitStorage 만 복사하고 역맵(lookupKeys/Vals)은 복사하지 않는다.
- `ChunkSnapshot.Section`: record 에서 final class 로 바꿨다. region 스레드에서는 `readCopy` 만 하고, `blocks()`·`biomes()` 를 처음 부르는 스레드(본문 직렬화 풀, 저장 코덱)가 풀어서 volatile 필드에 기억한다.
  scratch 가 열린 섹션은 예전처럼 즉시 `clone` 한다. 예전 생성자 `(short, int[], int[])` 는 그대로 남겼다.
- `ChunkSnapshot.copyLight`: 층이 모두 0 이거나 모두 0xFF 면 공유 상수 `ZERO_LAYER`·`FULL_LAYER` 를 가리키고, 아니면 `clone` 한다.
  스냅샷 빛 배열을 읽는 곳은 `ChunkSerializer`(isZero, writeBytes)와 `AnvilChunkCodec.putLight`(NBT 에 넣고 바로 기록)뿐이고, 둘 다 고치지 않는다.
- 편집 경쟁: 스냅샷은 여전히 같은 주인 스레드 구간에서 뜨고, `modCount` 도 같은 구간에서 잡는다(`World.serializedChunkBody` 는 고치지 않았다).
  사본은 원본과 배열을 나누지 않으므로, 스냅샷 뒤에 편집이 끼어도 풀린 값은 요청 시점 값이다. `ChunkBodyCacheRaceTest` 는 고치지 않고 통과한다.

### 출력 동일성 시험 `ChunkSnapshotCompactCopyTest`
- `randomChunks_sameBodyBytesAsLegacySnapshot`: 수정 전 `of` 를 시험 안에 그대로 두었다(`legacyOf`). 무작위 청크 2500개를 쓴다.
  섹션은 단일값, 간접 4비트, 간접 상한 근처, 직접(257종 이상) 분포에 공기 섞임, 바이옴 분포, scratch 가 열린 섹션을 섞었다.
  빛은 없음, 모두 0, 모두 15, 거의 균일, 무작위 층을 섞었다. 하늘빛 차원과 하늘빛 없는 차원 모두에서 본문 바이트가 같다. 섹션별 blocks·biomes·nonAirCount 도 같다.
- `editsAfterSnapshot_doNotLeakIntoLazyUnpack`: 스냅샷을 뜬 뒤 풀기 전에 블록 200칸(팔레트 성장 포함), 바이옴, scratch, 빛 층을 고친다. 그래도 스냅샷 바이트가 편집 전 기준과 같다(600청크).

## 2. `sharedSpawnPos` 배열과 스폰 시도 `Pos` (미채택)

코드로 확인한 것:
- `isRightDistanceToPlayerAndSpawnPoint` 는 스폰 지점 세 성분만 읽는다. 배열을 고치지 않고, 밖으로 내보내지도 않는다. RNG 호출도 없다.
  시험한 변경: `LevelServices` 에 `sharedSpawnX/Y/Z()` 를 더한다. 기본 구현은 `sharedSpawnPos()[i]` 이고, `ServerCore` 는 `levelData` 필드를 그대로 돌려준다.
  예전에도 세 필드를 따로 읽어 배열을 만들었으므로, 다른 스레드가 스폰 지점을 바꾸는 동안 읽는 경우(찢어짐)의 의미도 같다.
- `spawnCategoryForPosition` 루프의 `new Pos(x, y, z)` 는 거리 판정 앞에서 만들어졌다. 판정은 좌표와 `withinBorder(x, z)` 만 쓰므로,
  `Pos` 를 판정을 통과한 뒤에 만들도록 옮긴다. `Pos` 는 값 record 라서 만드는 시점이 결과에 영향을 주지 않는다.
  RNG 호출(`nextInt(6)` 네 번, 그다음 `getNearestPlayer`)의 순서와 수는 그대로다.
- 그대로 둔 것: `spawnCategoryForChunk:165` 의 시작 `Pos` 는 `getBlockState`, `isRedstoneConductor` 등으로 넘어가 바로 쓰인다(지울 수 없다).
  통과한 칸의 `Pos` 는 `getRandomSpawnMobAt`, `canSpawn`, `isValidSpawnPositionForType` 등 여러 곳으로 넘어간다. 그 안에서 붙들어 두지 않는다는 보장이 없어 재사용(가변 좌표)하지 않았다.
  `ChunkLevel.blockRandomPos` 의 `Pos` 도 블록 동작으로 넘어가므로 손대지 않았다.
- 시험 중에 쓴 동일성 시험(코드와 함께 되돌림): 수정 전 판정(배열과 Pos)을 복제하고, 무작위 입력 20만 개에서 결과가 같았다.

측정과 판단: **미채택**. 위 변경을 1번 위에 얹은 트리를 1번만 적용한 트리와 같은 걷기 벤치로 비교했다(N=32, 3회).
- 할당 평균: 1번만 321.3~334.1 KB, 1+2번 369.2~372.4 KB. 2번이 할당을 줄였다는 근거가 없다(JVM 실행 사이 차이가 더 크다).
- JFR(N=32, 1회): 루프 `Pos`(`spawnCategoryForPosition`) 무게가 기준선 131.3MB 에서 114.3MB 로 −13% 였다. 이 시나리오에서는 대부분의 시도가 거리 판정을 통과해서, `Pos` 를 판정 뒤로 미뤄도 줄어드는 양이 작다.
  기준선 JFR 상위 10에 `sharedSpawnPos` 의 `int[]` 는 없었다(C-4 의 2.4% 는 그때 다른 할당이 더 컸던 상태의 비율이다. 탈출 분석으로 사라지는 경우도 있는 것으로 보인다. 이것은 가정이다).
- 이득이 반복 범위 밖이라는 근거가 없어서 코드는 되돌렸다. 바닐라 순서와 RNG 를 지키는 방안 자체(위 두 가지)는 가능하다고 확인했다.
  다음에 스폰 할당이 상위가 되는 시나리오(멀리 흩어진 플레이어, 거리 판정 실패가 많은 경우)가 생기면 다시 본다.
  그때를 위한 동일성 시험 설계: 수정 전 판정을 시험에 복제하고, 무작위 입력(스폰 지점, 국경, 청크, 거리) 수십만 개에서 결과가 같은지 본다.

## 3. 엔티티·POI 저장의 저장소 전체 잠금 (F-01 후속)

코드로 확인한 것:
- 엔티티: `World.loadEntitiesAsync`, `saveEntitiesAsync`, `appendEntitiesAsync` 가 `synchronized (anvil.entityStore())` 를 쥔다. 그 안에서 NBT 인코딩과
  `RegionFileStore.writeChunk`(deflate)를 한다. 레인은 region 파일 단위라서 레인 사이에서는 병렬이어야 하는데, 이 잠금 때문에 IO 풀 스레드(기본 4개)가
  서로 다른 파일의 엔티티 저장을 한 줄로 처리한다. 레인 직렬은 **같은 파일**만 줄 세우므로, 다른 파일끼리의 직렬화는 레인이 보장하는 것이 아니라 이 잠금이 만드는 비용이다.
- POI: `AnvilWorldSource.writePoi` 와 `withPoi`(읽기, 레인 없는 `ioExecutor` 에서도 불린다)가 `synchronized (poiStore)` 를 쥔다.
- 이 잠금이 지켜야 하는 것은 같은 청크의 덧붙이기(읽고, 더하고, 쓰기)가 같은 청크의 저장과 엇갈리지 않는 것뿐이다. 다른 청크끼리의 섹터 기록은
  `RegionFileStore` 의 파일 잠금이 지킨다(F-12).
- 변경: 저장소 전체 잠금을 **청크별 줄무늬 잠금**(256개, `AnvilWorldSource.entityLock/poiLock`)으로 바꿨다. 같은 청크는 언제나 같은 잠금이라 덧붙이기의 원자성은 그대로다.
  호출하는 함수와 그 순서, 기록하는 바이트는 바뀌지 않는다.

벤치 `EntityStoreLockBench`: 레인 4개(기본 io-threads)가 각자 다른 region 파일에 엔티티 30개짜리 묶음 512개를 쓴다. 인코딩과 deflate 를 포함한다.
워밍업 1회 뒤 3회. 차단은 ThreadMXBean contention monitoring 의 스레드별 합이다.
| | 차단 횟수 | 차단 시간 | CPU 합 |
|---|---|---|---|
| 저장소 잠금(전) | 17~31 | 214~459 ms | 156.3~199.5 ms |
| 청크별 잠금(후) | 4~6 | 0~17 ms | 142.0~185.4 ms |

CPU 합은 범위가 겹친다(일의 양은 같다). 차단 시간은 범위가 겹치지 않는다. 자동 저장처럼 여러 파일의 엔티티를 한꺼번에 쓸 때,
예전에는 이 시간만큼 IO 레인이 서로를 기다렸다. 채택했다.
- 시험 `EntityChunkLockTest.concurrentAppendsSameChunks_noneLost`: 8스레드가 region 파일 4개에 걸친 청크 6개에 960번 읽고, 더하고, 쓴다. 덧붙인 항목 수가 청크마다 정확하다.

## 남은 위험
- 1: 공유 빛 상수(`ZERO_LAYER`·`FULL_LAYER`)는 읽기 전용 계약이다. 앞으로 스냅샷 빛 배열을 고치는 코드가 생기면 모든 스냅샷이 오염된다.
  저장 경로는 NBT 에 이 배열을 그대로 넣으므로, 저장 NBT 를 고치는 코드가 생겨도 같다.
- 1: 풀기를 미루면서 직렬화 풀 쪽 할당이 청크당 약 390KB 늘었다(region 쪽에서 옮겨 온 것). 풀 GC 압력은 그대로이고, region 스레드만 가벼워졌다.
- 1: `ChunkSnapshot.Section` 은 이제 record 가 아니다(equals/hashCode 가 값 비교가 아니다). 쓰는 곳은 없다.
- 3: 레인 밖 호출(`withPoi` 의 `ioExecutor` 읽기)은 이제 다른 청크의 POI 기록과 병렬로 돈다. 같은 청크끼리는 여전히 배제된다.
