## 설계서와 다른 점
- `runOne` 은 `SharedScheduler` 가 아니라 `Regionizer` 에 두었다(`gameTicks`·`recordTick` 이 private). 순서는 같다.
- `tryTake(now)` 에 `maxRunning` 인자는 없다(S4 의 공정성 몫). 선택기는 순수 EDF(머리 마감 최솟값).
- `tryTake` 끝에서 새 머리로 `wake(headDue)` 를 부른다(설계서에는 `schedule` 만). 예전 `signalAll` 처럼 같은 마감 region 을 다른 자는 워커가 받게 하려는 것 — `wake` 는 "그보다 늦게 깰 워커"만 깨우므로 필요 없을 때는 아무도 깨우지 않는다.
- 공유 풀 생성자(`World`/`Regionizer`)는 패키지 전용으로만 추가(시험용). `FurnaceMain` 연결 없음.
- 바쁜 워커 수 계측 이름은 `activeTicks`(설계서의 `running`).
- 시험 (c) 는 작업 완료 시각 대신 새 region 첫 틱의 큐 지연(계측)으로 잰다. 작업 완료로 재면 "새 region 이 먼저 한 번 돌고 작업은 그 뒤 인박스에 들어가 다음 틱에 돈다"는 기존 경합(S2 이전에도 있음)이 섞였다.

### 해석(정직하게)
- 최악값(max)·p99 는 같거나 좋아졌다. 부하 0 의 p95 는 0.05ms → 0.1ms 로 늘었다(절대값은 틱의 0.2%).
- **"나빠지지 않음"은 확인하지 못했다.** 부하 5ms 의 p95(3차원 2.0→4.8, 6차원 6.0→6.9)와 유휴 CPU(6차원 160→360ms/10초)는 후가 나쁘다. 전 측정의 범위가 넓고(3차원 5ms p95 0.04..4.49) 전·후 측정이 몇 시간 떨어진 다른 부하 상태의 공유 머신에서 이뤄졌으며, `RegionTickBench`(스케줄러와 거의 무관)의 CPU 도 같은 방향으로 45% 늘어서 머신 상태 차이가 섞였을 가능성이 크다. 그러나 S2 의 깨우기 방식(신호 전체 → 워커 하나 unpark + 새 머리 wake)이 유휴 CPU 를 늘렸을 가능성도 배제하지 못했다.
- 위 측정은 아래 교차 측정으로 대체한다.

## 교차 재측정 (같은 세션, 번갈아 5회)
위 1차 측정은 전·후가 몇 시간 떨어져 있어 다시 쟀다. 기준 = **0518ed29**(S1: 77542d14 의 Regionizer 워커 루프 그대로 + 계측 — 깨어남 수를 같은 방식으로 세기 위해), 후 = **6f56dbe2**(S3). 같은 워크트리에서 소스를 번갈아 바꿔 `기준, 후, 기준, 후 …` 순서로 5회씩 돌렸다(`MultiDimensionTickBench.dimensionsTickJitter`, 차원마다 region 2·워커 4, 200틱, 측정 구간 약 10초). 벤치는 이번에 `wakeups`(모든 워커가 기다림에서 돌아온 횟수, `schedStats()`)를 함께 찍게 했다. 값은 `[최소..최대] 중앙값`.

해석:
- **깨어남은 후가 적다**(부하 5ms 에서 약 30% 적고, 유휴에서도 같거나 적다). 유휴 6차원 24워커 기준 약 5000회/10초 = 워커당 약 21회/초로, 설계서 기대치(풀마다 ≤ T×20/초, 50ms 틱이면 워커마다 틱당 1회 남짓)와 맞다. 불필요한 unpark 가 많아서 생기는 비용은 보이지 않는다 — S2 깨우기 방식을 고치지 않았다.
- 유휴 CPU: 3차원은 후가 낮고(2310→1990), 6차원은 후가 조금 높다(350→420, 범위 340..450 와 350..430 이 겹친다). 방향이 일정하지 않고 10초에 수십 ms 차이다.
- 부하 5ms p95 중앙값은 후가 0.5~0.9ms 높지만 범위가 겹치고(3차원 기준 0.07..4.89 / 후 4.20..5.04), p99·max 는 같거나 낮다. 유휴 6차원 p95 는 0.095→0.119ms(+0.024ms).
- 판단: 5회 반복 범위 안에서 **일관되게 나빠진 지표는 없다.** 부하 p95 중앙값이 조금 높은 경향은 남는다(공유 머신 노이즈와 구분할 만큼의 표본이 아니다). S4 합격선(§9.2)을 잴 때 같은 교차 방식으로 다시 본다.
