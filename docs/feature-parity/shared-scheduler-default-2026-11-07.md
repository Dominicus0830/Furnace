# 공유 스케줄러(S4) 기본값 검토 — 기본 켬으로 바꿈 (Q5, 2026-11-07)

도미니코 결정(2026-11-07): "공유 스케줄러 S4 기본값 검토 후 맞다는 방향으로 세팅."
앞 기록: `shared-scheduler-s4-2026-10-28.md`(구현·첫 측정, 그때는 기본 꺼짐). 이 문서는 남은 의문(간헐적 40~60ms 튐)을 다시 재고 기본값을 정한 기록이다.

## 결론

**기본값을 켰다(`shared-region-pool=true`).** 모든 차원과 추가 월드(W1)가 region 워커 풀 하나를 함께 쓰고, `region-threads`(기본 CPU 수)는 서버 전체 워커 수가 된다.

- 근거 1 — 지난번 기본값을 끈 채 남긴 이유였던 **40~60ms 튐은 스케줄러 탓이 아니었다.** 이번 측정 52회(두 모드, 조용한 기계 40회 + CPU 경합 12회)에서 한 번도 나지 않았고, 큰 늦음이 날 때는 스케줄러와 무관한 스레드도 같은 구간에서 같이 늦었다(아래 "카나리"). 지난번 측정은 같은 기계에서 gradle 10여 개가 함께 돌던 때다.
- 근거 2 — 공유 풀은 같거나 낫다. 부하 5ms·6차원 p95 6.0ms → 0.06ms, 최대 12.2ms → 2.4ms(중앙값). 깨어남 6008 → 811회, 워커 24개 → 4개. 같은 일량 CPU 는 같거나 낮다(10-28 측정).
- 근거 3 — 차원별 풀은 차원·추가 월드마다 `region-threads` 개씩 스레드가 늘어난다(3차원이면 코어의 3배, 추가 월드 2개면 5배). 코어보다 많은 틱 스레드가 서로 선점하는 것이 차원별 모드의 p95 5ms 늦음의 원인이다.
- 근거 4 — 과부하 시나리오(합계 부하 100~200%, 한 차원만 무거움, 차원 수·워커 수 변화)를 **실제 공유 풀로** 처음 쟀다(아래 "C"). 여기서 약점을 하나 찾아 고쳤다: 한 차원의 region 틱이 40~80ms 로 길면, 가벼운 차원의 틱 사이에 그 차원이 네 워커를 다 채워 가벼운 차원이 틱마다 최대 60ms 늦었다(차원별 풀은 OS 가 나눠 줘서 안 늦음). 상한(T−1)을 "다른 차원에 지금 때가 된 일이 있을 때"가 아니라 "다른 차원 큐에 일이 있을 때" 걸도록 바꿔, 가벼운 차원은 차원별 풀과 같게 제때 돈다.
- 바닐라 결과에는 영향이 없다. 바뀌는 것은 "어느 워커가 어느 region 을 언제 돌리나"뿐이고, region 안의 틱 순서, 소유권 확인(`Region.isOwnerThread`·`Owned`), sprint/freeze 코드는 그대로다. 서버 전체 시험을 공유 풀로 돌려 확인했다(아래 "시험").

## 설정 (furnace.properties)

| 키 | 종류 | 기본값 | 허용 값 | 설명 | 경고 |
|---|---|---|---|---|---|
| `shared-region-pool` | ON/OFF | true | true\|false | 모든 차원·추가 월드가 region 워커 풀 하나를 쓴다. false 면 이전처럼 차원마다 `region-threads` 개 | 차원별이고 워커 합이 코어의 2배를 넘으면 경고 |
| `region-pool-dim-cap` | 수 | 0 | 0 이상 | 다른 차원 큐에 할 일이 있을 때 한 차원이 동시에 쓸 수 있는 워커 상한. 0 = 워커 수−1(한 워커는 늘 다른 차원 몫). 워커 수 이상으로 두면 상한 없음 | |
| `region-pool-starve-ticks` | 수 | 2 | 1 이상 | 차원의 가장 이른 작업이 이 틱 수만큼 밀리면 그 차원을 먼저 돌린다 | |

- 되돌리기: `shared-region-pool=false`. JVM 인자 `-Dfurnace.sharedRegionPool=true|false` 가 있으면 그 값이 이긴다(파일 값과 다르면 경고). `-Dfurnace.sched.dimCap`·`-Dfurnace.sched.starveTicks` 는 시험·벤치용으로 남겼고, 파일 키가 있으면 파일 키가 이긴다.
- 잘못된 값(`yes`, 음수, 0 굶음 틱)은 키 이름을 밝히며 기동을 멈춘다. 공유 풀이 꺼져 있는데 상한·굶음 키를 쓰면 "쓰이지 않는다"고 경고한다.
- 기동 로그: `[SCHED] region 워커 N개(서버 전체 공유|차원별, 차원 M개)`. 공유 풀에서 `region-threads` 가 코어의 2배를 넘거나, 차원별 풀에서 워커 합이 코어의 2배를 넘으면 경고 한 줄.
- **기존 서버 주의**: `region-threads` 를 직접 적어 둔 서버는 의미가 "차원마다"에서 "서버 전체"로 바뀐다. 예전에 `region-threads=4` 로 3차원을 돌렸다면 워커가 12개에서 4개가 된다. 4코어 기계라면 이것이 맞는 값이고(측정에서 더 빠름), 차원 수만큼 늘리고 싶으면 값을 올리면 된다.

## 측정 (2026-11-07)

`MultiDimensionTickBench.dimensionsTickJitter`, 차원마다 region 2, 200틱, 4코어 샌드박스, 현행(차원별)/공유 번갈아. 늦음 = region 틱 간격 − 50ms. `[최소..최대] 중앙값`.
벤치에 두 가지를 더했다(커밋에 포함): 측정 중 **GC 시간 합**(`GarbageCollectorMXBean`)과, 스케줄러와 무관한 **카나리 스레드**(1ms 파킹을 반복하며 늦잠을 기록). 늦음이 가장 큰 간격 3개마다 같은 구간의 카나리 최대 늦잠을 함께 찍는다(`MDBENCH-CAUSE` 줄). 카나리도 같이 늦었으면 스케줄러 밖(OS 선점·GC·세이프포인트)이다.

- 한 차원만 무거울 때(가장 흔한 실제 상황 — 오버월드에 렉 기계): 고친 뒤 가벼운 차원은 차원별 풀과 같게 제때 돈다.
- 기계 전체가 넘칠 때(합계 150%): 차원별 풀은 무거운 차원 하나가 80~100ms 늦고 나머지는 덜 늦는다. 공유 풀은 모든 차원이 25ms 안팎으로 고르게 늦는다(바닐라처럼 한 루프에서 다 같이 느려지는 쪽에 가깝다). 어느 쪽이 낫다고 하기 어려운 정책 차이이고, 두 모드 모두 CPU 가 모자란 것은 같다.
- `region-threads` 를 코어 수보다 작게(워커 2, 코어 4) 두면 공유 풀은 코어 절반만 쓴다 — 공유 풀에서 이 값은 서버 전체 워커 수다. 기본값(코어 수)이 맞다. 코어 수의 2배(워커 8)에서는 공유 풀이 같거나 낫다.
- 평상시 흔들림 벤치(A)는 고친 뒤 다시 2회: 부하 5ms·6차원 p95 0.05ms·최대 0.3~3.9ms 로 그대로.

### 해석
- 지난번 "한 회차씩 나는 30~60ms 튐"은 두 모드 모두에 있었고 공유 쪽 깨우기 유실 계측이 0 이었다. 이번에 무관한 스레드를 함께 재 보니 큰 늦음은 기계 쪽 멈춤과 겹친다. 지난번 측정 때 동시에 돌던 gradle 10여 개(CPU·메모리 경합, GC)가 원인이었다고 본다. 그 조건을 그대로 다시 만들지는 못했다(그때의 다른 작업을 알 수 없음).
- 공유 풀이 나쁜 경우는 찾지 못했다.

## 시험
- `SharedPoolS4Test.longTicksInOneDimensionLeaveAWorkerForOthers`(새): 60ms 틱 region 4개 차원 옆 가벼운 차원의 틱 간격이 50±10ms 를 벗어난 횟수 ≤ 10%, 그동안 무거운 차원 병렬도 = 3. 고치기 전 동작으로 돌리면 44 중 27·37 회 벗어나 실패한다(두 번 확인).
- `RegionPoolSettingsTest`(6): 기본 켬, 키로 끔, JVM 인자 우선·충돌 경고, 수치 키·잘못된 값 거부, 꺼졌을 때 수치 키 경고, 워커 과다 경고.
- 서버 전체 시험을 시험 전용 스위치 `-Dfurnace.test.sharedRegionPool=true`(모든 시험 월드가 공유 풀을 탄다)로: **3038개 실패 0·스킵 41**(11분 36초), 상한 규칙을 고친 뒤 다시 **3039개 실패 0·스킵 41**. 시험 출력에 찍힌 region 스레드 이름 58건이 모두 공유 풀 이름(`furnace-region-N`)이고 차원별 이름(`furnace-region-overworldN` 꼴)은 0건 — 지난번 "실제로 공유 풀을 탔는지 세지 않았다"는 가정을 이것으로 확인했다.
- CI 의 기본 시험(스위치 끔)은 지금처럼 차원별 경로를 돈다. `SharedPoolS4Test` 가 실제 공유 풀(세 차원 동시 틱·공정성·분리·sprint)을 늘 확인한다.

## 남은 것
- 실제 플레이어 접속 상태에서 오래 돌린 기록은 없다(벤치는 가짜 차원). 운영 중 `/tps`·`[SCHED]` 로그에서 이상하면 `shared-region-pool=false` 로 바로 되돌릴 수 있다.
- 무거운 차원이 **둘 이상** 동시에 긴 틱을 돌리면 둘이 합쳐 모든 워커를 채울 수 있다(상한은 차원마다 T−1). 이때 셋째 차원은 최대 그 틱 길이만큼 늦는다. 측정하지 않았다.
