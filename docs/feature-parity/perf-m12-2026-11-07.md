# M12 — 플레이어 2명부터 청크 전송이 느려지는 관찰 (2026-11-07)

대상: `docs/user-todo.md` "서버 성능 관찰"(N-05 청크 스냅샷 보관 제거 이후, 2명부터 1명일 때보다 느림).
같은 날 다른 스레드가 M12 의 다른 원인(종료 저장 유실, 빛 재계산)을 고쳤다 — `perf-multiplayer-chunks-2026-11-07.md`. 이 문서는 그와 겹치지 않는 압축 중복만 다룬다(두 변경은 서로 독립).
앞선 기록: `perf-c2-2026-10-27.md`(같은 청크 동시 요청이 각자 스냅샷·직렬화하던 중복을 진행 중 본문 공유로 제거), PR #92(`chunks-per-tick=auto`).

## 결론
- C-2 이후 **스냅샷·직렬화**는 이미 청크당 한 번이다(실서버에서도 확인: 고유 청크 수 ≈ 스냅샷 수).
- 실서버에서 남아 있던 플레이어 수 비례 비용은 **압축 중복**이었다. 청크 프레임 공유(`SharedChunkFrames`)가 "처음 보내는 연결의 이벤트 루프가 압축하고 캐시에 넣는" 방식이라, 여러 플레이어가 같은 청크를 거의 동시에 보내면 서로 다른 이벤트 루프가 캐시 미적중 상태로 같은 본문을 각자 압축했다(고유 청크 대비 압축 횟수: 1명 약 1.0배, 2명 1.3배, 4명 1.6~1.8배). 청크당 압축은 약 0.8 ms 로 청크 저장 비용의 큰 몫이다.
- 고침: 본문을 만드는 청크 풀 스레드에서 **한 번만 미리 압축**해 공유 캐시에 넣는다(`SharedChunkFrames.precompress`, 압축 임계값은 `NetworkServer` 가 시작할 때 알림). 이벤트 루프는 캐시된 프레임을 그대로 쓴다. 압축 바이트는 연결별 인코더와 같다(같은 레벨·임계값, 패킷마다 초기화되는 zlib — `CompressionTest.precompressedFrame_isSharedByChannels_andMatchesNormalPath`). 임계값이 다른 연결은 예전 경로로 돌아간다.
- 나머지 "2명부터 약간 느림"은 서버 구조 문제가 아니다. 아래 표의 클라이언트 쪽 시간 증가는 측정용 노드 클라이언트가 같은 4코어를 쓰는 탓(클라이언트 1개가 약 0.7코어, 4개면 서버가 쓸 코어가 줄어듦)이고, 플레이어마다 스폰 위치가 달라(스폰 반경 무작위) 고유 청크 수도 453 → 499~540개로 늘어난다.

## 측정
환경: 4코어 컨테이너, 시드 12345 노이즈 월드, 시야 10(441청크), 디스크에 이미 만든 땅을 서버 재시작 직후 받음(메모리 캐시 없음), 청크 속도 응답 64(빠른 바닐라 클라이언트 흉내). 클라이언트는 `tools/bot-test/chunkrate/chunkrate.js` 여러 개 동시 접속. 서버 쪽 시간은 임시 계측(첫 전송 결정 ~ 마지막 배치 Finished)이며 커밋하지 않았다. 공유 4코어라 반복 간 ±15% 잡음이 있다.

### 서버 쪽 전송 완료 시간과 압축 횟수 (수정 전 → 후)
| 플레이어 | 압축 횟수 / 스냅샷(고유 청크) 전 | 후 | 완료 ms 전 | 후 |
|---|---|---|---|---|
| 1 | 428~437 / 446~466 | 441 / 453~466 | 1466~1474 | 1422~1473 |
| 2 | 616 / 469 | 485 / 501 | 1639~1643 | 1461~1488 |
| 4 | 835~905 / 510~532 | 485~516 / 499~541 | 1675~1890 | 1627~1914 |
| 8 | (측정 안 함) | 893~899 / 899~905 | — | 2035~3096 (클라이언트 8개와 코어 경합) |

- 압축 횟수 / 고유 청크: 4명 기준 전 1.7~1.8배 → 후 약 1.0배. 8명은 후에도 1.0배.
- 서버 프로세스 CPU(user+sys, 4명 접속 구간, 반복 2회): 전 6.84 / 7.25 s → 후 6.60 / 6.62 s (1명: 전 5.44 / 7.23 s, 후 5.10 / 6.13 s). 차이가 잡음 범위에 가깝다. 압축이 여러 이벤트 루프에서 병렬로 돌아 중복의 벽시계 비용은 CPU 비용보다 작다.
- 클라이언트에서 마지막 청크까지 걸린 시간(참고): 1명 1.8~2.1 s, 2명 1.85~2.3 s, 4명 2.5~2.9 s, 8명 3.7~4.3 s. 수정 전과 후 차이는 잡음 범위이고, 증가분은 대부분 클라이언트 CPU 경합이다.

### 하지 않은 것
- 스냅샷 복사(약 390 KB/청크, region 스레드)를 없애는 구조 변경: `perf-c2`·`perf-c5` 에서 이미 비용이 분리됐고 플레이어 수와 무관하다.
- region 홉(N-10) 줄이기: 패킷 순서가 바뀔 수 있어 `perf-c2` 결정 유지.
- 서로 다른 플레이어에게 전송 속도를 나눠 주는 공정성 정책은 바닐라에도 없다(플레이어별 독립).

## 다시 재는 법
서버를 띄우고 `cd tools/bot-test && for i in 1 2 3 4; do node chunkrate/chunkrate.js C$i 10 64 2500 & done; wait`. 서버 쪽 시간이 필요하면 `Region.sendQueuedChunksAuto` 에 임시 로그를 넣는다. 단위 벤치 `MultiPlayerChunkSendBench`(`-Dfurnace.bench=true`)는 미리 압축을 켜지 않아 예전 경로(채널별 압축)를 잰다 — 새 경로를 재려면 벤치에서 `SharedChunkFrames.precompressThreshold(256)` 를 먼저 부른다.
