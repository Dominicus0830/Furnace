# C-4 성능 측정 (2026-10-28) — E-19~E-25 틱 할당, N-10 선행 시험

앞선 기록: `perf-c2-2026-10-27.md` 5.3 "미완" 두 항목을 이어서 한다.
원칙: 근거는 벽시계가 아니라 **region 스레드 CPU ns·할당 바이트**(ThreadMXBean 차분)다. 반복 3회 범위로 적는다.

## 환경·방법
- 머신: 4코어 VM, 측정 시작 시 load average 0.6~1.3(공유 머신, 다른 에이전트 gradle 은 `flock` 으로 배제).
- JVM: gradle test 기본(Java 21, G1, `maxHeapSize=3g`, `-ea`).
- 벤치: `furnace-server/src/test/java/org/domi/furnace/server/world/PlayerWalkTickBench.java` (기본 꺼짐).
  - 실행: `ORG_GRADLE_PROJECT_skipOracle=true flock /tmp/furnace-gradle.lock ./gradlew --offline :furnace-server:test --tests org.domi.furnace.server.world.PlayerWalkTickBench -Dfurnace.bench=true -Dfurnace.bench.reps=3`
  - 평지 월드, 시야 8, 엔티티 시야 4, region 스레드 1개(모든 region 이 한 워커 → 그 스레드 차분이 곧 region 비용), 청크 풀 2.
  - N명(1/4/16/32)이 6열로 모여 출발해 각자 다른 방향(360°/N)으로 달리기 속도(0.2806 블록/틱)로 걷는다.
    이동 입력은 `ConnectionHandler` 의 move_player_pos_rot 수락 경로와 같은 호출(`publishPosition` + `pushMove`)로 넣는다
    (로그인 상태머신 전체를 EmbeddedChannel 로 돌리지는 않았다 — 가정: 수락 뒤 region 쪽 경로는 같다).
  - 게임 틱은 `World.tickOnce()` 를 50ms 간격으로. 틱 시작 사이의 region 스레드 `getThreadAllocatedBytes`/`getThreadCpuTime`
    차분 = 그 틱 + 그 사이 인박스 작업(청크 로드·본문 스냅샷 홉). 예열 40틱 뒤 200틱 측정.
  - JFR: `-Dfurnace.bench.jfr=<경로>` 면 벤치가 `jdk.ObjectAllocationSample` 만 켠 녹화를 직접 시작하고, region 스레드 샘플을
    스택(위 8프레임)별 무게 합으로 묶어 상위 10개를 찍는다(N=32, 1회).

## 1. E-19~E-25 틱 핫패스 할당

### JFR 상위 할당원 (N=32, region 스레드 샘플 무게 합 592.2MB)
| # | 비율 | 할당 | 위치 |
|---|---|---|---|
| 1 | 30.8% | `int[]` | `PaletteStorage.unpack` ← `ChunkSection.blocks` ← `ChunkSnapshot.of` ← `World.serializedChunkBody`(본문 스냅샷) |
| 2 | 17.9% | `Object[]` | `ArrayList.grow` ← `NaturalSpawner$SpawnState.playersNear:57` ← `localCanSpawn` |
| 3 | 13.5% | `byte[]` | `ChunkSnapshot.copyLight:115` (하늘빛) |
| 4 | 8.1% | `byte[]` | `ChunkSnapshot.copyLight:116` (블록빛) |
| 5 | 4.7% | `Object[]` | `ArrayList.grow` ← `playersNear` (첫 grow) |
| 6 | 2.4% | `int[]` | `LevelServices.sharedSpawnPos` ← `NaturalSpawner.isRightDistanceToPlayerAndSpawnPoint` |
| 7 | 2.3% | `ArrayList` | `playersNear:52` |
| 8 | 1.7% | `Pos` | `NaturalSpawner.spawnCategoryForPosition:191` |
| 9 | 1.1% | `HashMap$Node` | `Region.updateVisibility` 의 `HashSet seen` |
| 10 | 1.0% | `MoveEntityPosRot` | `Region.broadcastMove` |

해석:
- 1·3·4(약 52%)는 청크 본문 스냅샷 복사다(C-2 5.2 에서 본 청크당 약 510KB). 걷기 시나리오의 p95 8~9MB 틱은 새 시야 줄의 스냅샷이 몰린 틱이다.
- **2·5·7(약 25%)은 자연 스폰의 지역 상한 판정이 청크·종류마다 근처 플레이어 목록을 새로 만든 것**이다. 플레이어 수에 비례해
  목록이 커지고(32명이 모두 128블록 안) 호출 수도 청크 수 × 종류 수라 N 이 클수록 커진다.
- 감사가 예로 든 `updateVisibility` 의 `HashSet seen`·`List.of` 는 1.1% 로 작다.

### 수정 — 채택: `NaturalSpawner.SpawnState` 근처 플레이어 목록 제거
- `playersNear` 가 만들던 목록 대신 같은 순서로 `players` 를 바로 훑으며 같은 판정(관전자 제외, 청크 중심 128블록)을 한다.
  `localCanSpawn` 은 "조건을 만족하는 근처 플레이어가 하나라도 있는가", `addMobToLocalCaps` 는 근처 플레이어마다 카운트 +1 이라
  순서·결과가 그대로다. RNG 호출 없음(parity 무관).
- 출력 동일성 시험: `SpawnStateLocalCapTest.localCaps_matchListBasedReference` — 예전 목록 기반 구현을 시험 안에 그대로 두고,
  플레이어 12명(관전자 포함)·무작위 청크·종류 4000단계에서 `canSpawnForCategory` 결과와 카운트 누적이 같은지 비교.

| 4 | 1236.6~1241.2 KB | 575.4~584.2 KB | 2.709~3.271 ms | 2.337~2.764 ms | 5.680~7.516 ms |

### 미채택(제안)
- 본문 스냅샷(1·3·4, 약 52%): 스냅샷 없이 region 스레드에서 직접 직렬화하면 이 할당은 사라지지만 region CPU 가 는다
  (C-2 5.2 와 같은 트레이드오프). 섹션 팔레트를 풀지 않는 스냅샷(`PaletteStorage` 원본 복사)이 후보지만 N-07 과 같이
  와이어 바이트 불변을 지켜야 해 별도 설계가 필요하다.
- `updateVisibility` 의 `HashSet seen`(1.1%)·`List.of`·이동 패킷 레코드(1.0%): 이득이 작아 이번에는 바꾸지 않는다.
- `sharedSpawnPos` 의 `int[]`(2.4%)·`Pos`(1.7%): 스폰 시도마다 새 배열·좌표. 바닐라 구조를 따르는 코드라 이식 순서를 해치지 않는
  선에서 캐시할 수 있는지 따로 본다.

## 2. N-10 선행 시험 — 청크 전송 패킷 순서 골든

### 시험
`ChunkSendPacketOrderGoldenTest.sameTickBlockChangeMoveAndChunkSend_packetSequenceIsFixed` (10회 반복).
- 본문 캐시를 미리 모두 채운 뒤(모든 요청이 캐시 적중) 플레이어 A·B 를 들이고 `startTicking()` 으로 실제 게임 틱을 돌린다.
  채널은 region 스레드 작업 안에서만 읽는다(EmbeddedEventLoop 큐가 스레드 안전하지 않아서).
- 한 인박스 작업(다음 틱 드레인 = 그 틱의 게임 틱 직전)에서: 이미 받은 청크 (0,0) 블록 편집, A 를 청크 (1,0) 으로 이동,
  B 이동·회전, 새로 구독될 청크 (3,0) 편집을 1틱 지연 작업으로.
- A 가 받는 패킷 열(현재 구현으로 기록):
  `block@1,-61,1, center, unload×5, batchStart, movePosRot, head, chunk@3,0, chunk@3,-1, chunk@3,1, chunk@3,-2, chunk@3,2, batchEnd, block@48,-61,1`
- 10회 반복 10회 같은 열. (처음 시도에서 패킷 id 만 볼 때 끝의 `block` 이 두 번 나온 적이 한 번 있었고 그 뒤 13회 재현되지 않았다 —
  원인 미확인, 간헐 실패가 나면 이것부터 본다.)

### 판단: 캐시 적중 첫 홉 줄이기 — 미채택
실험으로 `Region.sendQueuedChunks` 가 주인 스레드·로드됨·본문 캐시 적중이면 `submitAtChunk`(+`loadChunk`) 홉 없이
완료된 future 를 쓰게 바꿔 골든을 돌렸다. **10회 모두 실패**, 실제 열:
`..., batchStart, chunk×5, batchEnd, movePosRot, head, block@48,-61,1`.
- 지금은 본문 홉이 다음 틱 드레인에서 돌아, 같은 틱의 엔티티 이동·머리 회전 패킷이 청크보다 먼저 나간다. 빠른 경로는 청크와
  배치 끝을 그 틱의 `sendQueuedChunks` 안에서 바로 보내 엔티티 패킷 앞으로 옮긴다. 즉 **홉 수가 패킷 순서를 바꾼다.**
- 블록 변경과 청크 사이 순서(보류 → 청크 뒤)는 두 경우 모두 지켜졌다. 바뀌는 것은 청크 대 다른 틱 패킷 순서다.
- 그래서 최적화하지 않았다(실험 코드는 되돌림, CPU 전/후 측정은 하지 않음). 이 순서가 바닐라와 어느 쪽이 같은지는 확인하지 않았다
  (가정: 바닐라는 `PlayerChunkSender.sendNextChunks` 가 연결 틱에서, 엔티티 추적은 `ChunkMap.tick` 에서 돈다 — 바닐라 순서를
  jar 로 확인한 뒤 그쪽이 빠른 경로 순서라면 골든을 그 근거와 함께 고치고 다시 검토한다).
