# 마크 버전업 빠르게 하기 — 계획 (2026-11-16)

기준 커밋 `5a9c7c552`(기준 브랜치 `claude/quirky-wright-lra834`, PR #408 병합 뒤). 같은 내용을 공유 폴더 `furnace/reviews/version-upgrade-plan-2026-11-16.md` 에도 둔다.

목표: 지금 남은 작업이 끝나 실제 서비스가 가능한 상태가 된 뒤, 1.21.1 → 새 버전 올리기를 "코드 다시 쓰기"가 아니라 **"데이터 다시 뽑기 + 바뀐 바닐라 동작만 옮기기 + 바뀐 곳만 시험"** 으로 만든다. 단, 성능은 조금도 나빠지면 안 된다.

## 1. 요약 (먼저 읽을 것)

- 앞선 조사는 2026-07-05 의 `LLM-Wiki/output/furnace-version-upgrade-design.md` 하나다(AGENTS.md 규칙 6 이 이 문서를 가리킨다). 그 뒤 코드가 약 4배 커져서(서버 1,983 · 호환 계층 1,123 · API 469 클래스) **방향은 맞지만 범위가 크게 모자란다.** 7월 문서가 몰랐던 부채가 6개 더 있다(2장 표의 N1~N6).
- 버전업 비용은 두 덩어리다.
  1. **기계로 줄일 수 있는 것**(버전 숫자, 블록 상태 번호, 패킷 번호, 엔티티 메타데이터 칸 번호, 데이터 표 뽑기, 시험 정답표): 지금은 수백 곳에 손으로 박혀 있다. 0단계(V-01~V-08)에서 "한 곳에서 생성"으로 바꾸면 다음 버전업 때 거의 자동이 된다.
  2. **기계로 못 줄이는 것**(바닐라가 실제로 바꾼 동작: 새 블록·몹·패킷 형식·월드젠·월드 저장 형식): 이건 매번 사람이(모델이) 옮겨야 한다. 줄일 수 있는 것은 "무엇이 바뀌었고 Furnace 의 어느 파일을 고치면 되는지 찾는 시간"뿐이다 → 대응표(V-06)와 바닐라 소스 차이 도구(U-03)로 찾는 시간을 0 에 가깝게 한다.
- 0단계 작업은 모두 **결과가 바뀌지 않는 정리**라서 지금 진행 중인 작업과 나란히 할 수 있다(파일이 겹치는 V-03·V-04 만 ProtocolLib P0·T-141 뒤).
- 성능: 바꾸는 방식은 전부 **컴파일할 때 상수가 되는 `static final` 생성 상수**다. 실행 중 버전 분기·인터페이스 호출·표 조회를 핫패스에 새로 넣지 않는다. 바이트코드 비교(`javap`)로 "전과 같은 명령"임을 증명하고 기존 벤치로 한 번 더 본다(6장).
- 시험: CI 가 지금은 코드가 한 줄만 바뀌어도 서버 시험 약 3,900개를 4조각으로 전부 돌린다. **바뀐 클래스를 실제로 실행한 시험만 고르는 장치(V-08)** 를 넣어 PR 은 관련 시험만, 전체는 기준 브랜치 병합 뒤·출시 전에만 돌린다(5장).
- 도미니코 결정: Z1 **판마다 차례로(1.21.2 → … → 26.3) 확정**, Z2(PR 에서 관련 시험만) 남음. 8장.

## 3. 어디를 어떻게 바꾸나 (구조 변경)

원칙: **실행 중 버전 분기는 만들지 않는다.** 서버는 늘 한 버전만 빌드한다. 버전 차이는 "빌드할 때 어떤 데이터 파일로 상수를 생성하느냐"로만 생긴다. 그래서 핫패스에는 지금과 똑같은 상수 비교만 남는다.

### 3.1 한 곳: `gradle/minecraft.properties` (새 파일)
```
mc.version=1.21.1
mc.protocol=767
mc.dataVersion=3955
mc.resourceTag=1.21.1
mc.paperDevBundle=1.21.1-R0.1-SNAPSHOT
mc.bukkitVersion=1.21.1-R0.1-SNAPSHOT
mc.craftPackageSuffix=v1_21_R1
mc.packFormat.data=48
mc.packFormat.resource=34
mc.javaRelease=21
```
- Gradle 작업 `generateGameVersion` 이 `org.domi.furnace.server.version.GameVersion`(서버), `org.domi.furnace.api.GameVersion`(API, 플러그인에도 보임)을 `build/generated` 에 만든다. 모든 칸은 `public static final` 원시값·문자열 = **컴파일 시간 상수**라 javac 가 쓰는 자리에 그대로 박는다(실행 비용 0).
- 리소스 경로 약 100곳: `"blocks/blockattrs_" + GameVersion.RESOURCE_TAG + ".txt"` 꼴. 상수끼리 더하기라 이것도 컴파일 시간 상수다.
- `worldgen-oracle/build.gradle`, `furnaceVersion` 기본값 3곳, 툴체인도 이 파일을 읽는다.

### 3.2 생성 상수 묶음 (모두 `build/generated`, 커밋 안 함, 입력은 커밋된 리소스)
| 생성물 | 입력 | 바꾸는 곳 | 비고 |
|---|---|---|---|
| `StateIds` (`MIN_OAK_LEAVES`, `VINE_FIRST/LAST`, `GLOW_LICHEN_BASE`, `CAVE_AIR`, …) + 속성 공식 상수(잎 distance 보폭 4, 묶음 28) | `blocks/blockstates_<ver>.txt`, `definitions_<ver>.txt` | A4 의 40~60곳 | 공식은 속성 순서에서 **도출**하고, 도출값을 생성 시험으로 단언 |
| `PacketIds` (`CLIENTBOUND_LEVEL_CHUNK_WITH_LIGHT = 0x27` …, 상태별) | `protocol-<proto>-ids.txt`(지금 API 리소스) | 서버 패킷 133개 `ID`, `ConnectionHandler` `case` 68개, `Protocol767` | `case` 에 쓰려면 컴파일 시간 상수여야 한다 — 생성 상수는 그렇다 |
| `EntityDataIds` (`FOX_TYPE = 17` …) | `entity_data/layouts-<ver>.txt` | N2 의 104개 파일 | |
| Bukkit 생성 파일 376개 | 기존 `gen-bukkit-*.py` | — | 입력 경로만 `mc.resourceTag` 로 |

버전 이름이 들어간 클래스 이름(`Protocol767`, `EntityData767`, `GenericHand767`)은 0단계에서 이름을 안 바꾼다(PR 충돌만 키운다). 실제 버전업 때 `Protocol` 로 바꾼다.

### 3.3 데이터 뽑기 도구를 한 모듈로: `tools/vanilla-extract` (N1)
- 지금 `tools/vanilla-data/Export*.java` 등 18개 + 파이썬 바이트코드 해석 2개 → **Mojang 이름으로 쓴 Gradle 모듈 하나**. 1.21.1~1.21.11 은 바닐라 jar 를 **Mojang 공식 대응표(판마다 공개되는 server mappings)로 이름을 풀어** 클래스패스에 둔다 — Paper dev bundle 이 없는 판(예: 1.21.2 로 알려짐)에서도 돈다. 26.x 는 난독화 없는 바닐라 jar 를 그대로(둘 다 로컬 캐시, 커밋 안 함 — 규칙 7). 차례로 13개 판을 거치므로(Z1) 판 하나에 도구 수정이 생기면 13배가 된다 — 이 모듈이 1단계 속도의 핵심이다.
- 명령 하나: `./gradlew :vanilla-extract:run -Pmc=<버전>` → `resources/**/<ver>` 전부 + 시험 정답표 재생성.
- 수용 조건: **1.21.1 로 돌린 결과가 지금 커밋된 리소스와 바이트 단위로 같다.** 이것이 도구를 옮겨도 아무것도 안 바뀌었다는 증명이다.
- `settings.gradle.kts` 의 `skipOracle` 처럼 기본 빌드·CI 에서는 빠진다(Paper 저장소가 막힌 환경 대비).

### 3.4 바닐라 ↔ Furnace 대응표 (N5)
- 소스 전용 주석 `@VanillaPort("net.minecraft.world.entity.animal.Fox")` (`@Retention(SOURCE)` — 클래스 파일에도 안 남아 실행·크기 영향 0). 여러 바닐라 클래스를 합친 Furnace 클래스는 여러 값.
- 주석 처리기 또는 간단한 스캐너가 `build/vanilla-port-map.tsv` 를 만든다.
- U-03 도구: 두 버전 바닐라 소스(1.21.1 = Mojang 이름 디컴파일, 26.x = 난독화 없는 jar 디컴파일)를 클래스 단위로 비교 → "바뀐 바닐라 클래스 → 고칠 Furnace 파일 → 담당 묶음" 표. 디컴파일 소스는 커밋하지 않는다.

### 3.5 시험 정답표 버전 폴더
- `src/test/resources/<분류>/<ver>/…` 로 옮긴다(지금 `worldgen/fixtures/*.bin` 372개 등은 버전 폴더 없음). 시험은 `GameVersion.RESOURCE_TAG` 로 경로를 만든다.
- 버전업 때 새 폴더를 만들고 옛 폴더는 지운다(두 판을 같이 두지 않는다 — AGENTS.md 규칙 1 의 뜻 유지).

### 3.6 월드 데이터 올리기 틀 (N4)
- 지금 `OlderDataVersionException` 을 던지는 자리(청크·엔티티 청크·플레이어·level.dat·`ForcedChunks`·`CommandStorage` 등 `DataVersion` 23파일)를 "현재보다 옛 판이면 `FixTable` 통과 후 읽기"로 바꾼다. 0단계에서는 **틀만**(3955 → 3955 이라 단계 0개) 넣고, 단계 내용은 버전업 때 채운다.
- 성능: 판이 같으면 정수 비교 한 번(지금도 하는 비교)이고 단계 0개면 아무것도 안 한다. 청크 읽기 경로는 이미 이 비교를 한다.

### 3.7 호환 계층 (N3)
- 생성 가능한 것은 생성으로 옮긴다: Bukkit enum·레지스트리·태그·블록 상태·엔티티 클래스(이미 376개), 버전 문자열(`getBukkitVersion`, `CraftNames.VERSION`)은 3.1 상수로.
- 손 코드 shim 은 버전업 때 **"Paper API 서명 차이 도구"**(U-07a: 새 Paper API jar 의 공개 서명 ↔ Furnace 호환 클래스 서명 비교, B6 의 `filter121.py` 방식 확장)와 **"NMS 이름 차이 도구"**(바닐라 두 판의 Mojang 이름 클래스·멤버 비교 → shim 223+203 중 바뀐 것)로 고칠 목록을 뽑는다.
- 26.1 부터 바닐라가 난독화되지 않으므로, Spigot 대응표(H7d) 경로는 1.21.x 플러그인용으로만 남고 새 판에서는 할 일이 줄 것으로 본다(가정 — 착수 때 Spigot 쪽 정책 확인).

### 5.2 V-08: 시험 영향 선택 (Gradle + CI)
1. **영향 표 만들기(매일 밤, 기준 브랜치)**: 기존 커버리지 작업(`-Pcoverage`, JaCoCo)을 "시험 클래스가 끝날 때마다 실행 데이터를 꺼내고 비우는" JUnit 리스너로 돌린다(`org.jacoco.agent.rt.RT.getAgent().getExecutionData(true)`). 결과 `test-impact.tsv`: `시험 클래스 → 실행된 본 클래스 목록`. 산출물로 올리고 PR 이 받아 쓴다(커밋하지 않음). 시험 시간에는 영향 없음(밤 작업만).
2. **PR 에서 고르기**(`tools/ci/select-tests.py`): 바뀐 `.java` → 본 클래스 이름 → 그 클래스를 실행한 시험 클래스 + 바뀐 시험 클래스 자신. 결과를 `--tests` 목록(또는 `-PtestSelection=file`, `build.gradle.kts` 의 기존 `testShard` 처럼 `include` 필터)으로 넘긴다. 고른 수가 적으면 조각을 줄인다(예: 300개 미만이면 1조각).
3. **전체로 넘어가는 경우(안전망)** — 이 중 하나면 그 모듈 전체:
   - 빌드·CI 파일, `src/test` 공용 도우미(`TestServers`, `furnace-test`, 확장 `*Extension`), `junit-platform.properties`
   - 리소스(`src/main/resources/**` — 리소스는 클래스 커버리지에 안 잡힌다). 단 리소스 파일 → 읽는 클래스 대응을 표에 넣으면(읽기 함수에서 기록) 그 시험만
   - 금 파일·정답표 변경, `sched/**`·`Regionizer`·`ChunkColumn` 같은 동시성 핵심(목록은 `tools/ci/full-test-triggers.txt`)
   - 영향 표가 없거나 7일보다 오래됨, 새 본 클래스(표에 없음)는 같은 패키지 시험 전체로 대신
4. **전체 실행 시점**: 기준 브랜치 push(병합 뒤, 지금처럼 4조각), 매일 밤(영향 표 만들 때 함께), 출시·main 반영 전(노트북). 병합 뒤 전체에서 빨강이 나오면 그 PR 을 되돌리거나 바로 고친다 — 고르기가 놓친 것이 무엇인지 `select-tests.py` 시험에 사례로 추가.
5. **모듈 단위는 이미 분리**: `furnace-api`·`furnace-compat-paper`·`furnace-test` 는 바뀐 모듈과 그 모듈에 의존하는 모듈만 돈다(Gradle 프로젝트 의존 그래프로 판단: API 가 바뀌면 전부, 호환 계층만 바뀌면 서버 시험 0개).

예: `world/gen/feature/TreeFeature.java` 한 파일 고침 → 영향 표상 그것을 실행한 시험(트리·장식·월드젠 장면 몇십 개)만, ProtocolLib·명령·채팅 시험은 안 돈다.

### Z2. PR 에서 관련 시험만 돌릴 때 안전장치
- **쉬운 말**: PR 마다 바뀐 코드를 실제로 지나가는 시험만 돌리면 CI 가 훨씬 빨라진다(예: 나무 생성 한 파일 고치면 나무·장식 시험만). 대신 아주 드물게, 간접적으로 영향받는 시험을 놓쳐서 병합 **뒤** 전체 실행에서야 빨강을 볼 수 있다.
- **선택지**
  1. **(추천) PR 은 관련 시험만, 병합 뒤·매일 밤·출시 전은 전체** + 핵심 동시성 파일·빌드·리소스·시험 도구가 바뀌면 PR 도 전체 — 놓쳐도 몇 시간 안에 잡히고 그 PR 만 고치면 된다.
