# shim 채우기와 버전업을 더 빠르게 — 외부 사례 조사와 개선안 (2026-11-23)

도미니코 요청(11-23): "더 나은 방법을 연구·조사". 대상은 두 가지다. ① NMS shim(플러그인이 부르는 바닐라 클래스 겉모양)을 1.21.1 에서 실제 호출 95% 까지 채우기, ② 버전업(1.21.2·1.21.3 부터)을 빠르게. 방향은 도미니코가 정한 그대로다: **LLM 이 아니라 프로그램이 채우고, 시험도 프로그램이 한다.**

이 문서는 제안까지다. 코드는 바꾸지 않았다. 숫자 가운데 이번에 돌린 것은 2.3 의 패킷 표 하나이고, 나머지는 기존 문서의 실측(출처를 적음)이거나 "가정"이라고 적은 추정이다.

읽는 순서: 1장(결론) → 5장(상위 5개 실행 계획). 결정 F1~F3 은 `docs/user-todo/entries/2026-11-23-faster-shim-version-up.md` 에 쉬운 말로 적었고, 11-23 도미니코가 셋 다 추천(A)대로 확정했다(F1 시험 통과 읽기 연결 검토 생략·쓰기 유지, F2 바뀐 줄 보기 도구 만듦, F3 장면 시험 CI 에서도).

## 1. 결론 (먼저 읽을 것)

1. **왜 오래 걸리나.** shim 은 이미 빠르다: 108개 기호를 손으로 약 136분, 기호 하나에 약 1.3분이다(`compat-nms-batch5-axiom-voxy-2026-11-20.md` 표). 벽시계는 손 시간(검토 고침 포함)의 약 1.4배다(PR·CI·검토 왕복). 느린 곳은 기계가 아직 안 하는 두 가지, **"무엇에 이을지 찾기"와 "바닐라 값 시험 쓰기"** 다. 버전업은 PR #548 추정으로 현실 약 178 스레드시간인데, 그중 **약 60%(94시간)가 동작 옮기기(블록·아이템·엔티티·월드젠·명령)** 이고, "현실이 낙관의 2배"인 이유는 검토 반려와 정답 불일치 뒤 다시 하기다. 즉 시간을 줄이려면 ⓐ 찾기를 기계로, ⓑ 정답 확인을 기계로, 더 일찍 해야 한다.
2. **외부 사례에서 가져올 것은 세 가지다.**
   - Fabric 의 **Matcher**(두 jar 의 클래스·메서드를 바이트코드 모양으로 짝짓기)와 ViaVersion 의 **판 쌍마다 차이 표 생성 + 남는 것만 손으로** 방식 → "어디를 고칠지"를 멤버 단위로 자동으로.
   - Burger·PrismarineJS 의 **jar 바이트코드에서 패킷 모양을 뽑아 코덱을 만드는** 방식 → 패킷은 손 스키마 대신 추출.
   - Twitter Diffy 의 **차분 시험(같은 입력을 정답 쪽과 새 쪽에 넣고 결과를 견줌, 정답끼리 두 번 돌려 잡음 걸러내기)** 과 JQF·jqwik 의 **속성 기반·적용 범위 유도 입력 생성** → 시험을 사람이 쓰지 않고 프로그램이 만든다.
3. **가져오지 않을 것**: LLM 패치 이식(조사한 자바 벤치마크에서 성공률 40~46% — 프로그램 방향과도 맞지 않음), 여러 판 동시 지원 전처리기(Stonecutter·ReplayMod — Furnace 는 빌드당 한 판), 바닐라 위에 Mixin 을 얹는 방식(Sponge — 바닐라 코드를 싣게 됨), Paper 식 패치 묶음(Furnace 는 포크가 아님). 이유는 4.3.
4. **상위 다섯 개(5장)**, 효과 큰 순:
   | 순위 | 안 | 무엇을 줄이나 | 시간 절감 추정(가정) | 만드는 비용 |
   |---|---|---|---|---|
   | 1 | **차분 정답기 자동화**(T-235 실현 + 입력 자동 생성) | shim 값 시험 손 작성, 버전업 때 shim 동작 확인 75개 | shim 손 시간 약 30%↓, 버전업 U-07 약 4시간↓ | 1.5~2일 |
   | 2 | **연결 자동 추론기**(명세 줄 후보를 프로그램이 만들고 1번이 통과시키면 채택) | shim "무엇에 이을지 찾기" | shim 손 시간 추가 약 35%↓(1번과 합쳐 약 65%↓), 벽시계 100기호당 약 3시간 → 약 1.2시간 | 2~3일 |
   | 3 | **패킷 코덱 추출기**(바닐라 패킷 코덱 바이트코드 → 와이어 모양) | 버전업 U-04 프로토콜, 패킷 스키마 손 작성 | U-04 24h → 약 15h | 1~2일 |
   | 4 | **멤버 단위 대응표 + 바뀐 조각 보기**(Matcher 식 짝짓기 + 흐름 변경 정밀 분류) | 버전업 U-05 의 "어느 메서드가 어떻게 바뀌었나" 찾기와 오탐 | U-05 94h → 약 72h | 3~4일 |
   | 5 | **바닐라 장면 차분기**(같은 장면을 바닐라 서버와 Furnace 에서 돌려 상태를 견줌, 클라우드에서) | 재작업(현실 2배의 원인), PC 의존 | U-05·U-08·U-09 약 13h↓, PC 대기 감소 | 3~5일 |
   - 덤으로 **싼 것 하나**: 표류 보고(T-236)에 "본문 지문이 같으면 이름만 바뀐 것" 자동 판정과 명세 자동 고침을 넣는다(Matcher·OpenRewrite 식). 0.5~1일, U-07 약 4시간↓.
5. **합치면(가정)**: 1.21.1 → 1.21.3 한 홉이 현실 약 178 → 약 126 스레드시간(약 29%↓), 벽시계 현실 약 45h → 약 32h(5~6일 → 약 4일). 낙관 약 87 → 약 65 스레드시간. **도구를 만드는 데 약 10~14 스레드일**이 들어서 한 홉만 보면 본전이 안 되고, 1.21.4 이후 판마다 되풀이해 쓰일 때 이득이다(11-16 계획은 26.x 까지 여러 홉). shim 채우기는 1.21.1 에서 바로 이득이다.
6. **줄일 수 없는 바닥**: 바닐라 동작을 Furnace 구조(구역별 스레드)에 맞게 옮기는 일 자체. 바닐라 코드를 통째로 가져오지 않는 한(금지) 프로그램이 대신 못 한다. 프로그램이 할 수 있는 것은 "정확히 어디가 어떻게 바뀌었는지"를 줄 단위로 내놓고, 옮긴 결과가 맞는지를 자동으로 판정하는 것까지다.

### 2.3 패킷 코덱은 기계로 읽힐까 (이번에 잰 것)
바닐라 1.21.1 서버 jar(공식 대응표로 이름 확인, 결과는 개수만 적음)의 패킷 클래스 194개(`net.minecraft.network.protocol.*` 의 `Clientbound*Packet`·`Serverbound*Packet`, 안쪽 클래스 포함)를 `javap` 로 보고 코덱을 만드는 방식을 셌다.

| 코덱 만드는 방식 | 개수 | 기계로 와이어 모양을 뽑을 수 있나 |
|---|---:|---|
| `StreamCodec.composite(코덱, 게터, …)` | 27 | 예 — 인자 목록이 곧 필드 순서·코덱 |
| `StreamCodec.unit(…)`(필드 없음) | 9 | 예 |
| `Packet.codec(쓰기 메서드, 생성자)` 이고 쓰기 메서드에 **분기가 없음** | 135 | 대개 예 — 버퍼 쓰기 호출이 한 줄로 이어짐(읽기 쪽 대칭은 가정) |
| `Packet.codec` 이고 쓰기 메서드에 분기 있음(선택 필드·비트 묶음) | 14 | 손 |
| 그 밖·정적 초기화 없음·쓰기 메서드 못 찾음 | 9 | 손 |

→ **194개 중 171개(88%)는 기계가 와이어 모양을 뽑을 수 있는 꼴**이다(분기 없는 쓰기 메서드 135개는 안쪽에서 다른 코덱·`writeNbt` 같은 묶음 호출을 부르므로 "대개"). 지금 패킷 스키마(`furnace-api/.../protocol-767.schema`)는 손으로 쓰고 `tools/compat/packet-schema-check` 로 모양만 확인한다. 재현은 9장.

## 4. 외부 사례

### 4.1 마인크래프트 쪽

| 프로젝트 | 판 올리는 방식 | 우리에게 |
|---|---|---|
| **Paper** | Spigot·바닐라 위의 패치 묶음. 1.21.4 부터 Spigot 과 갈라져(hard fork) 패치 구조를 바꿨다(새 paperweight). 새 판에서 패치가 안 붙으면 사람이 고치고, 못 옮긴 패치는 `unapplied` 로 잠시 빼 둔다(PR #548 5.1 에서 6개 확인) | Furnace 는 포크가 아니라 같은 방식은 못 쓴다. "**못 옮긴 것을 명시적 목록으로 빼 두고 홉을 끝낸다**"는 운영 방식은 이미 `NoopFeature`·덫과 같은 생각 |
| **Folia** | Paper 위 패치(구역별 스레드) | 스레드 모델은 같지만 판 올리기는 Paper 를 따라감 — 참고할 도구 없음 |
| **Fabric** | 판마다 안 바뀌는 중간 이름(intermediary)을 **Matcher** 로 두 jar 의 클래스·필드·메서드를 "의미 유사도"(정적 분석)로 짝지어 이어 간다. **Stitch** 가 중간 이름을 만들고 관리 | **멤버 단위 짝짓기를 기계로**: 안 4(Furnace ↔ 바닐라 멤버 대응), 안 6(판 사이 이름 바뀜) |

### 4.3 가져오지 않는 것과 이유
- **LLM 으로 패치 옮기기**: 도미니코 방향(프로그램이 채운다)과 다르고, 공개 연구에서도 자바 성공률 40~46% 수준(4.2). 사람 검토 비용이 그대로 남는다.
- **여러 판 동시 지원 전처리기**(Stonecutter·ReplayMod): 버전업 계획 A9(서버는 늘 한 판)와 충돌. 조건 분기 코드가 늘어 성능·가독성이 나빠진다.
- **바닐라 위 Mixin**(Sponge): 바닐라 코드를 실어야 한다(EULA·통째 이식 금지 원칙).
- **mcmeta·minecraft-data 같은 남의 데이터 저장소에 의존**: 우리는 이미 공식 jar 에서 직접 뽑는다(V-05). 남의 가공본은 정답 기준이 아니다.

### 5.1 [1위] 차분 정답기 자동화 — T-235 실현 + 입력 자동 생성

**무엇**: 이름 푼 바닐라 jar 를 시험 안의 격리 로더에 올리고, shim 의 연결된 멤버마다 같은 입력을 양쪽에 넣어 결과(반환값·예외 종류·바뀐 인자 상태)를 견준다. 11-20 설계 5.2·5.5 와 시제품(`DiffHarness`, `Mth` 200만 호출 차이 0)을 정식으로 만들고, 거기에 **입력 생성을 타입별로 한 번만 쓰면 모든 멤버에 시험이 생기는** 구조를 더한다.

- 입력 생성기: 원시값(경계값 포함), `BlockPos`·`Vec3`·`AABB`·`Direction`·`ChunkPos`, NBT 트리, `Component`, 블록 상태(전부 26,684 — 데이터에서), 아이템 스택(기본 구성 요소 + 무작위 조합), 레지스트리 키. jqwik 처럼 고정 시드 + 줄이기(shrinking: 실패한 입력을 가장 작은 꼴로 줄여 보고).
- 비교 방법: 바닐라 객체와 shim 객체는 다른 클래스라 직접 `equals` 를 못 한다 → **중립 표현으로 내려서**(NBT 는 바이트, 좌표는 숫자, 블록 상태는 이름+속성 글) 견준다. 이 "내리기"도 타입별 한 번.
- 시험 대상 목록은 **잠금 파일(`shim-1.21.1.lock`)에서 자동으로** 뽑는다. 검사 종류가 `pure`·`read=any` 인 연결은 전부 대상, 정답기 없이 남은 것은 `build/shim-proof-report.md` 의 "증명 없음" 목록(설계 5.5 그대로).
- 2단계: 코덱(NBT·구성 요소·패킷 버퍼)은 JQF 식 적용 범위 유도 입력으로(구조가 깊어 무작위만으로는 안쪽까지 못 감).
- 버전업 때: 새 판 jar 로 같은 시험을 다시 돌리면 PR #548 이 말한 "이름 같고 흐름 바뀐 shim 멤버 75개"가 **자동으로 판정**된다.

**왜 1위**: 2위(추론기)가 "후보를 만들고 시험으로 거른다"는 구조라 정답기가 먼저 있어야 한다. 또 지금 손 시간의 큰 덩어리인 "바닐라 값 시험"을 없앤다. 결과가 바뀌지 않는 시험 일이라 위험이 낮다.

### 5.2 [2위] 연결 자동 추론기 — 생성-검증

**무엇**: `compat gaps`(T-233)·표본 순위(T-234)에 나온 "없는 기호"마다 프로그램이 **명세 줄 후보**를 만들고, 5.1 정답기(또는 기존 장면 시험)를 통과한 후보만 명세에 써 넣는다. 사람은 "후보가 없거나 다 떨어진 것"(지금의 설계 필요 17% + 다리)만 본다.

후보를 만드는 규칙(위에서부터 시도, 모두 기계적):
1. **상위·형제에 이미 있는 연결**: 같은 이름·서술자가 상위 클래스나 같은 인터페이스를 구현한 형제에 이어져 있으면 그대로(`@each` 꼴). 5c 처럼 "자동 연결 가능"으로 분류됐던 대부분.
2. **바닐라 안의 별칭**: 본문 지문표(PR #548 `BodyTable`)로 바닐라에서 몸통 모양이 같은 멤버(예: 같은 필드를 돌려주는 두 이름)를 찾아 `this.다른이름` 별칭 줄로.
3. **다리 메서드 형식 맞추기**: 핵심 층 다리(`ChunkInternals`·`EntityOps` 등)의 공개 메서드 중 (이름 비슷 + 인자·반환 형식이 "형식 대응 표"로 바꿔 맞는 것). 형식 대응 표 = `BlockPos ↔ long`·`BlockState ↔ 상태 번호` 같은 몇십 줄(사람이 한 번 씀, 판과 무관).
4. **멤버 대응표**(5.4 의 산출물): 그 바닐라 멤버를 이식한 Furnace 메서드가 있고 다리로 닿으면 그 다리.
5. **데이터 상수**: 레지스트리·종류 표에서 값이 나오는 필드(T-230 범위)는 생성으로.

채택 규칙:
- 검사 종류(`pure`/`read=any`/`read=snapshot`/`read=owner`/`write`)는 **다리 쪽에 미리 적힌 종류를 따라간다**(다리 메서드에 애노테이션 하나: 이 다리는 어느 스레드에서 불러도 되나). 그래서 추론기가 소유 규칙을 짐작하지 않는다.
- `pure`·읽기 연결: 정답기 통과면 자동 채택.
- 쓰기 연결(`write`): 후보는 만들되 **독립 검토 유지**(11-23 결정의 "설계 코드는 검토 유지"와 같은 선). 장면 차분기(5.5)가 생기면 그 시험 통과로 검토를 줄일지 다시 정한다.
- 후보가 여럿 통과하면 채택하지 않고 "모호함" 목록으로(조용히 엉뚱한 것에 잇지 않는다는 `SpigotMappings` 원칙).

출력: 명세 파일 diff + `shimLock` 재실행 + 증명 보고. 한 번 돌리면 PR 하나(생성기 PR → 11-23 결정대로 자동 대조 통과면 검토 생략, 쓰기 줄이 섞였으면 그 줄만 검토).

**효과 어림(가정)**: 2.1 표 기준 108기호 손 136분 중 기계적 90기호 몫(약 90분)의 대부분과 값 시험 작성이 빠진다 → 손 시간 약 65%↓(5.1 과 합쳐). 벽시계는 PR 왕복이 묶음마다 하나로 줄어 100기호당 약 3시간 → 약 1.2시간. 설계 필요 17% 는 그대로 사람 몫.

- 진행 중 스레드와 겹침: "shim 측정·남은 구멍 나누기" 스레드의 결과(남은 기호 목록)가 2b 의 입력이다. "엔티티 사슬 명세 이전"이 끝난 뒤 엔티티 쪽 후보가 쓸모 있어진다. 같은 명세 파일을 동시에 고치지 않도록 추론기 실행은 이전 스레드 병합 뒤에.

### 5.3 [3위] 패킷 코덱 추출기 — Burger 식

**무엇**: `vanilla-extract` 에 `-Pmode=packet-layout` 도구를 더한다. 패킷 클래스의 코덱 정의(정적 초기화의 `StreamCodec.composite` 인자 목록, 또는 `Packet.codec` 이 가리키는 쓰기 메서드의 버퍼 호출 순서)를 바이트코드로 따라가 **와이어 모양(필드 순서·코덱 종류)** 을 뽑는다. 분기·조건 필드가 있으면 `custom` 으로 표시하고 멈춘다.

- 출력은 캐시(Mojang 이름이 든 전체), 저장소에는 지금 스키마 형식(Furnace 가 쓴 중립 형식)과 같은 꼴로 **비교 결과만**. 처음에는 손 스키마 `protocol-767.schema` 와 대조해 도구를 믿을 수 있는지 확인한다(다르면 둘 중 하나가 틀린 것 — 손 스키마 버그를 찾을 수도 있음).
- 버전업 때: 두 판의 와이어 모양 차이가 곧 "패킷 형식 바뀜" 목록이다. PR #548 의 "선언이 바뀐 패킷 클래스 36개" 중 실제 와이어가 바뀐 것만 남는다. 분기 없는 것(2.3 의 171개 꼴)은 스키마를 자동 갱신하고, 서버 범용 코덱·shim 패킷 생성기가 그걸 그대로 쓴다.
- 손으로 남는 것: 분기 있는 14개 + 그 밖 9개, 그리고 **의미**(언제 무엇을 보내나 — 이동·회전 개편 같은 것)는 여전히 사람.

**효과 어림(가정)**: U-04 현실 24h 중 "새·바뀐 패킷의 필드 맞추기"를 기계가 → 약 15h. 서버 쪽 패킷 인코더를 스키마에서 생성하는 정도에 따라 더 줄 수 있음(그 생성은 이 과제 범위 밖, 판단은 착수 뒤).

**계획**: 3a 추출기(M, Sonnet high) → 3b 손 스키마 대조·차이 기록(S, Sonnet medium) → 3c 판 차이 보고에 붙이기(S, Haiku medium). 다른 안과 파일이 안 겹쳐 **지금 바로 나란히** 가능.

### 5.4 [4위] 멤버 단위 대응표 + 바뀐 조각 보기

**무엇**: 두 도구.
- **4a 멤버 대응표(Matcher 식)**: `@VanillaPort` 로 이미 짝지은 클래스 쌍(901곳) 안에서, Furnace 메서드와 바닐라 메서드를 **바이트코드 특징**으로 짝짓는다. 특징: 쓰는 상수(실수·정수·문자열), 부르는 대상의 대응(이미 짝지은 것), 인자 수·형식 대응, 분기 구조, 난수 호출 수(포팅은 난수 순서까지 같으므로 강한 신호). 점수 높은 짝만 표에, 애매하면 비움. 표는 Furnace 쪽 이름 + 바닐라 쪽 **지문**만 커밋(11-20 원칙 "커밋 기준선엔 Mojang 이름 원문 금지").
- **4b 바뀐 조각 보기**: 흐름 변경 후보(PR #548 의 1,727)마다 두 판 바닐라 메서드를 개발자 컴퓨터에서만 풀어(디컴파일, 캐시 전용) **정규화**(지역 변수 이름·람다 번호·이름 바뀜 제거) 뒤 줄 단위 차이를 만든다. 차이를 자동 분류: 상수만 / 이름만 / 순서만 / 진짜 흐름. 4a 로 이은 Furnace 메서드 위치(파일:줄)를 옆에 붙인다.

**왜**: U-05 스레드가 하는 일의 앞부분 — "이 클래스의 무엇이 바뀌었나 찾기·읽기" — 를 없앤다. 오탐(진짜 흐름 변화가 아닌 후보)도 정규화가 걸러낸다. 지금은 "흐름 변경 1,727 중 실제 비율 모름" 이라 U-05 가 오탐을 손으로 거른다.

**효과 어림(가정)**: U-05 현실 94h 의 약 20~30%(찾기·읽기·오탐 거르기) → 약 72h. 엔티티(32h, 임계 경로)가 가장 이득이 크다 — 단 **엔티티 `@VanillaPort` 표시(V-06 엔티티, PR #548 선행)가 먼저** 있어야 한다.

**위험·경계**: 4b 는 디컴파일한 바닐라 코드를 화면에 보여 준다. 지금도 포팅 스레드는 바닐라 코드를 읽고 옮긴다(규칙: "디컴파일 소스는 커밋하지 않는다") — 4b 는 그걸 정리해 보여 줄 뿐 저장소·공유 폴더에는 아무것도 남기지 않는다. 그래도 도구로 굳히는 것이라 결정 F2 로 확인받는다.

**계획**: 4a(M, Opus medium — 짝짓기 점수 설계) · 4b(M, Sonnet high) 나란히. 선행 V-04·V-06 엔티티(PR #548 6장, Sonnet medium)를 먼저 또는 같이.

### 5.5 [5위] 바닐라 장면 차분기 — 서버 동작을 클라우드에서 정답과 견주기

**무엇**: 같은 "장면"(시드·데이터팩·명령 목록·봇 행동)을 **바닐라 서버와 Furnace 에서 돌려 결과 상태를 견주는** 하나의 틀. `parity-audit` 의 `RunVanilla`(바닐라를 직접 띄움)와 봇 시험을 합친 것이다.

- 결정성: `/tick freeze` + `/tick step N` 으로 틱을 맞추고, 장면은 `NoAI`·고정 위치 소환처럼 정해진 것부터. 견주는 것: 영역 `.mca`(블록·블록 엔티티), 엔티티 NBT(`/data get`), 봇이 받은 패킷 흐름(종류·순서·주요 필드), 명령 응답.
- 잡음 거르기(Diffy 식): 바닐라를 두 번 돌려 서로 다른 칸은 잡음으로 빼고 Furnace 와 견준다(`parity-audit` 이 월드젠에서 이미 하는 방식).
- 장면 묶음: 지금 PR 마다 따로 쓴 봇 스크립트 약 40개(`tools/bot-test/pr*.js` 등)를 장면 파일로 옮겨 **회귀 시험**이 되게 한다. 버전업 때는 새 판 바닐라로 같은 장면을 다시 돌리면 "바닐라 동작이 바뀐 장면" 목록이 자동으로 나오고, Furnace 가 따라가야 할 것이 장면 단위로 보인다.
- 바닐라 1.21.1 에는 게임 시험 틀(`net.minecraft.gametest.framework`)이 들어 있다. 이를 장면 형식으로 쓸 수 있는지는 착수 때 확인(가정 — 1.21.1 서버에서 바로 켜지는지 모름). 안 되면 명령·봇으로.

**효과 어림(가정)**: 재작업(현실 2배의 원인)을 홉 중간에 잡는다 → U-05 재작업 약 10h, U-08·U-09 PC 대기 약 3h ↓. 1.21.1 에서도 동작 parity 회귀를 잡는 이득이 있다.

**위험**: Furnace 는 구역별 멀티스레드라 같은 틱 안 처리 순서가 바닐라와 다를 수 있다 — 관측 결과(틱 끝 상태)만 견주고 중간 순서는 보지 않는다. 바닐라 서버를 CI 에서 돌리려면 EULA 동의(`eula=true`)를 그 기계에서 하게 된다 → 결정 F3.

**계획**: 5a 장면 형식·실행기(바닐라·Furnace 둘 다 띄우기, 틱 맞추기, 상태 뽑기)(M~L, Sonnet high) → 5b 비교·잡음 거르기·보고(M, Sonnet medium) → 5c 기존 봇 스크립트 옮기기(M, Haiku medium, 나눠서 병렬 가능). 클라우드에서 바닐라 서버가 뜨는지는 PR #548 이 데이터 생성기 실행으로 확인함(서버 자체 기동은 착수 때 확인 — 가정).

### 5.6 [덤] 표류 보고에 이름 바뀜 자동 판정 — T-236 확장

T-236(판 사이 표류 보고)을 만들 때 처음부터 넣을 것:
- 사라진 멤버와 새 멤버가 **본문 지문(모양 해시)이 같고** 같은 클래스(또는 같은 위치의 상위)에 하나씩만 있으면 "이름만 바뀜"으로 자동 판정, 명세·손 조각·시험의 이름을 기계가 고쳐 쓴다(OpenRewrite `ChangeMethodName`·`ChangeType` 과 같은 일을 작은 자체 도구로). 서술자만 바뀐 것은 형식 대응 표(5.2 의 2a)로 해결되면 자동.
- 지문이 다르거나 후보가 여럿이면 지금 설계대로 제안만(조용히 엉뚱한 것에 잇지 않음).
- 효과 어림: PR #548 의 shim 190줄(서술자 64 + 사라짐 126) 중 상당수가 이름 바뀜·패킷 생성자 꼴이라 U-07 20h → 약 16h(가정). S~M, Sonnet medium.

## 9. 재현 (2.3 패킷 표)

```
./gradlew -PskipOracle=true :vanilla-extract:run -Pmc=1.21.1 -Pmode=sig-table     # 캐시에 server.jar·server_mappings.txt
cd <빈 작업 폴더>
unzip -q ~/.cache/furnace-vanilla-extract/1.21.1/server.jar 'META-INF/versions/*'
mkdir x && (cd x && unzip -q ../META-INF/versions/1.21.1/server-1.21.1.jar)
M=~/.cache/furnace-vanilla-extract/1.21.1/server_mappings.txt
# 패킷 클래스와 그 난독 이름
grep -E "^net\.minecraft\.network\.protocol\.[a-z.]+\.(Clientbound|Serverbound)[A-Za-z]*Packet(\$[A-Za-z]+)? -> " $M | sed 's/:$//' | awk '{print $1, $3}' > pk.txt
# StreamCodec·Packet·FriendlyByteBuf 의 난독 이름은 대응표에서(1.21.1: yx, zg, vw·wk)
# 각 클래스의 정적 초기화(javap -c -p)에서 composite(yx.a:(Lyx;Ljava/util/function/Function;…)) / unit(yx.a:(Ljava/lang/Object;)) / Packet.codec(zg.a) 호출을 세고,
# Packet.codec 인 것은 (vw|wk) 하나를 받는 void 메서드 몸통에 if*·goto·switch 가 있는지 본다.
```
결과(11-23): 194개 — composite 27, unit 9, `Packet.codec` 150(분기 없음 135·분기 있음 14·쓰기 메서드 못 찾음 1), 정적 초기화 없음 4, 그 밖 4. 이름이 든 목록은 캐시 밖에 남기지 않았다(작업 폴더는 지움).
