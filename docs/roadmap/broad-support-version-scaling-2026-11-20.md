# 넓게 지원하면서 버전업은 쉽게 — 설계 (2026-11-20)

기준 커밋 `dda0f603`(기준 브랜치 `claude/quirky-wright-lra834`). 앞선 계획 `version-upgrade-plan-2026-11-16.md`(V-01~V-09, 홉 틀 U-01~U-09)를 이어 쓴다. 그 계획이 "판 숫자·표를 한 곳에서 생성"을 끝냈다면(V-01·02·03·05·06·07·08 병합), 이 문서는 남은 큰 덩어리 — **플러그인이 부르는 마인크래프트 내부 이름(NMS) 호환 껍데기(shim)를 수천 개로 늘리면서도 판마다 손으로 다시 쓰지 않게 하는 구조** — 와, 같은 생각을 다른 영역(Bukkit·Paper API, 프로토콜, 데이터, 동작, 월드젠, 저장 형식)에 펼친 표를 다룬다.

구현은 하지 않았다. 대신 가능성을 실제로 확인했다(2장 숫자는 모두 이번에 돌린 결과다). 시제품은 공유 폴더 `furnace/shim-coverage-plan-2026-11-20/` 에 있고 저장소에는 넣지 않았다.

도미니코 결정이 필요한 것은 `docs/user-todo/entries/2026-11-20-shim-coverage-plan.md` 에 쉬운 말로 따로 적었다(이 문서 10장은 요약).

---

## 1. 결론 (먼저 읽을 것)

1. **"지원한다"와 "손으로 구현한다"를 떼어 놓는다.** 바닐라 1.21.1 서버의 Mojang 이름 클래스는 6,148개, 공개·보호 멤버는 52,612개다. 이걸 다 손으로 쓰면 판마다 멤버의 6~24% 를 다시 손봐야 한다. 그러나 이 멤버들은 성질이 다섯 가지로 갈리고(3장), 그중 셋은 **기계가 만들 수 있다**: ① 선언(이름·서명·상속 관계), ② 데이터에서 나오는 상수(블록·아이템·소리·레지스트리 키 같은 수천 개 필드), ③ 판 사이 차이 목록. 사람이 쓰는 것은 "Furnace 의 무엇에 잇는가"뿐이고, 그것도 **판과 무관한 핵심 층**에 한 번 쓴다.
2. **서명은 저장소가 아니라 빌드 때 개발자·CI 컴퓨터에서 만든다.** 이미 있는 `tools/vanilla-extract`(V-05)가 바닐라 jar 와 공식 대응표를 내려받아 이름을 풀어 둔다. 여기에 "서명표" 도구 하나를 더하면 된다 — 이번에 시제품으로 1.21.1·1.21.4·1.21.11·26.1 네 판 모두 뽑혔다(26.1 은 난독화가 없어 대응표 없이). 서명표는 커밋하지도, 서버 jar 에 싣지도 않는다.
3. **없는 것은 지금처럼 "부르는 그 자리에서 진짜와 같은 링크 오류"로 둔다.** Paper 식 "몸통이 던지는 빈 껍데기(Dummy)"는 쓰지 않는다 — 플러그인의 `catch (NoSuchMethodError)` 기능 감지를 깨기 때문이다(`NmsLinker`·`NmsTrap` 가 이미 이렇게 한다). 대신 **어느 덫이 몇 번, 어떤 플러그인에서 걸렸는지 세서** 채울 순서를 정한다.
4. **판을 올릴 때 일이 저절로 목록으로 나온다.** 새 판 서명표 × Furnace 연결 명세 → "이름·서명이 바뀐 연결 N개" 표가 빌드 실패 메시지로 나온다. 측정으로 보면 지금 shim 이 정확히 맞춘 멤버 9,331개 중 1.21.4 에서는 약 180개(1.9%), 26.1 까지는 약 710개(7.6%)만 손볼 대상이다.
5. **시험은 "바닐라 jar 를 정답기로" 자동화한다.** 서명 대조는 CI 관문으로, 값 클래스(좌표·수학·NBT 등)는 바닐라 클래스를 시험 안에서 이름 풀어 올려 같은 입력으로 결과를 견준다 — 이번 시제품에서 `Mth` 10개 함수 × 20만 번 = **200만 호출, 차이 0** 으로 돌아가는 것을 확인했다.
6. **성능은 손으로 쓴 shim 과 같다.** 생성물은 평범한 자바 코드(정적 위임 호출)라 JIT 가 인라인한다. 리플렉션·프록시·실행 중 표 조회는 쓰지 않는다. 소유 스레드 검사는 생성기가 모든 연결에 똑같이 넣어 빠뜨림이 사라진다(비용은 스레드 비교 한 번).
7. 이행은 6단계(8장), 새 과제 T-227~T-240. 첫 두 과제(서명표·서명 관문)는 결과가 안 바뀌는 도구 일이라 지금 FAWE 77개를 채우는 스레드와 나란히 할 수 있다.

### 2.3 판 사이 변화율 (같음 / 서술자 바뀜 / 사라짐·이름 바뀜)
| 비교 | 바닐라 전체 멤버 | shim 이 닿는 클래스의 멤버 | **shim 이 지금 정확히 맞춘 9,331개** |

- 플러그인이 실제 쓰는 멤버는 바닐라 평균보다 훨씬 덜 바뀐다. 손볼 양은 "판 하나에 수백 개"이지 "수천 개"가 아니다. 단 그 수백 개를 **사람이 찾게 두면** 시간이 다 거기 간다 → 4.5 의 표류 보고가 찾기를 0 으로 만든다.
- 바뀌는 모양은 대부분 기계적이다(26.1 기준 예): `ResourceLocation` → `Identifier` 이름 바뀜(그 타입을 받는 모든 서술자가 따라 바뀜), `SoundEvents.*` 필드 타입이 `SoundEvent` → `Holder$Reference`, `Mth.sin(F)F` → `(D)F`, `GameRules`·`DirectionProperty`·`CatVariant`·`WolfVariant` 등 클래스가 사라지거나 옮겨감. 1.21.1 shim 최상위 클래스 중 26.1 에서 사라지는 것은 12개.
- Paper API(`paper-api` jar): 1.21.1 → 1.21.11 에서 클래스 1,821 → 2,228(사라진 것 18), 멤버 24,818 → 30,469, **1.21.1 멤버의 98.9% 가 그대로**다. Bukkit·Paper API 는 "더하기만 하는" 표면이라 판 올리기 비용이 작고, 새로 생긴 것 목록만 자동으로 받으면 된다.

## 3. 핵심 생각 — 표면의 다섯 성질

| 성질 | 예 | 어떻게 지원하나 | 판 올릴 때 |
|---|---|---|---|
| **① 선언** — 클래스가 있고, 상속 관계·이름·서명이 바닐라와 같음 | `class CropBlock extends Block`, `ServerLevel implements WorldGenLevel` | **생성**(서명표). 손으로 쓰지 않는다 | 재생성 |
| **② 데이터 상수** — 데이터에서 값이 정해지는 필드·열거형 | `Blocks.WHEAT`(그 객체가 `CropBlock` 이어야 함), `Items.*`, `SoundEvents.*`, `Attributes.*`, `BuiltInRegistries.*`, `Registries.*` 키, `Direction`·`DyeColor` | **생성**(서명표 + 추출한 데이터 표 + 손으로 쓴 작은 핵심: `Holder`·레지스트리 구현) | 재생성 |
| **③ 값 계산** — 상태 없는 순수 계산 | `Mth`, `BlockPos`, `Vec3`, `AABB`, `ChunkPos`, NBT, `Component` | **손으로 한 번**(바닐라 동작을 보고 새로 씀 — 서버 포팅과 같은 방식). 정답은 차분 시험(5장)이 자동으로 지킨다 | 서명 바뀐 것만, 차분 시험이 알려 줌 |
| **④ 보기·다리** — Furnace 의 실제 월드·엔티티·아이템을 바닐라 모양으로 보여 주고 쓰기를 넘김 | `ServerLevel#getBlockState`, `Entity#getX`, `ItemStack#getCount`, `ServerPlayer#connection` | **연결 명세**(무엇을 무엇에 잇는지 한 줄) + 생성기가 위임 몸통·소유 스레드 검사를 만든다. 복잡한 것만 손 오버라이드 | 명세의 대상 이름이 바뀐 것만 |
| **⑤ 상속 대상** — 플러그인이 하위 클래스를 만들고 서버가 그 가상 메서드를 불러 줘야 함 | 가짜 플레이어 `extends ServerPlayer`, 몹 `extends Zombie`(Citizens 264개) | **손 설계**(`@NmsInheritable` 규칙 #480). 생성기는 final·가상 여부만 바닐라와 맞춰 준다 | 손 |
| (밖) **의미가 충돌** — Furnace 멀티스레드 구조와 맞지 않음 | 틱 루프 내부, 단일 서버 스레드 가정 | 지금처럼 등급 C, 대체 API 안내 | — |

판단 기준: "플러그인이 쓰는가"와 "어느 성질인가" 두 축. 쓰지 않는 클래스(데이터 고치기 333, 몹 AI 내부 333 등)는 선언도 만들지 않는다 — 4.4 의 이유.

## 4. 구조

### 4.1 세 층

```
 [판과 무관한 핵심 — 손, 한 번]           [판별 어댑터 — 거의 전부 생성]              [자동 생성·대조 — 기계]
  furnace-server (포팅된 동작)              build/generated/nms-shims/<판>/            tools/vanilla-extract
  furnace-api internal 다리(ChunkInternals…)  ← 서명표(판) + 연결 명세 + 이름 바꿈 규칙   ├ sig-table   (서명표, 캐시)
  compat 연결 핵심 org.domi.furnace.compat.bind (개념 단위: EntityOps, LevelOps…)       ├ reports     (데이터 생성기 보고)
  ③ 값 클래스 몸통                          src/shims/<판>/ (판에만 있는 손 오버라이드, 보통 0~수십 개)  └ drift       (판 사이 차이 × 명세)
```

- **핵심 층**은 마인크래프트 판을 모른다. "엔티티를 지운다", "칸의 블록 상태 번호를 읽는다"처럼 Furnace 개념으로 쓴다. 이미 있는 `furnace-api` 의 internal 다리(`ChunkInternals` 등), `NmsOwner`, 보기 객체 규칙(N2b 의 안정 정체성)이 여기다.
- **판별 어댑터**는 그 판의 Mojang 이름·서명을 입은 얇은 껍데기다. 서버는 늘 한 판만 빌드하므로(버전업 계획 A9) 어댑터도 그 판 하나만 빌드한다. 판을 올리면 생성물은 다시 만들고, 손 오버라이드는 `src/shims/<새 판>/` 로 옮기며 필요 없어진 것은 지운다(두 판을 같이 두지 않는다 — AGENTS.md 규칙 1 의 뜻).
- **기계 층**은 V-05 `vanilla-extract` 를 키운다. 바닐라 jar·대응표·이름 푼 jar 는 이미 그 캐시에 있다.

### 4.2 서명표 (생성, 커밋 안 함)
- 입력: 이름 푼 바닐라 서버 jar(1.21.x) 또는 그대로의 jar(26.x). Paper·CraftBukkit 이 더한 멤버(`ServerLevel#captureBlockStates`·`paperConfig`, `CraftPlayer` 등)는 **Mojang 이름 Paper 서버 jar** 에서: `worldgen-oracle` 이 이미 쓰는 paperweight userdev 가 그 jar 를 만든다(Paper 저장소가 닿는 PC·CI 에서. 클라우드에서 막히면 그 칸만 "Paper 표 없음"으로 표시하고 바닐라 표로 진행 — 가정: CI 에서 닿는지 T-227 에서 확인).
- 내용: 클래스마다 접근 플래그·상위·인터페이스·제네릭 서명 문자열, 멤버마다 종류·접근·이름·서술자. **코드 속성(바이트코드 몸통)은 읽지 않는다** — 도구 구조상 몸통에 손이 닿지 않게 만든다(법적 경계, 6장).
- 출력 위치: `~/.cache/furnace-vanilla-extract/<판>/sig-table.tsv.gz`. Gradle 작업 입력으로만 쓰고 빌드 결과물·저장소에는 남기지 않는다.
- 시제품: `furnace/shim-coverage-plan-2026-11-20/sigtable.py.txt`(정식판은 V-05 모듈 안 Java 도구로 — 이름 풀기는 이미 `JarRemapper` 가 한다).

### 4.3 연결 명세와 생성기
지금도 같은 모양의 생성기가 있다: 패킷 스키마(`protocol-767.schema`, Furnace 가 쓴 중립 형식) → `PacketShimGenerator` → `build/generated` 의 패킷 shim + 손으로 쓴 덧붙임(`packet-shim-extras.txt` 의 `@@ <클래스>`). 이걸 모든 shim 으로 일반화한다.

명세 예시(`furnace-compat-paper/src/shimspec/entity.spec`, 커밋함 — Furnace 가 쓴 글):
```
# 클래스            보기 대상(핵심 층)                         소유 규칙
class net.minecraft.world.entity.Entity    view=EntityView   owner=entity-region
  getX          -> pos.x            read=snapshot          # 다른 스레드도 읽기 허용(공개 스냅샷)
  getUUID       -> uuid             read=any
  getId         -> networkId        read=any
  discard       -> EntityOps.discard                       # 주인 region 에서만, 아니면 NmsOwner 규칙
  setPos(DDD)   -> EntityOps.teleportLocal                 # 서술자는 겹치는 이름이 있을 때만 적는다
  save          -> @hand                                   # 손 오버라이드(src/shims/common/…)
```
- 이름만 적고 서술자는 서명표에서 채운다. 그래서 `ResourceLocation` → `Identifier` 같은 타입 이름 바뀜은 명세를 고치지 않아도 따라간다(판별 "이름 바꿈 규칙" 파일 한 줄이 핵심 층의 Java 타입과 이어 줌).
- 생성기가 만드는 것: 클래스 선언(서명표 그대로의 상위·인터페이스·final·레코드/열거형 여부), 명세에 있는 멤버만의 몸통(핵심 층으로 정적 호출 + 소유 규칙 검사), ② 데이터 상수 클래스 전체, 판 상수(`GameVersion`).
- 생성기가 **만들지 않는 것**: 명세에 없는 멤버. 그 멤버는 클래스 파일에 없으므로 `NmsSymbols` 가 "없음"으로 보고 `NmsLinker` 가 그 호출 자리를 덫으로 바꾼다(지금과 같은 실패 방식).
- 인터페이스를 선언했는데 그 추상 메서드 중 명세에 없는 것: 생성기가 몸통을 만들지 않고 클래스를 추상으로 만들 수는 없으므로(플러그인이 받는 객체는 구체 클래스), **`NmsSymbols` 가 "구현 없는 추상 메서드 = 없음"으로 판정하도록 한 줄 넓힌다**(덫이 걸림). 서명표에서 그 목록을 빌드 때 뽑아 색인에 넣는다 — 실행 중 계산 없음.
- 손 오버라이드: 지금처럼 Java 소스를 쓰되 클래스 머리(상속·필드 선언)는 생성기가 붙인다(패킷의 `@@` 덧붙임과 같은 "부분 클래스" 방식). 지금 손으로 쓴 shim 376+215 파일은 한 번에 옮기지 않고, 패키지 단위로 "생성 선언 + 손 몸통"으로 옮기며 **javap 비교로 바이트코드가 전과 같음**을 증명한다(V-01 의 `tools/ci/javap-same.sh` 재사용). 상속 관계를 바로잡는 패키지만 바이트코드가 달라지고, 그 차이는 2.2 표의 구멍을 메우는 것이다.

### 4.4 없는 것 다루기와 사용 계측
- 실패 방식은 그대로(H5 5장): 직접 호출은 그 자리에서 `NoSuchMethodError`·`NoSuchFieldError`·`NoClassDefFoundError` 의 하위 오류, 리플렉션은 진짜처럼 실패, 상속 거부는 정의 때.
- **빈 선언 클래스를 함부로 만들지 않는다.** 클래스만 있고 멤버가 없으면 `Class.forName("net.minecraft…")` 로 "Mojang 이름 Paper 인가"를 감지하는 플러그인이 Bukkit API 대체 경로 대신 NMS 경로로 들어갔다가 첫 멤버에서 실패한다(지금은 클래스가 없어 대체 경로로 간다). 그래서 선언만 있는 클래스는 ① `instanceof`·상속 관계에 필요한 것(예: `CropBlock`)과 ② 멤버를 실제로 채운 클래스의 상위 사슬에만 만든다. 표본 분석(T-234)이 플러그인의 `Class.forName` 문자열을 따로 세어 "감지 대상 클래스" 목록을 만들고, 그 클래스는 주요 멤버를 채운 뒤에만 연다.
- 계측(T-233): `NmsCompatReport`(로드 때 정적 참조)와 `NmsTrap`(실행 때 덫)이 이미 플러그인·대상별 첫 1회 경고를 남긴다. 여기에 **(플러그인, 심볼)별 횟수**를 더해 운영자가 `furnace compat gaps` 명령으로 표(tsv)를 내보내게 한다. 자동으로 밖에 보내지 않는다(결정 D2). 덫 경로만 세므로 정상 호출 비용은 0.
- 우선순위 점수 = (그 심볼을 부르는 표본 플러그인 수 × 플러그인 인기 가중치) + (운영자가 보내 준 덫 기록의 실제 호출 수). 표본은 다운로드 상위 플러그인 약 100개로 늘린다(지금 21개 — T-234). 결과는 `docs/feature-parity/compat-gaps-ranking-<날짜>.md` 로 정례 갱신.

### 4.5 판 올릴 때 흐름 (버전업 계획 U-07 을 이것으로 바꾼다)
1. U-02 가 새 판 서명표를 만든다(자동).
2. **표류 보고**(T-236): 명세의 각 연결을 새 서명표에서 찾는다 → `같음 / 서술자만 바뀜 / 이름 바뀜 후보 / 사라짐` 으로 분류해 `build/shim-drift-<n-1>-<n>.md` 를 낸다. "이름 바뀜 후보"는 같은 클래스에서 같은 서술자를 가진 새 이름, 또는 같은 위치(상위 사슬)의 비슷한 이름을 제안만 한다(자동으로 잇지 않음 — 조용히 엉뚱한 멤버로 잇지 않는다는 `SpigotMappings` 원칙과 같음).
3. 바뀐 것이 남아 있으면 **빌드가 실패**한다(목록이 곧 할 일). 사람은 그 목록만 고친다: 서술자만 바뀐 것은 대개 핵심 층 연결 그대로(타입 이름 바꿈 규칙 한 줄), 의미가 바뀐 것은 핵심 층 수정.
4. Paper API 쪽은 새 `paper-api` 서명표 대 Furnace 의 Bukkit 재구현 → "새로 생긴 메서드·클래스" 목록(구현 전에는 지금처럼 명확한 미지원). 2.3 에서 보듯 대부분 더하기다.
5. 차분 시험(5.2)을 새 판 jar 로 다시 돌려 ③ 값 클래스의 동작 변화를 잡는다(예: `Mth.sin` 이 double 을 받게 바뀌면 서명표가, 계산이 바뀌면 차분 시험이 잡는다).

## 5. 시험 전략

### 5.1 서명 관문 (CI light 단계, T-228)
- `furnace-compat-paper` 컴파일 결과 ↔ 서명표(바닐라 + Paper): 이름·서술자·static·final·접근 범위·상위·인터페이스·레코드/열거형 여부. 다르면 실패.
- **의도한 차이는 기준선 파일**(`furnace-compat-paper/src/test/resources/shim-signature-baseline.txt`)에 이유와 함께 한 줄씩. 예: `MinecraftServer 상위 = Object (바닐라 ReentrantBlockableEventLoop) — 단일 서버 스레드 가정을 주지 않기 위해, 등급 C`. 이 파일에는 이미 shim 에 있는 이름과 Furnace 가 쓴 이유만 들어가므로 새로운 Mojang 정보가 없다(6장).
- 처음 켤 때 기준선은 2.2 의 숫자(서술자 다름 185, 상속 다름 297)에서 시작해, 구멍인 것은 고치고 의도인 것만 남긴다. T-216 의 "전수 대조 정례화"가 이것으로 끝난다.
- 서명표가 필요하므로 CI 는 vanilla-extract 캐시를 Actions 캐시로 둔다(내려받기는 `piston-meta.mojang.com` 원 출처에서만). 받기에 실패하면 **건너뛰지 않고 실패**한다(규칙 5) — 다만 문서만 바뀐 PR 은 지금처럼 이 단계가 돌지 않는다.

### 5.2 차분 시험 — 바닐라를 정답기로 (T-235)
- 시험 안에서 이름 푼 바닐라 jar 를 격리 로더에 올리고, ③ 값 클래스(`Mth`·`BlockPos`·`Vec3`·`AABB`·`Direction`·NBT 직렬화·`Component` 직렬화·레지스트리 키 해석 등)를 **같은 입력으로 양쪽을 불러 결과를 견준다**. 입력은 고정 시드 난수 + 경계값(음수, 0, 큰 수, NaN, 정수 경계).
- 시제품(`DiffHarness.java.txt`)이 바로 이것이다. 바닐라 클래스가 정적 초기화에서 부트스트랩을 요구하는 것(`Blocks` 등)은 `vanilla-extract` 의 `Vanilla.java` 부트스트랩을 쓴다.
- 이 시험은 저장소에 바닐라 코드를 넣지 않는다. 시험 실행 때 캐시에서 읽을 뿐이다.
- ④ 보기·다리의 동작 정답은 지금처럼 Paper 실서버 대조(`tools/compat/fawe-paper/` 시나리오, 노트북·데스크탑)와 IdentityKit 장면 시험이 맡는다. 생성기로 옮긴 패키지는 "옮기기 전후 javap 같음"이 1차 증명이다.

### 5.3 데이터 생성기 보고서 대조 (T-238)
바닐라 `--reports` 결과로 Furnace 의 표가 바닐라와 같은지 판마다 자동으로 본다: `packets.json` ↔ 패킷 번호표(V-03 의 `PacketIds`), `commands.json` ↔ Furnace 명령 트리(바닐라 명령의 인자 구조), `registries.json` ↔ 레지스트리 내용·번호, `blocks.json` ↔ 블록 상태 번호. 일부는 이미 추출 도구가 이 보고서를 읽어 리소스를 만들지만, "Furnace 코드가 만든 결과"를 보고서와 직접 맞대는 시험은 명령 트리 등에 없다.

### 5.4 실제 플러그인
- 표본 100개 정적 분석(T-234) — 판마다·월마다 다시 돌려 "부르는 심볼 중 지원 비율"을 숫자로 남긴다. 목표 지표: **표본이 부르는 심볼의 95% 이상이 선언·연결됨, 나머지는 덫**.
- 실기동 시험은 지금 체계(H4 기동 시험, 봇 시험, FAWE-Paper 대조)를 그대로 쓴다.

|---|---|---|
| 호출 한 번 더(껍데기 → 핵심 층) | 생성 몸통은 `invokestatic` 한 번. 핵심 층 메서드가 작으면 JIT 가 인라인해 손으로 쓴 shim 과 같은 기계어가 된다. **리플렉션·`MethodHandle`·동적 프록시·실행 중 이름 조회는 생성물에 쓰지 않는다**(생성기 규칙, 시험으로 금지 — 생성 소스에 `java.lang.reflect`·`invokedynamic` 이 없음을 단언) | 옮긴 패키지마다 javap 전후 비교(같거나 정적 호출 한 겹), `NmsChunkReadBench` 류 기존 벤치 전후 3회 |
| 보기 객체 할당 | 지금 규칙 유지: Furnace 객체마다 보기 하나를 고정(정체성 안정 — N2b). 생성기는 보기 얻기를 `furnace-api` 의 칸(slot) 읽기 한 번으로 만든다 | 틱당 할당 계수(IdentityKit)가 전후 같음 |
| 클래스 수가 늘어 기동·메모리 증가 | JVM 은 쓰인 클래스만 올린다. 늘어나는 것은 jar 크기(생성 클래스 수천 개 — 수 MB 추정, 가정)와 `NmsSymbols` 색인. 색인은 빌드 때 미리 만든 이진 표로 바꿔 플러그인 로드 때 클래스 파일을 읽지 않게 한다(지금보다 빨라짐) | 기동 시간·플러그인 로드 시간 전후, jar 크기 |
| 소유 스레드 위반 | 생성기가 명세의 `owner=`·`read=` 에 따라 **모든 연결에 같은 검사**를 넣는다: 주인 스레드면 통과(스레드 비교 한 번), 공개 스냅샷 읽기는 그대로, 아니면 `NmsOwner` 규칙(틱 스레드 아니면 주인에게 부탁, 다른 region·전역 스레드면 `ThreadOwnershipException`). 손으로 쓸 때 생기던 "검사 빠뜨림"이 구조적으로 사라진다 | 명세의 모든 쓰기 연결에 대해 "다른 region 스레드에서 부르면 던진다"는 생성 시험을 기계적으로 만든다 |
| 덫 경로 | 정상 경로 비용 0(덫은 없는 심볼 자리에만 있다). 계측 횟수 세기는 덫 안에서만 | — |
