# 깃 태그와 버전 규칙 (2026-11-16)

목적: 마크 판(1.21.1 → 1.21.2 → … → 26.x)이 바뀌어도, "어느 판의 어느 시점 코드인가"를 커밋 이름 대신 **태그**로 말할 수 있게 한다. 보고서·병합 기록·공유 폴더 jar 는 이 이름으로 가리킨다. 계획 배경: `docs/roadmap/version-upgrade-plan-2026-11-16.md`(1-4 홉 사이 브랜치 규칙).

도구: `tools/release/furnace-tag.sh`(이름 검사·다음 이름·태그 만들기). 형식은 `.github/workflows/tag-check.yml` 이 태그가 올라올 때 다시 검사한다.

## 1. 네 가지 태그

모두 **주석 태그**(`git tag -a`)이고, **한 번 만든 태그는 옮기거나 지우지 않는다**(잘못 만들었으면 새 이름으로 다시 찍고 문서에 적는다). `<MC>` 는 마크 판 그대로(`1.21.1`, `1.21.11`, `26.1`).

| 종류 | 이름 | 뜻 | 언제·누가 | 어느 브랜치 |
|---|---|---|---|---|
| 릴리스 | `v<MC>-<X.Y.Z>` 또는 `v<MC>-<X.Y.Z>-rc.<N>` 예: `v1.21.1-0.1.0`, `v1.21.1-1.0.0-rc.1` | 사용자에게 내보내는 빌드 | 출시 판단은 **도미니코**. 코디네이터가 승인 뒤 찍는다 | `ver/<MC>`(없으면 기준 브랜치), 첫 `1.0.0` 은 main 반영 뒤 |
| 홉(포팅) | `port/<MC>` 예: `port/1.21.2` | "그 마크 판으로 옮기기 끝, U-09 통과" 시점 — 다음 홉의 출발점 | 홉의 마지막 PR 이 병합되고 기준 브랜치 전체 시험이 초록일 때 그 홉 담당 스레드가 찍는다 | 기준 브랜치 |
| 마일스톤 | `ms/<MC>/<슬러그>` 예: `ms/1.21.1/t141-api`, `ms/1.21.1/n2b-fawe` | 로드맵 항목 하나(T-141 API 묶음, N2b, 버전업 0단계 …)가 끝난 시점 | 항목의 마지막 PR 이 병합되고 기준 브랜치 전체 시험이 초록일 때 담당 스레드(없으면 코디네이터) | 기준 브랜치 |
| 병합 묶음 | `base/<MC>/<YYYYMMDD>-<N>` (날짜는 **UTC**, N 은 그날 1부터) 예: `base/1.21.1/20261116-1` | 기준 브랜치에서 전체 시험(6조각+light)이 초록인 시점의 체크포인트 — 되돌리기·이분 탐색·보고서 인용용 | 코디네이터가 병합 보고할 때 하루 1~3개 이하(PR 마다 찍지 않는다) | 기준 브랜치 |

- 슬러그는 소문자·숫자·하이픈만(`ms/1.21.1/T141` 은 거부). 한글·공백 금지.
- 태그 이름만으로 판이 갈린다: 같은 슬러그라도 `ms/1.21.1/…` 와 `ms/1.21.2/…` 는 다른 태그다.

## 2. Furnace 버전 숫자 `X.Y.Z`

- **마크 판과 따로 센다.** 판이 바뀌어도 이어서 올라간다(1.21.1 의 `0.4.0` 다음 1.21.2 첫 출시는 `0.5.0`). "Furnace 기능 수준"과 "맞는 마크 판"이 따로 읽힌다.
- **`0.x.y` = 아직 실서비스 전.** 서비스 가능 선언(도미니코)이 첫 `1.0.0` 이다.
- 올리는 기준: **Y(마이너)** — 사용자가 보는 기능·설정 키·호환 계층 동작이 늘거나 바뀜, 새 마크 판으로 옮김. **Z(패치)** — 버그 고침만(특히 `ver/<MC>` 에 들어가는 급한 고침). **X(메이저)** — 월드 저장·설정 파일·플러그인 API 가 옛 것과 안 맞게 바뀜(`docs/policy/api-stability.md` 와 함께 판단).
- 급한 고침: 이미 다음 판으로 간 뒤의 1.21.1 고침은 `ver/1.21.1` 에서만, 태그는 `v1.21.1-<해당 계열 X.Y.Z+1 패치>`. 기준 브랜치에는 같은 고침을 따로 병합(체리픽)한다.
- 시험판은 `-rc.N`. 최종 릴리스 전에만 쓴다. 베타·알파 접미사는 쓰지 않는다.

## 3. 빌드에 나타나는 모습 — 어긋나지 않게

- 빌드 버전은 가장 가까운 릴리스 태그(`v*`)에서 읽는다(루트 `build.gradle.kts` 의 `furnaceBuildVersion`): 태그 위 = `0.1.0`, 태그 뒤 n 커밋 = `0.1.0+14.gabc1234`, 릴리스 태그 없음 = `dev+abc1234`.
- 이 값이 서버 fatJar 의 `Implementation-Version` 이 되어 콘솔 첫 줄(`This server is running Furnace <버전> (Minecraft <MC>)`), `/version`, `getVersion()`(`git-Furnace-<버전> (MC: <MC>)`)에 나온다. 마크 판은 코드의 `minecraftVersion()`·상수가 따로 말하므로 버전 문자열에 `1.21.1` 을 섞지 않는다. 전에는 항상 `dev` 였다.
- 판이 바뀔 때(`gradle/minecraft.properties`, 계획 V-01) 마크 판이 한 곳에서 오므로, 릴리스 태그의 `<MC>` 가 그 값과 같은지는 릴리스 때 `tools/release/furnace-tag.sh create` 를 쓰기 전에 사람이 확인한다(V-01 이후 스크립트가 파일을 읽어 자동 대조하도록 확장).
- **jar 이름**: 빌드 산출물 `furnace-server.jar` 는 그대로(`archiveFileName` 고정). 이름은 올리는 쪽에서 붙인다 — 릴리스 자산 `furnace-server-<MC>-<X.Y.Z>.jar`(예: `furnace-server-1.21.1-0.1.0.jar`), 공유 폴더 개발 빌드는 지금처럼 `furnace-server-<커밋8자리>.jar`(그 커밋이 어느 태그 뒤인지는 `git describe --tags --match "base/*" <커밋>` 으로 찾는다).
- **Maven 좌표**(헤드리스 시험·플러그인용): 개발은 `1.21.1-SNAPSHOT` 그대로, 릴리스는 `-PfurnaceVersion=<MC>-<X.Y.Z>`(태그에서 `v` 뺀 것).

## 4. 태그 찍는 법

```
git fetch origin --tags
tools/release/furnace-tag.sh next-base 1.21.1          # 오늘의 다음 base 이름
tools/release/furnace-tag.sh create base/1.21.1/20261116-1 <커밋> -m "6조각+light 초록, PR #417 까지" --push
```
스크립트는 (1) 이름 형식, (2) 같은 이름이 없는지, (3) 커밋이 기준 브랜치·`ver/<MC>`(릴리스는 `main` 도)에 있는지를 검사한다. 푸시 전에 **그 커밋의 기준 브랜치 실행이 초록인지**(체크 `test`) 직접 확인한다 — base·port·ms 태그는 초록이 아닌 커밋에 찍지 않는다.

## 5. 스레드가 따를 것

- 병합 보고서에는 가능하면 가장 가까운 `base/…` 태그를 함께 적는다.
- 마일스톤을 끝내는 PR 의 스레드는 병합 뒤 `ms/…` 태그를 찍고 코디네이터에게 알린다(푸시 권한이 막히면 코디네이터가 찍는다).
- 릴리스(`v…`)는 **도미니코의 출시 지시 없이 찍지 않는다.** 일반 병합·마일스톤·홉 태그는 스레드가 알아서 한다.
- 태그를 걸었다는 이유로 브랜치 규칙(기준 브랜치 병합, main 은 FAWE PR 병합·실서버 시험 뒤 한 번에)이 바뀌지 않는다.

## 6. 브랜치 이름 (Paper 를 따름)
- 판마다 유지 브랜치 `ver/<MC>`(예: `ver/1.21.1`) — 그 판의 급한 고침·패치 릴리스용. 기준 브랜치가 다음 판으로 간 뒤에 갈라 둔다.
- 새 판 포팅 작업은 기준 브랜치 위에서 한다. 필요하면 `dev/<MC>` 를 쓴다. (Paper 도 태그는 판 이름 그대로, 브랜치는 `ver/<판>`·`dev/<판>` 을 쓴다. Furnace 는 자체 버전이 따로 있어 태그에는 `v<MC>-<X.Y.Z>` 를 쓴다.)
