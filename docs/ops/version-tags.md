# 깃 태그와 버전 규칙 (2026-11-16, 같은 날 단순화)

목적: 마크 판(1.21.1 → 1.21.2 → … → 26.x)이 바뀌어도 "어느 판의 어느 시점 코드인가"를 커밋 이름 대신 **태그**로 말한다. 보고서·병합 기록·공유 폴더 jar 는 이 이름으로 가리킨다. 계획 배경: `docs/roadmap/version-upgrade-plan-2026-11-16.md`(1-4).

**원칙(도미니코 11-16): 한 판에는 계속 갱신되는 하나의 빌드만 있다.** 한 판 안에서 여러 번 "출시"하지 않는다. 그래서 Furnace 자체 버전 번호(`0.1.0` 등)는 두지 않고, Paper 처럼 태그는 판 이름 그대로 쓴다.

도구: `tools/release/furnace-tag.sh`(이름 검사·다음 이름·태그 만들기). 태그가 올라오면 `.github/workflows/tag-check.yml` 이 이름 형식을 다시 검사한다.

## 1. 세 가지 태그

모두 **주석 태그**(`git tag -a`)이고 **한 번 만든 태그는 옮기거나 지우지 않는다**(잘못 만들었으면 새 이름으로 찍고 문서에 적는다). `<MC>` 는 마크 판 그대로(`1.21.1`, `1.21.11`, `26.1`).

| 종류 | 이름 | 뜻 | 언제·누가 | 어느 브랜치 |
|---|---|---|---|---|
| 판 | `<MC>` 예: `1.21.1`, `26.1` | **그 마크 판 빌드가 완성된 시점**(첫 서비스 가능 상태, 버전업이면 U-09 통과) — 한 판에 하나. 이후 그 판의 갱신은 병합 묶음 태그로 이어진다 | 완성 판단은 도미니코(서비스 선언·홉 통과). 코디네이터가 승인 뒤 찍는다 | 기준 브랜치(판이 끝나 `ver/<MC>` 가 갈라진 뒤에는 그 브랜치) |
| 마일스톤 | `ms/<MC>/<슬러그>` 예: `ms/1.21.1/t141-api` | 로드맵 항목 하나가 끝난 시점 | 항목의 마지막 PR 이 병합되고 기준 브랜치 전체 시험이 초록일 때 담당 스레드(없으면 코디네이터) | 기준 브랜치 |
| 병합 묶음 | `base/<MC>/<YYYYMMDD>-<N>` (날짜 **UTC**, N 은 그날 1부터) 예: `base/1.21.1/20261116-1` | 기준 브랜치에서 전체 시험(6조각+light)이 초록인 체크포인트 — 되돌리기·이분 탐색·보고서 인용용 | 코디네이터가 병합 보고할 때 하루 1~3개 이하(PR 마다 찍지 않는다) | 기준 브랜치 |

- 슬러그는 소문자·숫자·하이픈만(`ms/1.21.1/T141` 은 거부). 한글·공백 금지.
- 판 태그 앞에 `v` 를 붙이지 않는다(`1.21.1`).
- 전에 구상했던 `v<MC>-<X.Y.Z>` 릴리스 태그와 `port/<MC>` 는 쓰지 않는다 — 판 태그 하나가 그 역할을 한다(홉 통과 = 판 태그).

## 2. 빌드에 나타나는 모습

- 빌드 버전은 가장 가까운 판 태그에서 읽는다(루트 `build.gradle.kts` 의 `furnaceBuildVersion`): 태그 위 = `1.21.1`, 태그 뒤 n 커밋 = `1.21.1+14.gabc1234`, 판 태그 없음 = `dev+abc1234`. 지금은 판 태그가 아직 없으므로 `dev+해시` 로 나온다.
- 이 값이 서버 fatJar 의 `Implementation-Version` 이 되어 콘솔 첫 줄(`This server is running Furnace <버전> (Minecraft <MC>)`), `/version`, `getVersion()`(`git-Furnace-<버전> (MC: <MC>)`)에 나온다. 전에는 항상 `dev` 였다. 마크 판 자체는 코드의 `minecraftVersion()`·상수가 따로 말한다(V-01 이후 `gradle/minecraft.properties` 한 곳).
- 판 태그를 찍기 전에 사람이 그 이름이 `minecraftVersion()` 과 같은지 본다(V-01 이후 스크립트가 파일을 읽어 자동 대조하도록 확장).
- **jar 이름**: 빌드 산출물 `furnace-server.jar` 는 그대로(`archiveFileName` 고정). 올리는 쪽에서 이름을 붙인다 — 공유 폴더 개발 빌드는 지금처럼 `furnace-server-<커밋8자리>.jar`(어느 태그 뒤인지는 `git describe --tags <커밋>`), 판 완성 빌드는 `furnace-server-<MC>.jar`.
- **Maven 좌표**(헤드리스 시험·플러그인용): `1.21.1-SNAPSHOT` 그대로. 고정 좌표가 필요하면 `-PfurnaceVersion=<MC>` 로 낸다.

## 3. 태그 찍는 법

```
git fetch origin --tags
tools/release/furnace-tag.sh next-base 1.21.1          # 오늘의 다음 base 이름
tools/release/furnace-tag.sh create base/1.21.1/20261116-1 <커밋> -m "6조각+light 초록, PR #417 까지" --push
```
스크립트는 (1) 이름 형식, (2) 같은 이름이 없는지, (3) 커밋이 기준 브랜치·`ver/<MC>`(판 태그는 `main` 도)에 있는지를 검사한다. 푸시 전에 **그 커밋의 기준 브랜치 실행이 초록인지**(체크 `test`) 직접 확인한다 — 초록이 아닌 커밋에는 찍지 않는다.

## 4. 스레드가 따를 것

- 병합 보고서에는 가능하면 가장 가까운 `base/…` 태그를 함께 적는다.
- 마일스톤을 끝내는 PR 의 스레드는 병합 뒤 `ms/…` 태그를 찍고 코디네이터에게 알린다(푸시가 막히면 코디네이터/도미니코가 찍는다).
- 판 태그(`<MC>`)는 **도미니코의 판단 없이 찍지 않는다.** base·ms 태그는 스레드가 알아서.
- 태그가 있다고 브랜치 규칙(기준 브랜치 병합, main 은 FAWE PR 병합·실서버 시험 뒤 한 번에)이 바뀌지 않는다.

## 5. 브랜치 이름 (Paper 를 따름)
- 판마다 유지 브랜치 `ver/<MC>`(예: `ver/1.21.1`) — 그 판의 급한 고침용. 기준 브랜치가 다음 판으로 간 뒤에 갈라 둔다. 고침은 그 브랜치에 넣고 같은 고침을 기준 브랜치에도 따로 병합(체리픽)한다. 한 판 안의 갱신은 새 출시가 아니라 병합 묶음 태그로 남는다.
- 새 판 포팅 작업은 기준 브랜치 위에서 한다. 필요하면 `dev/<MC>`.
