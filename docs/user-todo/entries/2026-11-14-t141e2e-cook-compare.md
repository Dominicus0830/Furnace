# T-141 E2e 화로 굽기 완료 비교 — 결정할 것 (2026-11-14, PR #381 검토)

배경: Paper 는 굽기 속도 배율 API 를 넣으면서 화로의 "다 구웠나" 비교를 바닐라 `진행 == 총 시간` 에서 `진행 >= 총 시간` 으로 바꿨다.
PR #381 은 바닐라 동작을 지키려고 배율이 1.0 일 때는 바닐라 `==` 를 남겼다. 검토에서 이 때문에 화로가 멈추는 경우를 찾았고
(플러그인이 배율을 0.5 로 늦췄다가 1.0 으로 되돌리면 진행 300 > 총 시간 200 이 되어 영영 안 구워진다), 그 멈춤은 고쳤다
(배율이 바뀐 화로는 다음 굽기까지 `>` 도 완료로 본다). 남는 질문은 아래 하나다. **결정: B+ (11-15, 도미니코)** — 맨 아래.

### T141E2e-D1. 배율 1.0 인데 진행이 총 시간보다 큰 화로를 어떻게 할까 (추천: A — 검토자 추천)
이 상태는 바닐라에선 `/data` 로 CookTime 을 CookTimeTotal 보다 크게 적을 때만 생긴다. 플러그인에선 `setCookTime(getCookTime() + n)` 처럼
진행을 앞당기는 "빠른 화로" 플러그인이 만든다.
- **A(추천)**: Paper 처럼 늘 `>=` — 다음 틱에 굽는다. Paper 플러그인과 같다. 바닐라와 다른 곳은 `/data` 로 일부러 엇갈리게 적은 화로뿐(바닐라는 멈춘다).
- B(지금): 바닐라 `==` 를 지키고, 배율이 바뀐 화로만 `>` 도 허용(다음 굽기까지). `/data` 결과는 바닐라와 같지만, 진행을 앞당기는 플러그인 화로는 Paper 와 달리 멈춘다.

A 로 정하면 서버 FurnaceBlockEntity 의 비교 한 줄과 시험 하나(`vanillaOvershootAtOneStaysLikeVanilla`)를 바꾼다.

## 직접 확인하면 좋은 것
- 없음(서버 단위 시험으로 끝남).

## 결정: B+ (11-15, 도미니코)
서버 틱은 바닐라 `==` 그대로(배율이 바뀐 화로의 `>` 허용도 그대로). 호환 계층 `CraftFurnace#update` 가 적을 때 **진행 ≥ 총 시간이고 재료 칸에 아이템이 있으면
진행을 총 시간 − 1 로 적는다** — 다음 틱에 `==` 로 굽혀 Paper `>=` 와 같은 결과. 값이 NBT 에 남아 청크가 내려가도 안전하고, `/data`·일반 게임은 바닐라 그대로다.
배율을 1.0 으로 되돌리는 경우(setCookSpeedMultiplier → update)도 같은 쓰기 경로라 맞춰진다.
- 재료 칸이 비었으면 손대지 않는다(빈 화로 기본값 진행 0·총 0 에 -1 을 적지 않으려고. 재료를 넣으면 바닐라가 진행을 0 으로 되돌린다).
- 남는 Paper 와의 차이: ① update 직후 같은 틱에 상태를 새로 읽으면 플러그인이 적은 값이 아니라 총 시간 − 1 이다(그 상태 객체의 getCookTime 은
  적은 값 그대로지만 getSnapshotNBT 는 맞춘 값). ② 불 꺼진 화로에 진행을 크게 적으면 다시 불이 붙을 때 Paper 보다 2틱쯤 늦게 굽는다.
- 시험: 호환 `BukkitFurnaceSpeedEventTest.overshootIsWrittenAsTotalMinusOne`, 서버 `FurnaceCookSpeedMultiplierTest.compatClampedOvershootCooksNextTick`.
