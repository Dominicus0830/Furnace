# 호환 계층 아이템·인벤토리·블록·엔티티 (H3) — 2026-11-07

서버 쪽은 시험으로 확인(헤드리스 서버 위에서 소유 스레드·아닌 스레드, 접속 처리기 모양 키트 플러그인). 문서 `docs/feature-parity/compat-h3-2026-11-07.md`, `docs/api/compat-paper.md`. 직접 확인·결정할 것:

- **직접 확인(접속 시험):** 실제 클라이언트로 키트 플러그인 모양 jar(접속하면 이름·설명·마법을 단 아이템 지급)를 올려 아이템 이름·설명 줄이 Bukkit 에서와 같은 색·기울임으로 보이는지(설명 줄은 기본 보라 기울임, 이름은 기울임). Bukkit 에서 `§r` 를 앞에 붙이던 플러그인이 있다면 그 효과도.
- **직접 확인(Bukkit 원문 대조):** 이 컨테이너는 Bukkit·Paper 소스를 못 받아 아래는 기억 기준이다. 서버 jar 가 있으면 한 번 대조해 주세요: ① `Inventory#addItem` 이 빈 칸에 새로 넣을 때 아이템 종류 최대 스택(진주 16)으로 쪼개는가, 인벤토리 한도(64)로 쪼개는가(지금은 종류 최대). ② `ItemMeta#getDisplayName` 이 이름 없을 때 `null` 인가 `""` 인가(지금은 `null`). ③ `Entity#getNearbyEntities` 가 위치가 아니라 충돌 상자를 본다는 점(지금은 위치 기준).
- **결정:** `ItemStack#addEnchantment` 의 최대 레벨·적용 아이템 검사를 하려면 Furnace API 에 마법 부여 정의(최대 레벨·적용 아이템 태그)를 노출해야 합니다. 지금은 1~255 만 검사합니다. 노출할까요? 답이 없으면 지금처럼 둡니다(실제 아이템 결과는 바닐라 규칙에 어긋날 수 있는 레벨까지 허용).
- **결정:** 다른 스레드(접속 처리기·전역 스레드의 명령)가 플레이어 인벤토리에 쓰면 지금은 소유 스레드로 **예약**하고 읽을 때 겹쳐 보입니다(예약이 실제로 적용되기 전 몇 틱 동안 서버 안 다른 코드는 옛 내용을 봅니다). 대안: 전역 스레드를 잠깐 막고 결과를 기다리기(교착 위험이 커서 비추). 답이 없으면 예약 방식을 유지합니다.
- **결정:** 가상 인벤토리(`Bukkit.createInventory`)·`BlockState` 는 이번에 넣지 않았습니다(둘 다 클릭·열기 이벤트나 블록 엔티티 데이터가 같이 필요한 큰 묶음). 메뉴 플러그인을 많이 쓰시면 다음 묶음으로 올려 주세요. 답이 없으면 H4 의 실제 플러그인 시험 결과로 우선순위를 정합니다.
