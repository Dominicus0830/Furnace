## F1. 시험을 통과한 읽기 연결은 검토 생략 — 확정 A(11-23 도미니코)

- 쉬운 말: 지금 shim 을 채울 때 사람이 "이 바닐라 메서드는 Furnace 의 무엇에 이으면 되나"를 찾아 한 줄씩 적습니다. 지난 묶음 108개를 보니 84% 는 규칙만으로 찾을 수 있는 꼴이었습니다. 이걸 프로그램이 찾고, 같은 입력을 바닐라와 Furnace 양쪽에 넣어 결과가 같으면 채택하게 하려 합니다.
- 예: `Entity#getX` 처럼 값을 읽기만 하는 연결은 수천 개 입력으로 바닐라와 같은지 기계가 확인할 수 있습니다. 반면 블록을 놓거나 엔티티를 지우는 "쓰기" 연결은 스레드 소유 규칙이 걸려 있어 사람 눈이 필요합니다.
- 고를 것:
  - **A(추천). 읽기는 검토 생략, 쓰기는 검토 유지.** 11-23 에 정한 "생성기 PR 은 자동 대조 통과면 검토 생략"을 프로그램이 찾은 연결에도 넓히는 것입니다.
  - B. 전부 검토. 안전하지만 사람 검토가 병목으로 남습니다.
  - C. 전부 생략. 가장 빠르지만 쓰기 연결의 스레드 소유 실수를 놓칠 수 있습니다.
- 안 하면(B): shim 채우기가 지금보다 빨라지긴 하지만(찾기는 기계가) 묶음마다 검토 왕복이 남아 벽시계 절감이 절반쯤으로 줄어듭니다.

## F2. 바뀐 줄 보기 도구 — 확정 A(11-23 도미니코)

- 쉬운 말: 버전업 때 "이 메서드 속이 바뀌었다"는 목록은 이미 나옵니다(PR #548, 1.21.2 는 1,727개). 그런데 실제로 무엇이 바뀌었는지는 스레드가 바닐라 코드를 직접 풀어 읽어야 합니다. 이 도구는 두 판의 그 메서드를 개발 컴퓨터에서만 풀어 **바뀐 줄만** 보여 주고, 상수만 바뀐 것·이름만 바뀐 것·진짜 흐름이 바뀐 것을 나눠 주고, 이식한 Furnace 파일 위치를 옆에 붙입니다.
- 지금 규칙("디컴파일 소스는 커밋하지 않는다")은 그대로 지킵니다. 풀어 본 내용은 화면과 캐시에만 있고 저장소·공유 폴더·서버 파일에는 들어가지 않습니다. 지금도 포팅 스레드가 하는 일을 정리해 줄 뿐이라 법적 위치는 바뀌지 않는다고 봅니다(법률 자문 아님). 그래도 "도구로 굳히는" 것이라 확인을 받습니다.
- 고를 것:
  - **A(추천). 만든다.** 버전업의 가장 큰 덩어리(동작 옮기기, 현실 약 94시간)에서 약 20~30% 를 줄입니다(가정).
  - B. 만들지 않는다. 목록(어느 메서드)까지만 기계가, 무엇이 바뀌었는지는 사람이.
- 안 하면(B): 엔티티처럼 바뀐 메서드가 많은 곳(1.21.2 에서 537개)을 스레드가 하나씩 열어 봐야 하고, 오탐도 손으로 거릅니다.

## F3. 바닐라 장면 시험을 CI 에서도 — 확정 A(11-23 도미니코)

- 쉬운 말: "바닐라 서버와 Furnace 에서 같은 장면(예: 좀비 소환 → 10틱 진행 → 상태 비교)을 돌려 결과를 견주는" 시험 틀을 만들려 합니다. 지금 PR 마다 따로 쓴 봇 스크립트 약 40개를 이 틀로 모으면 그대로 회귀 시험이 됩니다. 바닐라 서버를 띄우려면 그 기계에서 `eula.txt` 에 동의(`eula=true`)해야 합니다. 개발 컴퓨터에서는 이미 `parity-audit` 도구가 이렇게 하고 있습니다.
- 고를 것:
  - **A(추천). CI(GitHub Actions)에서도 돌린다.** 바닐라 jar 는 공식 주소에서만 받고 CI 캐시에만 둡니다. 틀린 곳이 PR 단계에서 드러나 홉 끝 PC 시험에서의 재작업이 줄어듭니다.
  - B. 개발 컴퓨터(클라우드 스레드·도미니코 PC)에서만. CI 에서는 안 돕니다.
- 안 하면(B): 장면 시험이 사람이 돌릴 때만 돌아서, 회귀를 놓치는 기간이 생깁니다.
