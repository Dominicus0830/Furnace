## D1. 연결 파일의 이름 — 추천 A

- 쉬운 말: 연결 파일은 "이 내부 멤버는 Furnace 의 이 기능으로 동작한다"를 한 줄씩 적은 파일입니다. 지금 사람이 쓰는 명세 파일(`src/shimspec/*.spec`)도 같은 이름을 씁니다.
- 예: `Zombie` 의 `isBaby()` 줄 → "엔티티 데이터의 아기 칸을 읽는다".
- 검토 반영(11-23): 그대로 쓰는 것은 플러그인이 볼 수 있는 공개·보호 이름뿐이고, 바닐라 비공개 이름(예: 엔티티 데이터 칸 상수)은 엔티티 번호표처럼 지문으로 적는다. 검사 장치가 평문 비공개 이름을 막는다.
- 고를 것: **A(추천)** 공개 이름 그대로 — 검토 가능, 명세와 같은 규칙. B 이름 해시 — 커밋에 이름이 안 남지만 검토가 불가능해 쓰기 줄 검토 원칙(F1)을 지킬 수 없습니다.

## D2. 관용구로 이은 쓰기 줄 — A 확정(도미니코, 11-24 01:14 KST)

- 쉬운 말: 바닐라에는 "엔티티 데이터 칸 하나를 바꾼다" 같은 똑같은 모양의 몸통이 수백 번 나옵니다. Furnace 쪽 구현을 한 번 쓰고(관용구) 독립 검토를 받으면, 어느 칸인지만 다른 줄들은 기계가 붙이고 바닐라 대조(월드 밖 엔티티로 부른 뒤 상태 비교)가 통과하면 검토 없이 넣습니다.
- 결정 F1(11-23)은 "시험 통과한 읽기 연결만 검토 생략, 쓰기는 유지"였습니다. 이 안은 쓰기도 **관용구 구현 단위로 한 번** 검토하자는 것이라 F1 을 조금 넓힙니다.
- 확정 내용: 같은 모양으로 반복되는 연결 줄(관용구 적용)은 자동 바닐라 대조를 통과하면 줄마다 검토하지 않는다. 관용구 구현 자체(손 코드)와 추론기·정답기 도구 변경은 지금처럼 독립 검토.
- 독립 검토가 권한 조건(설계 6장): 관용구 PR 에 월드 안 경로 시험, 멤버마다 대조가 실제로 차이를 가려내는지 확인, 소리·이벤트 같은 부수효과 있는 멤버 제외, Bukkit 메서드로 잇는 쓰기 제외, 묶음 PR 마다 무작위 표본(10줄 또는 5%) 확인.
- 안 했다면: 엔티티 데이터 쓰기 147줄·블록 상태 바꾸기 수십 줄을 줄마다 검토 — 영역 스레드 시간이 그만큼 늘어납니다.

## D3. 기대치 — 알림

- 측정(설계 2장): 플러그인이 부를 수 있는 동작 없는 내부 메서드 약 31,000개 가운데 바닐라 몸통이 "값만으로 정해지는" 것과 자주 반복되는 모양은 20% 안팎이고, 나머지는 진짜 계산이라 Furnace 의 해당 기능에 손으로 다리를 놓아야 합니다(바닐라 코드를 옮겨 오는 것은 금지).
- 도구는 그 나머지에 대해서도 "서버의 어느 메서드가 이미 같은 일을 하는지"를 찾아 줍니다(약 1만 개가 Furnace 가 이미 이식한 클래스 위에 있음).
