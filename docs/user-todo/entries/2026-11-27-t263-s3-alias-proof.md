# 연결 추론기(T-263) S3 — "다른 메서드를 그대로 부르기만 하는" 메서드(별칭)를 무엇으로 증명할까 — 2026-11-27

근거: 설계 `docs/roadmap/link-inferrer-t263-2026-11-23.md` 3.2 G3·3.4, 도구 `LinkInfer.alias`.

## 무엇인가

바닐라에는 몸통이 "같은 클래스(또는 부모)의 다른 메서드를 같은 인자로 부르고 그 값을 그대로 돌려줌" 한 줄뿐인 메서드가 있다. 예:
- `lerpTargetX()` → `return this.getX();`
- `getCommandSenderWorld()` → `return this.level();`
- `isVisuallySwimming()` → `return this.isSwimming();`

Furnace 에서 `getX()`·`level()`·`isSwimming()` 은 이미 사람이 만들고 검토한 진짜 몸통이 있다. 그런데 `lerpTargetX()` 같은 "부르기만 하는 쪽"은 아직 던지는 껍데기라, 플러그인이 부르면 오류가 난다.
도구가 지금 찾은 이런 후보는 **152개, 그중 부를 대상이 Furnace 에 살아 있는 것 21개**(Paper 몸통 대조로 2개가 더 빠짐)다. 부를 대상이 채워질수록 다음 실행에서 늘어난다(나머지 131개는 대상이 아직 껍데기).

## 정할 것

설계는 이 줄들을 "월드 밖 엔티티 대조기(O3)"가 생긴 뒤 대조해서 넣기로 했다.
그런데 대조기가 하는 일은 결국 `lerpTargetX()` 와 바닐라를 견주는 것인데, `lerpTargetX()` 는 `getX()` 를 부르기만 하므로 **실제로 시험되는 것은 Furnace 의 `getX()`** 다. 줄 자체가 틀릴 길은 없다:
- 도구는 바닐라 몸통이 **정확히** "인자 그대로 → 가상 호출(재정의 따라감) → 그대로 반환"일 때만 후보로 낸다(형 바꾸기·인자 빼기·다른 순서는 후보 아님).
- Paper 서버 몸통도 같은 꼴이어야 한다(Paper 가 고친 것은 빠짐).
- 부를 대상이 Furnace 에서 사람이 만든 몸통(손 shim·JDK·T-262 채움)일 때만. 대상이 아직 껍데기면 빌드 검사가 줄을 막는다.
- 부를 대상이 하위 클래스에서 아직 껍데기면, 부르면 그 껍데기가 오류를 낸다(틀린 값을 조용히 내지 않는다).

## 고를 것

- **A. 별칭도 모양 증명으로 지금 넣는다(추천)** — 엔티티 데이터 읽기 줄과 같은 규칙(바닐라·Paper 꼴 일치 + 빌드 검사). 지금 약 19~21줄, 대상이 채워질 때마다 기계적으로 늘어난다. 대상 메서드의 정확성은 그 메서드의 손 구현 검토·시험이 맡는다(지금도 그렇다).
- **B. 설계대로 대조기(O3) 뒤에 넣는다** — 대조기 만드는 데 2~3일. 그동안 이 줄들은 오류를 낸다. 대조기가 생겨도 실제로는 대상 메서드를 시험하는 것이라 별칭 줄 자체의 증명은 A 와 같다.

안 정하면(B 그대로): 별칭은 O3 뒤로 밀리고, 그 사이 플러그인이 이 메서드를 부르면 오류.

추천 A. 대조기(O2·O3)는 그대로 만든다 — 그것이 필요한 곳은 별칭이 아니라 **Bukkit 구현에 잇는 줄(G2)과 블록 상태 관용구(S4)**, 그리고 "이미 사람이 채운 멤버를 숨기고 도구가 같은 답을 내는지"(오채택 재기)다.
