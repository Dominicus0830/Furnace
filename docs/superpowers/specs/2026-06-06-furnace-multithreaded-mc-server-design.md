# Furnace — 바닥부터 만드는 멀티스레드 마인크래프트 서버 설계서

> 작성일 2026-06-06. 상태 승인 대기. 작성자 도미니코(손현민).

## 1. 비전

바닐라/기존 버킷은 월드 로직을 단일 스레드로 틱한다. 플레이어·엔티티·레드스톤이 몰리면 그 한 스레드가 병목이 되어 렉이 생긴다. Furnace는 **스레드 소유권을 코어 데이터 모델에 처음부터 박아** 이 병목을 구조적으로 푸는, 자바로 바닥부터 작성하는 마인크래프트 서버다.

기존 멀티스레드 서버(Folia)는 단일 스레드 코드베이스(Paper)에 지역별 스레딩을 나중에 끼워넣느라 고생했다. Furnace는 from-scratch라는 점을 최대 무기로 삼아, 동시성을 사후 기능이 아니라 **처음부터 불변식(invariant)** 으로 둔다.

### 프로젝트 성격

학습·장기 하비 프로젝트다. 여정(마인크래프트 내부·네트워킹·동시성 학습)이 목적이며, "천천히 그러나 완벽하게"를 페이스로 삼는다. 상업 운영(DailyTown 구동)은 현 시점 목표가 아니다.

## 2. 목표와 비목표

### 목표
- 자바 21+로 바닥부터 구현. Mojang/Bukkit 코드 미사용.
- 멀티스레드가 최우선. 지역(region) 단위 병렬 틱을 북극성으로 둔다.
- Paper처럼 **플러그인 API를 별도 모듈로 분리**. 구현이 바뀌어도 플러그인이 안 깨지게 한다.
- 마인크래프트 자바 1.21.1(프로토콜 767) 클라이언트와 통신.

### 비목표 (현 단계)
- 멀티 프로토콜 버전 동시 지원. 1.21.1 단일 버전 먼저. (YAGNI, 나중에 확장)
- 온라인 모드(Mojang 인증). 오프라인 모드 먼저.
- 바닐라 100% 기능 패리티. 학습 가치 우선으로 마일스톤마다 범위를 좁힌다.

## 3. 확정된 핵심 결정

| 항목 | 결정 | 근거 |
|---|---|---|
| 근본 방향 | 순수 바닥부터 (Java) | from-scratch의 무기 = 소유권을 코어에 선설계 |
| 언어 | Java 21+ | MC 생태계 표준, 세밀한 GC/성능 제어, Virtual Threads·Vector API 활용 |
| 동시성 | Region-owned 북극성, 단계적 구현 | 첫 플레이까지 막히지 않으면서 retrofit 회피 |
| API | `furnace-api` 별도 모듈 | Paper 패턴, 구현 무지(無知) 인터페이스 |
| 네트워킹 | Netty 기반, 1.21.1 단일 프로토콜 | 학습 범위 한정 |

## 4. 동시성 모델

### 4.1 북극성 — Region-owned

월드를 독립적인 **region**으로 나눈다. 각 region은 자기 청크와 엔티티를 소유하며, 별도 스레드(스레드풀)에서 틱한다. 한 객체는 항상 정확히 하나의 스레드가 소유한다. 다른 스레드가 그 객체를 직접 만지는 것은 금지다.

### 4.2 관통 불변식

새 객체·시스템을 만들 때마다 **"이것은 어느 스레드 소유인가"** 를 먼저 답한다. 디버그 빌드에서 잘못된 스레드의 접근은 즉시 assert로 터진다. 동시성은 기능이 아니라 지켜야 할 불변식이다.

### 4.3 단계적 구현

| 단계 | 동시성 실제 모습 | 학습 목표 |
|---|---|---|
| S1 | 틱 1스레드 + IO/네트워크/청크생성/조명 오프스레드 | 도메인 파악, 첫 접속 |
| S2 | region 추상화 도입, region 1개로 동작 | 소유권 경계 검증 |
| S3 | region N개 스레드풀 병렬 틱 | 진짜 Folia식 병렬 |
| S4+ | 교차지역 스케줄러, 핫존 내부 staged 병렬 | 한계 돌파 |

### 4.4 스케줄러 API 형태 — retrofit 회피 핵심 결정

스케줄러 API의 **형태(시그니처)는 M0에 고정**하고, **내부 구현만 후속 마일스톤에서 채운다.** region이 1개일 때(M0)와 N개일 때(M3)가 동일한 시그니처를 쓰도록, M0부터 모든 스케줄 연산을 **비동기 반환(`CompletableFuture` 또는 콜백)** 형태로 정의한다.

- region 1개 → 즉시/동기적으로 완료되더라도 반환 타입은 `CompletableFuture`.
- region N개 → 같은 시그니처, 콜백이 대상 region 스레드에서 실행되도록 내부만 변경.

이로써 "M0에서 API를 완성한다"는 과욕(=교차지역 의미론이 안 정해졌는데 완성 주장)을 피하고, 대신 **교차지역까지 수용하도록 설계된 v0 표면**을 둔다. 형태가 처음부터 비동기이므로 region 분할이 실가동돼도 시그니처를 갈아엎지 않는다.

스케줄러 종류 (Folia식, `furnace-api`에 노출).
- `GlobalScheduler` — 서버 전역, region 무관 작업.
- `RegionScheduler` — 특정 위치/region 소유 스레드에서 실행.
- `EntityScheduler` — 특정 엔티티 소유 스레드에서 실행(엔티티가 region 이동해도 따라감).

### 4.5 교차지역 최대 난제

폭발·엔티티 텔레포트·피스톤이 region 경계를 넘는 경우가 regionized 서버의 핵심 난제다. 처리 후보.
1. 관련 region 락 후 동기 처리 — 단순하나 락 경합 위험.
2. 메시지 패싱 — 타 region에 작업을 큐잉(Folia 방식) — 비동기 복잡.
3. 경계 넘는 연산을 `GlobalScheduler`로 직렬화 — 안전하나 느림.

**방침.** 북극성은 2번(메시지 패싱), 초기엔 3번으로 시작. M3 스펙에서 확정한다. 4.4의 비동기 시그니처 고정이 이 전환을 시그니처 변경 없이 가능케 한다.

## 5. 모듈 구조

```
furnace/
├─ furnace-api/      # 플러그인이 의존하는 순수 인터페이스. impl 무지(無知).
│                    #   스레드 소유권/스케줄러를 1급으로 노출 (Folia식 RegionScheduler)
├─ furnace-server/   # 코어 구현
│   ├─ net/          # 프로토콜, 패킷, 인코딩(Netty), 1.21.1 단일 버전
│   ├─ world/        # 청크, region IO(Anvil), region 소유권 모델
│   ├─ entity/       # 엔티티, 틱, 물리
│   ├─ registry/     # 블록/아이템/바이옴 레지스트리 (데이터 주도)
│   ├─ sched/        # 스레드풀, region 스케줄러, 틱 루프
│   └─ bootstrap/    # main, 설정, 플러그인 로더
└─ furnace-plugin-test/  # API 검증용 샘플 플러그인
```

플러그인은 `furnace-api`만 의존한다. `furnace-server` 변경이 플러그인을 깨뜨리지 않는다.

## 6. 마일스톤 로드맵

각 마일스톤은 도달 시점에 **자기만의 스펙 문서**를 따로 작성한다. 지금 M1~M6을 상세화하면 추측투성이가 되므로(YAGNI), 본 문서는 전체 로드맵 + M0 상세까지만 확정한다.

### M0 — 토대 + 스레딩 골격 (멀티스레드 심장)
- Gradle 멀티모듈: `furnace-api` / `furnace-server` / `furnace-plugin-test`.
- 틱 루프 (고정 20 TPS, 드리프트 보정).
- 스케줄러 코어. `GlobalScheduler`/`RegionScheduler`/`EntityScheduler` 표면을 **비동기 반환 시그니처로 고정**(4.4). region = 월드 전체 1개로 구현.
- 소유권 프리미티브. `Owned<T>` 개념 + 스레드체크 가드. 잘못된 스레드 접근 시 assert.
- 설정 로더, 구조화 로깅.
- ✅ verify: 20 TPS 유지(오차 측정), 태스크가 지정 스레드서 실행(스레드 id 단언), 소유권 위반 테스트가 실제로 터짐.

### M1 — 네트워킹: 핸드셰이크 → play 진입
- Netty 파이프라인, VarInt, 패킷 프레이밍/압축.
- 프로토콜 1.21.1(767) 상태. handshake/status/login/configuration/play.
- 서버 리스트 핑(status), 로그인(오프라인), configuration 단계, play 전이.
- KeepAlive, 디스커넥트.
- ✅ verify: 바닐라 1.21.1 클라가 접속→play 도달→빈 월드서 끊기지 않고 유지.

### M2 — 월드 데이터 모델 + 청크 전송 (지형 보임)
> 상세: `docs/superpowers/specs/2026-06-07-m2-world-chunk-transfer-design.md`
- 청크/섹션 구조, 팰릿(단일+간접+직접 전체)+비트스토리지(바닐라 포맷).
- 블록 레지스트리(바닐라 data report/데이터팩 기반, 데이터 주도).
- 월드 소스 = **superflat 생성만**. `WorldSource` 인터페이스로 Anvil 자리만 잡음(Anvil 읽기는 M4로 이동 — write와 짝).
- 청크 패킷 인코딩 전송 → 클라가 블록 봄. heightmap용 **NBT write 최소 도입**(M1의 무NBT 전제는 청크 패킷에서 깨짐).
- 첫 진짜 멀티스레드 이득. 청크 직렬화를 워커풀로 오프메인 → channel eventLoop서 순서전송.
- ✅ verify: 스폰 후 지형 렌더, 바닥 안 빠짐. 청크 직렬화가 워커 스레드서 도는 것 확인.

### M3 — 플레이어 이동 + 엔티티 틱 + region 소유권 실가동 (S2→S3)
> 크기가 커 3개로 분해: **M3a**(플레이어 이동·멀티플레이 가시성, S1→S2, region 1개 틱) · **M3b**(region N개 분할·병렬 틱, S2→S3) · **M3c**(교차지역 핸드오프·원자연산 §4.5 확정). 각자 spec→plan→구현.
> M3a 상세: `docs/superpowers/specs/2026-06-07-m3a-player-movement-design.md`
> M3b 상세: `docs/superpowers/specs/2026-06-08-m3b-region-parallel-tick-design.md`
> M3c 상세: `docs/superpowers/specs/2026-06-08-m3c-cross-region-visibility-design.md` (교차region 가시성=스냅샷. 교차region 원자 블록연산은 가변블록이 생기는 M4로 이동.)
> M3d 상세: `docs/superpowers/specs/2026-06-08-m3d-entity-view-distance-design.md` (엔티티 가시 거리를 view-distance에서 분리. 시뮬레이션 거리(틱 범위)는 M4+로 미룸.)
- 플레이어 엔티티, 이동 패킷, 위치 동기.
- 엔티티 베이스 + region 내 틱.
- 월드를 region으로 분할, 각 region이 자기 청크+엔티티 소유, 스레드풀서 병렬 틱.
- 교차지역 경계. 플레이어가 region 넘어가면 소유권 핸드오프.
- 교차지역 원자연산 처리법(4.5의 1/2/3) 확정.
- ✅ verify: 서로 다른 region의 두 플레이어가 다른 스레드서 틱(스레드 id 단언), 경계 넘어도 크래시/레이스 없음, 스트레스 테스트 통과.

### M4 — 상호작용 + 게임플레이 코어 + 영속성
> 크기가 커 3개로 분해: **M4a**(가변 블록=파괴 + region 청크 소유 + 교차region 블록 브로드캐스트) · **M4b**(Anvil read+write 영속성 + 청크 퇴출) · **M4c**(인벤토리/아이템/블록엔티티 + 블록 설치). 순서 a→b→c. 물리 전파·교차region 원자연산(§4.5)은 M5(틱 물리 대상 생길 때).
> M4a 상세: `docs/superpowers/specs/2026-06-08-m4a-mutable-blocks-design.md`
- 블록 파괴/설치, 블록 업데이트.
- 인벤토리 + 아이템 처리(기본), 블록 엔티티.
- 영속성. 청크/플레이어 저장 = **Anvil read+write 한 단위**(NBT reader 도입, M2 write와 합쳐 완성). 기존 월드 .mca 로드 + 저장 라운드트립.
- ✅ verify: 설치/파괴가 재시작 후 유지, 월드 save/load 라운드트립 일치.

### M5 — 엔티티/AI + 조명 + 확장 게임플레이
- 조명 엔진(오프스레드).
- 몹 엔티티, 패스파인딩(오프스레드).
- 레드스톤(난이도 높음, region 단위 업데이트).
- ✅ verify: 몹 스폰/이동, 편집 후 조명 정확.

### M6 — 플러그인 API 성숙
- 이벤트 시스템(스레드 인지형), 플러그인 로더.
- 플러그인용 스케줄러 API(region/entity/global) 정식 공개.
- 샘플 플러그인이 API 검증.
- ✅ verify: 샘플 플러그인이 올바른 스레드서 이벤트 반응.

## 7. 위험 요소

- **교차지역 원자연산**(4.5) — 프로젝트 최대 난제. 4.4의 비동기 시그니처 고정으로 retrofit 위험을 낮춤.
- **프로토콜 정확도** — 1.21.1 패킷 포맷 한 곳만 틀려도 클라가 침묵 종료. wiki.vg/Minecraft Wiki 프로토콜 문서를 1차 출처로 삼고, 패킷별 단위 테스트.
- **범위 폭주** — 학습 하비라 동기 유지가 관건. 마일스톤마다 "verify" 통과 = 작은 승리로 잘게 쪼갬.
