# 클라이언트 청크 로딩 느림 진단 — 2026-11-11

질문(도미니코): "클라이언트에서 봤을 때 청크 로딩 속도가 현저히 느린 것 같은데, 전송 시스템 문제인지 청크 계산·생성 시스템 문제인지."

**답: 둘 다 있었지만 체감의 대부분은 전송 쪽이었다.** 실제(바닐라) 클라이언트는 서버가 배치를 보내는 데 걸린 시간을 보고
받을 속도를 스스로 정하는데, Furnace 가 배치 시작(ChunkBatchStart)과 끝(ChunkBatchFinished) 사이를 거의 늘 한 틱(약 45ms) 벌려 놓아
클라이언트가 "나는 느리다"고 판단해 속도를 **틱당 0.15청크(초당 약 20청크)** 까지 낮췄다. 이미 만든 땅도 시야 10(441청크)에 22초가 걸렸다.
이 부분을 고쳐 **22.0초 → 9.5~11.3초**(이미 만든 땅), 새 땅 24.0초 → 13.7~13.9초가 됐다. 새 땅에서 남은 시간은 월드젠 CPU(전체 CPU 의 약 87%)다.

11-07 진단(`docs/feature-parity/perf-chunk-send-2026-11-07.md`)은 늘 64 를 답하는 측정 봇을 써서 이 문제를 보지 못했다.

## 1. 측정 방법

- 4코어 컨테이너, `-Xmx3G`, 시드 12345 노이즈 월드, 시야 10, `difficulty=peaceful`. 기준 = 기준 브랜치 88f33ee1.
- **바닐라 클라이언트 흉내 접속기** `tools/bot-test/chunkrate/vanillaclient.js`(새로 씀): minecraft-protocol 직접 접속, 바닐라
  `ChunkBatchSizeCalculator` 를 그대로 옮겼다 — Start 를 받은 때부터 Finished 를 받은 때까지 시간 ÷ 배치 크기 = 청크당 시간,
  지수 평균(새 표본은 이전 평균의 1/3~3배로 자름, 가중치 최대 49), `chunk_batch_received` 에 `7ms ÷ 평균` 을 답한다.
  (가정: 클라이언트 계산식은 기억한 바닐라 1.21.1 클라이언트 코드다. 컨테이너에서는 클라이언트 jar 를 못 받아 바이트코드로 대조하지 못했다.
  서버 쪽 `PlayerChunkSender`(난독 `arq`)는 바닐라 1.21.1 서버 jar 를 `javap -c -p` 로 대조했다 — 아래 3장.)
  봇 자신의 청크 처리 비용(압축 풀기·패킷 해석)은 청크당 약 1.5ms 로, 실제 클라이언트와 비슷한 크기다.
- 예전 접속기 `chunkrate.js`(늘 64 를 답함)는 "클라이언트가 아주 빠를 때"의 서버 상한을 볼 때만 쓴다.
- 빠른 이동: `chunkrate/vanillamove.js` — 콘솔 `/tp` 로 1초마다 32블록씩(초당 32블록, 겉날개 수준) 20번 옮기며, 옮기기 직전 반경 4청크를 받은 비율.
- 서버 단계별 시간: 새 옵션 `-Dfurnace.chunktrace=true` (`world/ChunkTrace`) — 5초마다 `[CHUNKTRACE]` 한 줄. 끄면 상수 거짓이라 비용 없음.

## 2. 진단 결과 (수정 전)

### 2-1. 전송: 클라이언트가 속도를 스스로 낮췄다 (주원인)

| 장면 (시야 10, 441청크) | 다 받기까지 | 초당 | 배치 평균 크기 | Start~Finished(클라이언트, 중앙값) | 클라이언트가 알린 속도 |
|---|---|---|---|---|---|
| 이미 만든 땅(디스크) | 22.0초 | 20.7 | 1.1 | 46.7ms | 0.15/틱 |
| 이미 만든 땅, 메모리(재접속) | 22.1초 | 20.6 | 1.1 | 47.7ms | 0.15/틱 |
| 새 땅 | 24.0초 | 19.2 | 1.1 | 46.9ms | 0.15/틱 |
| 이미 만든 땅, 4명 동시 | 22.3~23.3초 | 20~20.8 | 1.1 | — | 0.3~2.1/틱 |
| (참고) 늘 64 를 답하는 봇, 디스크 | 3.2초 | 176 | 18 | — | 64 |

`[CHUNKTRACE]`(디스크, 정상 상태): `batch avg=44.8ms`, `batch.cached avg=0.00`, `batch.size 1.00`, 그 안의 `ser 2.1ms` + **`hop.ser 42.2ms`**, `client.want 15`(=0.15/틱).

원인 사슬:
1. auto 전송(`Region.sendQueuedChunksAuto`)은 로드된 청크를 배치에 넣지만, 디스크에서 막 올라왔거나 갓 생성된 청크는 **본문(패킷 바이트)이 아직 없다**.
2. 본문은 직렬화 풀에서 만들고(2ms), 결과를 캐시에 넣는 일은 주인 region 작업 큐로 돌아가는데 이 큐는 **틱마다 한 번** 비워진다 → 평균 42ms 뒤 다음 틱에 청크와 Finished 가 나간다.
3. 바닐라 클라이언트는 이 45ms 를 "청크 하나 처리에 45ms" 로 보고 `7ms ÷ 45ms ≈ 0.15` 청크/틱을 요청한다.
4. 바닐라 규칙(배치 응답 때 미확인 배치가 0 이면 quota=1)대로 한 왕복에 한 청크씩 → 초당 약 20청크에 고정. 배치가 작아질수록 한 청크당 시간이 커져 회복하지 못한다.
5. 원격 접속이면 왕복 시간(RTT)이 더해져 더 느리다(한 청크당 RTT+45ms).

바닐라 `PlayerChunkSender.sendNextChunks` 는 준비된(`LevelChunk`) 청크만 대기 집합에 두고, Start → 청크 패킷 생성·전송 → Finished 를 **한 호출 안에서** 끝낸다(3장).
그래서 바닐라에서 클라이언트가 재는 시간은 자기 처리 시간과 전송 시간뿐이다.

## 3. 바닐라 대조 (1.21.1 서버 `arq` = PlayerChunkSender, `javap -c -p`)

- 시작 속도 9.0, 미확인 배치 상한 첫 응답 전 1 → 응답 뒤 10, 응답값 `clamp(0.01, 64)`, NaN 이면 0.01, 응답 때 미확인 0 이면 quota=1.0 — Furnace `ChunkSendRate` 와 같다.
- `sendNextChunks`: quota 를 채우고, 대기 집합(로드된 청크만 들어감)에서 가까운 순으로 floor(quota) 개를 골라 `aci`(Start) → 청크마다 `adg`(LevelChunkWithLight) 를 그 자리에서 만들어 전송 → Finished(크기) — 모두 한 호출 안.
- Furnace 의 남은 차이(이번에 안 바꿈): 첫 응답이 오기 전까지는 **틱마다** 64개까지 배치를 보낸다(바닐라는 9개 배치 하나를 보내고 응답을 기다린다). 접속 직후 클라이언트가 첫 응답을 보낼 때까지(보통 왕복 한 번)만 해당.

## 4. 고친 것 (`chunks-per-tick=auto`, 기본값)

- `Region.sendQueuedChunksAuto`: 로드된 청크 중 **본문이 준비된 것만** 배치에 넣는다. 준비 안 된 것은 직렬화만 걸어 두고(한 틱에 최대 64개, 가까운 것부터) 다음 틱에 보낸다.
  → 배치는 Start·청크·Finished 가 한 틱 안에서 동기로 나간다(바닐라와 같은 모양). 다른 region 이 가진 청크는 예전처럼 배치 안에서 기다린다(드묾).
- `World.chunkBodyReadyOrPrefetch`: 본문 준비 확인 + 미리 직렬화. 레드스톤처럼 **매 틱 블록이 바뀌는 청크**는 직렬화가 끝나 캐시에 들어가도
  보내기 직전에 다시 비워져 영영 못 갈 수 있다 — 보내려다 2틱 기다린 청크(`ChunkColumn.bodyWaits`)는 바닐라처럼 그 자리(region 스레드)에서 직렬화한다
  (청크당 약 2ms, 측정 중 시야 10 한 번에 1개 꼴). 이런 청크가 많아도 한 틱에 몰리지 않게 region 당 틱마다 4개까지(`Region.MAX_SYNC_BODIES_PER_TICK`).
- 미리 직렬화 창: 배치 다음의 로드된 청크를 클라이언트 속도(또는 이번 예산)의 2배, 2~64개만 본다(첫 응답 전 64). 느린 클라이언트에서 보내지도 않을
  본문을 매 틱 다시 만들지 않게, 예산이 0인 틱에 대기열 1,024개를 끝까지 훑지 않게.
- 숫자 `chunks-per-tick` 설정(예전 동작)은 그대로.
- 진단 옵션 `-Dfurnace.chunktrace=true` 추가.
- 시험: `ChunkSendAutoTest.everyBatch_finishesInTheTickItStarted`(배치가 tick() 안에서 닫히는가 — 예전 동작으로 되돌리면 실패),
  `chunkChangedEveryTick_isStillSent`(매 틱 markDirty 되는 청크도 온다 — 대기 상한을 없애면 실패), 기존 `loadedChunks_goOutAtClientRate_notCappedAt16` 은
  "첫 틱은 직렬화만, 다음 틱에 64개"로 기대를 고쳤다.

## 5-1. 독립 검토 반영 (2026-11-11, `/mnt/project-files/furnace/reviews/chunk-pr211.md`)

검토 판정: 병합을 막는 문제 없음. 실서버 재현 디스크 시야 10 21.7초 → 8.8~9.0초, 클라이언트 속도 0.15 → 4.2/틱.
- R1(중간) 매 틱 바뀌는 청크가 많을 때 바로 직렬화가 한 틱에 상한 없이 몰림(재현 한 틱 64개) + 느린 클라이언트(0.15/틱)에서 미리 직렬화 64개 창이 40틱에 2,254번 직렬화 →
  틱당 4개 상한과 클라이언트 속도에 맞춘 창으로 고침: 같은 재현에서 한 틱 최대 4개(81청크 모두 23틱에 도착), 40틱 직렬화 194번. 시험 `everyChunkChangingEachTick_syncSerializationIsCappedPerTick`.
  (검토 메모: 화로·호퍼의 내용 변화는 markChunkDirty 만 해서 본문 캐시를 비우지 않는다 — 실제로 해당하는 것은 블록 상태가 매 틱 바뀌는 청크.)
- R2(낮음) 예산 0인 틱에 대기열을 끝까지 훑음 → 창이 준비된 청크도 세도록 고침.
- R3(낮음, 그대로) 다른 region 이 가진 청크·청크를 만들지 않는 관전자의 청크는 여전히 배치가 틱을 넘을 수 있다. region 이 합쳐지면 사라지는 짧은 상태.
- R4(문서) 첫 응답 전 동작 문구를 3장에서 고침.

## 6. 남은 후보 (크기 순)

1. **월드젠 CPU**(새 땅의 유일한 큰 병목): 노이즈·밀도 함수 53% — `ImprovedNoise` 결과 공유·캐시, `NoiseChunk` 보간 경로 점검. 표면 10%, 바이옴 RTree 7%. 결과가 칸 단위로 바닐라와 같아야 하므로 oracle 대조 시험과 함께(Opus high 권장).
2. **직렬화 결과의 작업 큐 왕복**(`hop.ser` 평균 42ms): 미리 직렬화 결과를 "급한 작업"으로 넣어 틱 사이에 캐시를 채우면 빠른 클라이언트의 한 틱 지연(3.2 → 3.6초)도 없앨 수 있다. 작음.
3. **설치 왕복**(`hop.load` 평균 20~25ms)과 생성 풀 대기(`hop.genpool`): 빛 계산이 월드젠과 같은 풀에서 줄 선다 — 빛을 다른 풀로 나누면 새 땅에서 가까운 청크가 조금 빨리 보인다.
4. 첫 응답 전 64개 배치(바닐라는 9개): 바닐라와 맞출지 결정 필요 — 접속 직후 첫 화면만 해당.
