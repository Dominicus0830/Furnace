근거는 R0 재측정 보고서(`R0-remeasure-cloud.md`·`R0-remeasure-laptop.md`), 청크 전송 진단(`docs/audit/chunk-loading-diagnosis.md`)과 현재 코드 읽기다.

## 1. 후보 ① 본문 직렬화 풀 대기 `hop.serpool`

### 1-1. 지금 구조(코드 확인)
- 청크 본문 직렬화(`World.startBodySerialization` → `serializeChunkBody`)는 전용 풀 `ChunkWorkerPool`(`net/ChunkWorkerPool.java`)에서 돈다.
  이 풀은 `newFixedThreadPool(코어 수)`, 스레드 우선순위 NORM−1, **무제한 FIFO 큐 하나**다. 이 풀의 사용처는 본문 직렬화 하나뿐이다(`World.java:1456`).
- 한 일은 직렬화(`ChunkSerializer`) + 미리 압축(`SharedChunkFrames.precompress`, zlib 레벨 6)이다. 압축이 전송 비용의 약 80%(B1 보고서, 11-14).
- 일을 거는 쪽은 둘이다. ① **요청된 일**: 이미 보낼 차례가 와서 본문이 필요한 청크(`speculative=false`). ② **미리 직렬화**: 배치 뒤쪽 청크를 클라이언트 속도의 2배, 2~64개 창으로 미리 만든다(주인 region 스레드에서 걸면 `speculative=true`, T-011. 주인 스레드가 아닐 때는 `serializedChunkBody(cp,true)` 길로 `speculative=false` 로 걸려 낡은 일 건너뛰기를 못 받는다 — `World.java:1556`, 독립 검토 지적). 둘이 같은 큐에 **들어온 순서대로** 선다.
- 미리 직렬화 일이 풀에서 시작할 때 이미 낡았으면 건너뛴다(`ser.staleskip`, T-011). 요청이 붙으면 `speculative` 가 거짓으로 바뀐다(`BodyJob.speculative` volatile).

### 1-2. 측정 근거(이미 있는 것)
| 장면 | A(1차 기준) | B(2차 기준) | 출처 |
|---|---|---|---|
| 클라우드 4코어, 냉 8×16, 풀 대기 평균/최대 | 6086 / 9888 ms | 82~119 / 247~297 ms | R0 클라우드 |
| 노트북(스레드 12), 냉 8×16, 붐빌 때 창 평균 | 68~142 ms | **277~753 ms**(최대 1.3~1.4초) | R0 노트북 |
| 같은 노트북 장면 직렬화/보낸 청크 | — | 0.45~0.69(A 2.41) | R0 클라우드 표 |

- 클라우드에서는 T-011 로 풀 대기가 **크게 좋아졌다**(6초 → 0.1초). 노트북에서만 B 가 A 보다 길다. 같은 노트북에서 전체 시야 도착 시간은 B 가 13~19% 짧다. 그러니 풀 대기가 **지금 전체 시간의 병목이라는 증거는 없다.**
- 노트북 B 가 길어진 원인은 코드·측정에서 확인되지 않았다. 가정: (a) B 는 미리 직렬화를 더 일찍·많이 걸어 큐가 깊어졌다(T-011 창), (b) 생성 풀(코어−1)과 CPU 를 다툰다(`ThreadPriorityPolicy` 가 윈도에선 안 먹어 NORM−1 이 효과 없음 — B2 보고서). 둘 다 `hop.serpool` 을 요청 일/미리 일로 나눠 보면 가려진다. **지금 chunktrace 는 둘을 합쳐 평균 낸다**(`World.java:1465`).
- 풀 대기가 길어도 클라이언트 속도 추정은 안 나빠진다(Start~Finished 는 이미 준비된 본문만 한 틱 안에 보낸다 — 진단 문서 4장). 영향은 **본문이 늦게 준비되어 그 청크가 한두 틱 뒤에 나가는 지연**뿐이다.

### 1-3. 개선안과 기대 이득
**안 A (권장): 두 차선 큐 — 요청된 일을 미리 직렬화보다 먼저.**
- 풀 안에서 "요청된 일" 큐와 "미리 직렬화" 큐를 따로 두고, 스레드는 요청된 쪽부터 꺼낸다. 미리 직렬화는 요청이 붙으면 요청 큐로 올린다(한 번만 돌게 하는 완료 표시 필요). 미리 직렬화가 굶지 않게 일정 시간(예: 50ms) 이상 기다린 일은 요청 큐 뒤에 합친다.
- 기대 이득: 붐빌 때 **지금 보낼 청크의 본문 대기만** 줄어든다(미리 일 뒤에 줄 서는 몫 제거). 풀 총 처리량·CPU 는 그대로다. 이득의 크기는 위 가정 (a) 가 맞아야 나온다 — 그래서 **구현 첫 단계가 측정 분리**(1-5).
- 결과 동일: 직렬화 바이트는 그대로, 순서만 바뀐다. 청크가 클라이언트에 나가는 순서는 `PlayerChunkSender` 가 거리순으로 정하므로 바닐라 순서·내용에 영향 없다. 증명: `ChunkSendPacketOrderGoldenTest`·`ChunkBodyCacheRaceTest` 통과 + 봇이 받은 청크 해시 = 서버 해시.
- 위험: ① 승격 경쟁(미리 일을 요청 큐로 옮길 때 두 번 도는 것 — 완료 표시로 막음) ② 굶김(요청 일이 계속 오면 미리 일이 안 돈다 → 위 시간 상한) ③ 스레드 간 순서가 바뀌어 `modCount`·진행 표시 규칙(`inflightSerializedBody` 읽는 순서)을 깨지 않아야 함 — 진행 표시 읽기 순서 주석(`World.java:1457`)을 지킨다.

**안 B: 풀 크기·우선순위 조정(코어 수 → 코어−N 등).** 기각 후보: 코어 수가 적은 장비에서 직렬화가 생성에 굶는지 아닌지는 장비마다 다르다. 측정 없이 바꾸면 B2 가 이미 "스레드 줄이기 기각"으로 결론낸 방향과 부딪친다. 근거 없이 만지지 않는다.

**안 C: 압축 레벨·libdeflate(M-05).** 풀 처리량 자체를 올린다(압축이 비용 80%). 이미 M-05(측정 먼저)·T-025(설정 키)로 등록돼 있어 새 번호를 안 만든다. 이 후보의 이득이 가장 클 수 있으나(풀이 포화인 장면에서만), 결정 3·4(도미니코 — 압축 레벨 기본값)가 걸려 있다. 풀 포화가 안 보이는 현재 측정에서는 순서도 낮다.

### 1-4. 판정
- **T-226 등록(P2, OPT, 측정 먼저 → 구현)**: 안 A. 1단계는 계측만(작은 PR). 2단계(큐 교체)는 계측에서 "요청 일의 풀 대기 평균이 미리 일보다 뚜렷하게(예: 2배 이상) 길거나 100ms 를 넘을 때"만 진행. 기준이 안 맞으면 폐기한다(풀 대기가 병목 아님).
- 안 B 기각, 안 C 는 기존 M-05 유지.

### 1-5. 구현 계획(T-226)
1. **계측(코드 약 15줄)**: `hop.serpool` 을 `hop.serpool.req`·`hop.serpool.spec` 으로 나누고 풀 큐 깊이(`queue.size()`)를 chunktrace 에 한 줄 추가. 끄면 비용 없음(`ChunkTrace.ON` 상수 거짓). 시험: 기존 chunktrace 시험이 있으면 키 이름만 갱신.
2. **측정(도미니코 PC, 코디네이터 요청)**: 아래 3장 계획서 ①.
3. **조건 충족 시 큐 교체**: `ChunkWorkerPool` 에 두 차선(`PriorityBlockingQueue` 대신 `ConcurrentLinkedQueue` 두 개 + 스레드가 요청 큐부터 poll). `BodyJob.speculative` 가 바뀌는 지점에서 승격. 시험: (a) 요청 일이 미리 일을 추월한다 (b) 승격한 일이 정확히 한 번만 돈다 (c) 미리 일이 시간 상한 뒤엔 돈다 (d) 기존 `ChunkBodyCacheRaceTest`·`ChunkBodyLightDeferTest` 통과.
4. A/B: 같은 측정을 한 번 더 → 요청 일 풀 대기·시야 도착 시간·TPS. 이득이 잡음(같은 변형 1~5초) 안이면 되돌린다.

규모 S(계측)+M(큐), 모델 Sonnet high(큐·승격 경쟁은 독립 검토 필수).

### 1-6. 독립 검토 반영(Explore 읽기 전용 검토, 11-20)
구현 때 반드시 지킬 것(T-226 2단계 조건):
1. 승격은 큐 중복 등록으로 하지 않는다. 중복분이 낡은 일 건너뛰기에서 `null` 을 돌려주면 `World.java:1470` 의 `handle` 이 `f.complete(null)` 을 해 기다리던 요청이 null 본문을 받는다. 일마다 원자 상태(대기·승격됨·시작됨)를 두고 CAS 로 한 번만 시작한다.
2. `ChunkWorkerPool.submit` 은 `supplyAsync` 로 감싸 BodyJob 이 큐에서 안 보인다. 시그니처를 바꿔 큐 항목이 상태를 들게 한다. 두 차선은 논블록킹 큐라 워커를 깨울 장치(세마포어·LockSupport)가 필요하다 — `LinkedBlockingQueue` 두 개 + 한 세마포어가 더 단순하다.
3. 진행 표시를 먼저 읽고 `speculative` 를 나중에 읽는 순서(`World.java:1457`)를 차선 선택·시간 상한 합치기에도 지킨다. 시간 상한으로 합친 일은 차선만 옮기고 `speculative=true` 로 둬 낡은 건너뛰기를 계속 받게 한다(승격과 구분).
4. 계측 분류는 submit 시점이 아니라 **풀에서 시작하는 시점의 값**(승격 여부 포함)으로 기록한다. 대기 중 승격된 일이 spec 쪽에 잡히면 요청 대기가 과소 측정된다. 주인 스레드가 아닌 길의 미리 직렬화(1-1)는 별도 이름으로 센다.

## 2. 후보 ② 스폰 청크 CPU

### 2-1. 지금 구조(코드 확인)
- F6(PR #279 등): 주 오버월드에 바닐라와 같은 START 티켓을 건다. 게임 규칙 `spawnChunkRadius`(기본 2)+1 거리, 중심은 월드 스폰. 청크 49개(7×7)가 늘 올라와 있고, 예약 틱(블록)·엔티티 틱은 `spawnTicketWithin` 판정으로 돈다(`World.java:1818,1845`).
- **무작위 틱·자연 스폰은 이 청크들에서 돌지 않는다**: `Region.collectTickingChunks` 는 `players.isEmpty()` 면 바로 0 을 돌려주고(`Region.java:1981`), 아니면 플레이어 근처(체비셰프 NATURAL_SPAWN_RANGE)만 모은다. 바닐라와 같다(바닐라는 스폰 청크도 플레이어 없이는 무작위 틱 없음 — PR #279 검토).
- 그러므로 스폰 청크가 플레이어와 멀 때 드는 일은 예약 틱·블록 이벤트뿐이고, 엔티티·블록 엔티티 틱은 접속자가 있거나 `world.tick-when-empty` 가 늘 돌림일 때만 돈다(`emptyIdle` 300틱 규칙, `World.java:1066~1095`, `RegionLevel.java:373`). 유휴 측정은 이 쉼 상태다. 스폰 지점에 농장·호퍼가 없으면 거의 0 이다.

### 2-2. 측정 근거
| 항목 | A(스폰 청크 없음) | B(49청크) | 출처 |
|---|---|---|---|
| 유휴 로드된 청크 | 0~1 | 49 | R0 |
| 유휴 CPU | 2.7%(클라우드) / 3.3~3.6%(노트북) | 3.4% / 3.3~3.6% | R0 클라우드·노트북 |
| 유휴 region MSPT | 0.7(첫 판) → 0.66 | 0.27~0.30 ms | R0 노트북 |
| 유휴 RSS | — | +100~130MB | R0 노트북 |
| 새 월드 기동 | — | +1.2초, 할당 +40~50% | R0 |
- 유휴 CPU 증가는 클라우드 +0.7%p(4코어 기준 약 0.03코어), 노트북은 **같음**. 49청크 region 틱 평균 0.3ms 는 한 틱 50ms 의 0.6%.
- 보고서가 따로 문제로 적은 것은 **1명 걷는 장면에서 B 의 CPU 가 1.3 → 2.2코어**인 것인데, 이는 유휴 스폰 청크 몫이 아니라고 이미 판정됐다. 원인은 가정이다(걸으며 생기는 원형 둘레 청크 생성, 로드 청크 500 → 1160). 스폰 청크가 원인이라는 증거는 없다.

### 2-3. 개선안과 판정
- 유휴 비용이 측정상 0.3ms/틱이고 무작위 틱이 없으므로 **줄일 코드 후보가 지금은 없다**. 스폰 청크를 끄거나 반경을 낮추는 것은 바닐라와 결과가 달라지므로(예약 틱 장치·호퍼 시계 등 관측 결과 변화) 성능 이유로 기본값을 바꾸지 않는다(PR #279 확정: 바닐라 일치, 운영자는 게임 규칙 `spawnChunkRadius` 로 직접 조절 가능).
- 가능한 후속 둘, 모두 **실측 뒤에만**:
  1. 스폰 구역에 레드스톤·호퍼·소 농장이 큰 서버에서 그 region 이 별도 틱 한 몫을 먹는가(스폰 농장은 일반적). 이건 스폰 청크 문제가 아니라 일반 엔티티·블록 엔티티 틱 비용이라 기존 엔티티·블록 TASK 에 흡수된다.
  2. 새 월드 기동 +1.2초·할당 +40~50%(49청크 생성). 대부분 월드젠이고 바닐라도 같은 청크를 만든다. 요새 고리 계산(T-024)이 기동 CPU 의 47~56% 라 그쪽이 먼저다.
- **TASK 신규 없음.** 새 측정 항목 M-22 만 등록한다(아래 3장 ②).

## 3. 측정 계획(코디네이터가 도미니코 PC 스레드에 요청할 것)
같은 PC 에서 다른 시험과 겹치지 않게, Java 서버·Node 봇, UTF-8, 콘솔 창. 빌드는 같은 jar 로 모든 변형을 돈다.

① **serpool 분리(T-226 1단계 계측 PR 이 병합된 뒤)** — 장면: R0 ③ 냉 8×16 (만든 땅을 다시 열고 8명이 시야 16으로 접속), `-Dfurnace.chunktrace=true`, 노트북·데스크탑 각 3판, 변형은 기본/`-XX:ActiveProcessorCount` 로 코어를 반으로 줄인 것. 기록: `hop.serpool.req`·`.spec` 평균·최대·큐 깊이, 시야 도착 시간, 가장 느린 TPS. 판정 기준은 1-4.

② **M-22 스폰 청크 A/B** — 같은 jar 로 게임 규칙 `spawnChunkRadius` 0(0 이면 거리 1 이라 티켓을 안 건다 — `World.refreshSpawnTicket`) 대 2(기본), 두 장면: (가) 유휴, 접속자 0, 5분 (나) 1명이 R0 ② 새 땅 걷기(o00walk2.js), 같은 시드. 각 3판. JFR(`-XX:+DebugNonSafepoints`) 실행 표본에서 스폰 구역 청크(월드 스폰 7×7) 소속 스택 몫과 CPU 코어 수를 본다. 목적은 1명 장면 1.3 → 2.2코어의 원인을 "스폰 청크" 대 "원형 둘레 생성"으로 가르는 것. 판정: (가)(나) 모두 스폰 청크 몫이 CPU 의 2% 미만이면 후보 닫음.
