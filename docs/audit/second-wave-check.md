## 3. 치명도 판정

### 3.1 올림: A14-01 `PluginTasks` 누수 — 높음 → **치명(충돌)**

계획서 정의의 "충돌"에 해당한다고 본다. 까닭은 아래 계산이다.

끝난 한 번짜리 작업 하나가 붙잡는 것(64비트 HotSpot, 압축 포인터, 객체 8바이트 정렬 — **계산값, 힙 덤프로 재지는 않았다**):

| 객체 | 크기 |
|---|---|
| `TaskScheduler.Once`(머리 12 + 참조 4 + boolean 1) | 24 B |
| `guard` 람다(머리 12 + 잡은 참조 3개) | 24 B |
| `ConcurrentHashMap` 노드(머리 12 + hash·key·val·next) | 32 B |
| 표 칸(참조 4 B, 채움 0.375~0.75) | 5~11 B |
| 플러그인 람다(참조 1~3개를 잡을 때) | 16~24 B |
| **합계** | **약 100~115 B + 람다가 잡은 객체** |

| 거는 속도 | 하루 쌓이는 수 | 하루 늘어나는 힙(최소) | 힙 4 GB 가 차는 데 |
|---|---|---|---|
| 초당 20개(틱당 1개) | 173만 | 약 0.17~0.2 GB | 약 3주 |
| 초당 100개 | 864만 | 약 0.86~1.0 GB | 약 4~5일 |
| 초당 1000개(접속자 50명 × 틱당 1개) | 8640만 | 약 8.6~10 GB | **약 10시간** |

- 위는 최소값이다. 람다가 플레이어·아이템·이벤트 객체를 잡으면 나간 플레이어 객체까지 통째로 남아 훨씬 빨리 찬다.
- 권장 API 경로(`tasks().runGlobal`·`runRegion`)의 평범한 쓰임새(다음 틱 되돌리기, 지연 메시지)에서 생기고, 다시 켜기 전에는 줄지 않는다. 결과는 힙 고갈 → GC 멈춤 → OOM 으로 서버가 죽는다.
- 수정은 작다(실행 뒤 집합에서 빼기). **치명으로 올리고 A14 수정의 맨 앞에 둔다.** 모델은 보고서대로 Sonnet medium.

### 3.2 그대로지만 먼저: A08-01 잔디·균사체·나일리움 빛 차단 근사 — 높음 유지, **우선순위 맨 앞**

- 양탄자·중계기·비교기·퇴비통 밑 잔디가 무작위 틱으로 흙이 된다(재현 확인). 잔디 위 양탄자는 아주 흔한 건축이고, 서버가 도는 동안 **저장된 월드가 조용히 바뀌며 되돌아가지 않는다**(플레이어가 다시 깔아야 한다).
- 블록이 사라지거나 아이템이 없어지는 것은 아니라 "손상" 정의에는 못 미친다고 봤다(높음 유지). 다만 고치기 전까지 피해가 계속 쌓이는 유일한 2차 항목이라 가장 먼저 고칠 것을 권한다. 수정은 판정 함수 교체 하나(빛 표는 이미 있음).
